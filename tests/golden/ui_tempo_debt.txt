# UI 动效节拍台账 —— 只减不增（tools/ui_tempo_audit.py 守）
#
# 【这张表记的是什么】非战斗场景里**直接写死毫秒数**的 tween 处数与取值种类。
#   目标不是"少用 tween"，是**收成少数几档**（`UIPalette.T_TAP/T_BASE/T_TRANS/T_SLOW/T_SET`）。
#
# 【依据】用户 2026-09-30「我需要你一帧帧看」+ 那段 84 秒真机录屏。
#   2026-10-02 补量（我欠了三遍的那个「动效毫秒数」）：2480 帧全抽、逐帧差分、
#   门槛取差分分布 90 分位（2.99，中位 0.14）、连续段容忍 3 帧静止 ⇒ 50 段动效。
#   ★参考的节拍只有**三档**：转场 ~300ms · 点击/状态反馈 135~240ms · 大段演出 1.0~1.7s
#   ★★而我们这边 **169 处 tween 用了 45 种时长**（30ms ~ 2900ms）—— 每个动画各拍一个数。
#
# 冻结于 2026-10-02
#   起点: 处数 169 / 种类 45
#   样板批（v0.19.494）: MainMenuScene 8 处 + MatchmakingScene 1 + SettingsScene 1
#     共 10 处换成 T_TAP / T_TRANS ⇒ 处数 169 → 159。
#   ⚠ 种类数仍是 45：0.12 与 0.30 在**主战斗文件**里还有 13 处没换（那批留给下一轮，
#     本仓规矩是大改先在小批上过门禁再铺开）。种类数要等那 13 处也换完才会掉。
#
#   第二批（v0.19.497）: 把**数值上正好等于某个档位**的 40 处全换成常量 ——
#     T_BASE 14 · T_SLOW 9 · T_TAP 7 · T_TRANS 6 · T_SET 4
#     (RealtimeBattle3DScene 33 / SettingsScene 3 / MainMenuScene 2 / TeamSelectScene 2)
#     ⇒ 处数 159 → 119，种类数 45 → **40**（五个档位的裸数字全部绝迹，第一次掉下来）。
#   ★这批**零视觉风险**：改的是写法不是数值（0.12→T_TAP 而 T_TAP := 0.12）。
#     替换用的正则与本审计器**逐字相同** —— 它是账，我不另立口径。
#   ★★剩下的 119 处是**另外 40 种数值**，不能一刀切往档位上靠：
#     离最近档位 ±7%~±100%（T_SLOW±9% 17 处 / T_TAP±17% 16 处 / T_TAP±100% 12 处 …）
#     —— 那是真改动效，得逐个看它在演出里干什么（memory `fb-my-thresholds-degrade-good-assets`:
#     「我拍的阈值会把好素材改坏」）。众数指路：500ms×11 · 140ms×9 · 400ms×8 · 420ms×8。
# ════════════════════════════════════════════════════════════════════
# ★★2026-10-02 第二批 —— 顺手发现**上面那两个基线数字本身是错的**
# ════════════════════════════════════════════════════════════════════
#
# 【怎么发现的】准备把「数值上正好等于某档位」的那批换成常量时，抽查 diff 看到一行：
#     tw.tween_property(spr, "position", _world_pos(pos2d, UIPalette.T_SET), 0.42)
#   改掉的是**内层 `_world_pos` 的参数**，不是时长 0.42。
#   根因在审计器原来那条正则：`tween_(?:property|interval)\([^)]*?,\s*([0-9.]+)\s*\)`
#   —— `[^)]*?` 非贪婪，遇到嵌套调用就停在**内层**的右括号上。
#
# 【于是它两头都错】另写一个括号配平的解析器对账（两套独立实现结果完全一致）：
#     · **虚报 21 处**：`tween_property(spr,"scale",Vector3(0.3,0.3,0.3),0.46)` → 数成时长 0.3
#     · **漏报 65 处**：`tween_interval(1.4)` 没有逗号，一次都没被数到
#   真账是 **203 处 / 43 种**，不是 159 / 45。
#   ⚠ 所以「159」这个基线是**虚报与漏报互相抵消后的巧合数字** ——
#     而棘轮把它焊成了下限，等于**让错判据守得更牢**。
#
# 【修了什么】审计器改用 `tween_durations(src)`（括号配平、取最后一个顶层参数）。
#   批量改造脚本 **import 这个函数**复用口径，不再自己抄一条正则
#   （memory `fb-hand-rolled-copies-drift`：手抄的副本必然落后）。
#   顺带给审计器加了 `if __name__ == '__main__'` 守卫 —— 不加的话 import 当场跑完并 sys.exit。
#
# 【这一批改了什么】数值上**正好等于**某个档位的 42 处全换成常量：
#     T_BASE 15 · T_SLOW 11 · T_TAP 9 · T_TRANS 5 · T_SET 2
#     (RealtimeBattle3DScene 34 / MainMenuScene 3 / TeamSelectScene 2 /
#      MatchmakingScene 1 / SettingsScene 1 / hp_bar 1)
#   ⇒ 处数 203 → **161**，种类数 43 → **38**（五个档位的裸数字全部绝迹）。
#   ★零视觉风险：改的是写法不是数值（0.12 → T_TAP 而 T_TAP := 0.12），42 增 42 删。
#
# 【剩下的 161 处 / 38 种不能一刀切】它们离最近档位 ±7%~±100%。
#   往档位上硬靠就是真改动效，得逐个看它在演出里干什么
#   （memory `fb-my-thresholds-degrade-good-assets`：我拍的阈值会把好素材改坏）。
#   众数指路：140ms×13 · 500ms×12 · 420ms×10 · 100ms×10 · 600ms×8 · 180ms×8
#
# 【第三批：量过，决定不做】先按「它在演出里干什么」分类，不按数值大小：
#     淡入淡出 modulate  74 处 · 29 种 (30~900ms)
#     缩放 scale         27 处 · 18 种 (50~1200ms)
#     位移 position      24 处 · 17 种 (40~1400ms)
#     间隔/等待          18 处 · 16 种 (50~2600ms)
#     变色 color          9 处 ·  8 种 / 尺寸 pixel_size 7 处 · 7 种 / 帧 frame 2 处
#   对参考的三档（反馈 135~240 · 转场 ~300 · 大段 1000~1700）:
#     反馈 37 处(23%) · 转场 10 处(6%) · 大段 6 处(4%) · **档外 108 处(67%)**
#
#   ★想找一条「不是我拍的」吸附判据: 60fps 下一帧 16.7ms，差不到一帧的就是同一个动画。
#     实测 **≤1 帧只命中 2 处**（都是 130ms→T_TAP），种类数 38→37 —— 这条路没收益。
#     放宽到 ≤2 帧（33ms）能动 55 处，但 140ms→120ms 是 **14% 的变化** ——
#     **那是真改手感，不是重构**（memory `fb-my-thresholds-degrade-good-assets`）。
#   ⇒ 剩下 161 处 / 38 种**不动**。要继续收，得先逐角色量参考（「参考的淡出是多少毫秒」），
#     拿外部尺子定每一档，而不是我挑个阈值往上吸。本审计器照旧守住「不许回潮」。
#
