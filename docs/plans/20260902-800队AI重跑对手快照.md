### 现有 AI 到底「蠢」在哪 —— 逐条查过，不是我印象

`tests/_cohort.gd:31`：

```gdscript
const STRATEGIES := ["merge_first", "greedy_cost", "random", "synergy"]
```

四种策略**只作用在「货架 10 格按什么顺序买」这一个决策上**（`_cohort.gd` 的 `idxs.sort_custom`）：

| 策略 | 实际行为 | 蠢在哪 |
|---|---|---|
| `random` | 随机排序 | 纯噪声，不是玩家会有的行为 |
| `greedy_cost` | 按 `cost` 从高到低 | 只看单件费用，**不看羁绊、不看是否合成、不看龟的定位** |
| `merge_first` | 优先买"已有 1～2 张的同 id" | 只追三合一，**从不看类型** |
| `synergy` | 优先买"能推过下一档阈值"的（2026-08-12 才加） | 四种里唯一看羁绊的；但**只看下一档**，不认"这一路能不能走到顶档" |

**四种里没有任何一种做这三件事**：①按费用带成型（高费流）②认准一条羁绊线走到顶 ③故意铺宽拿多个 1 档。
⇒ 用户说的「蠢 AI」有具体所指，不是感觉。

### 羁绊档位的真实数据（决定 S6/S7 可不可行）

`scripts/gamedata/phase2_types.gd` 的 `TYPES` + `data/p2eq-types.json`：

| 类型 | 档位阈值 | 该类型**总件数** |
|---|---|---|
| 剑 / 食物 / 盾 / 药水 / 枪 / 弓箭 | `[3, 6, 9]` | 各 **9 件** |
| 奇械 / 灵物 / 法器 / 遗物 | `[2, 5, 8, 10]` | 各 **10 件** |

这决定了 S6 是一条**极难**的路线，不是随便买买就能到 —— 这一点必须在验收里量，不能假设它做得到。

## 方案

### §1 策略档案（Archetype）—— 六种，覆盖用户点名的三类

每只机器人开局抽一个 archetype，整局**一以贯之**（现有实现是每场重抽顺序偏好，不构成"流派"）。

| # | 名称 | 对应原话 | 核心行为 |
|---|---|---|---|
| A1 | **高费流** | S5「四五费的高费流」 | 优先攒钱、少刷新；货架只在出现 4～5 费时出手；低费件只在"能三合一"时买 |
| A2 | **单线顶档** | S6「羁绊开9档/10档」 | 开局锁定一个类型，**只补该类型缺的 id**；其余只买能三合一的 |
| A3 | **双线中档** | S6/S7 之间 | 锁两个类型各推到中档（6 或 8） |
| A4 | **多羁绊铺开** | S7「很多个羁绊2档1档」 | 每次买**当前离最低档最近**的类型，横向铺满尽量多的 1～2 档 |
| A5 | **三合一优先** | —（保留现有 `merge_first` 当对照组） | 追星级 |
| A6 | **随机** | —（保留现有 `random` 当**下界基准**） | 噪声对照 |

★保留 A5/A6 是**故意的**：没有对照组就说不清"优化后的 AI 到底强了多少"。

### §2 策略要作用在三个决策点（不只是买装顺序）

| 决策点 | 现状 | 改成 |
|---|---|---|
| 货架排序 | 四种策略只改这里 | 按 archetype 的打分函数排序 |
| **买不买 / 攒不攒钱** | 现在是"有钱就买" | A1 高费流要能**跳过一整轮不买**，把钱留到出高费 |
| **刷不刷新** | `MAX_REFRESH = 2` 固定 | A2 单线顶档在"货架没有我要的类型"时才刷；A1 少刷 |

### §4 工时标定（实测，不是估的）

跑法与产物同 §调查。标定条件：`COHORT_BOTS=8 COHORT_MAX_ROUNDS=40 TURTLE_SEED=20260902`，墙钟 600 秒。

| 量 | 实测 |
|---|---|
| 600 秒内跑完 | **4 轮 · 16 场** |
| 单场墙钟 | **≈ 37.5 秒** |
| 空场帧率（对照） | 146 fps；`Engine.max_fps` **本来就是 0**，没有帧率上限可解 |

外推到 800 只（每轮 400 场，单进程）：

| 轮数 | 场次 | 墙钟 |
|---|---|---|
| 20 轮 | 8000 场 | **3.5 天** |
| 40 轮 | 16000 场 | **6.9 天** |
| 60 轮 | 24000 场 | **10.4 天** |

★轮数**不随机器人数变化**（由"输光 8 命出局"决定，不由人数决定）⇒ 总场次 ≈ 人数/2 × 轮数，
  对人数是**线性**的。所以 800 只就是 32 只那次的 25 倍。

**⇒ 当前速度下 800 只不可行。** 三条可能的路（需要你选，见未决点⑧）：

| 路 | 说明 | 代价/风险 |
|---|---|---|
| P1 **实现 FAST_SIM** | `tests/_probe_fastsim.gd` 早就写好了验证（关/开跑同一场，指纹必须逐字相同），但 **`FAST_SIM` 在产品代码里从来没有实现过**（`git log -S` 全历史为空）⇒ 那个探针一直在比较两次**完全相同**的运行，断言恒真 | 提速倍数未知，要先量；确定性由现成探针守 |
| P2 **多进程并行** | 开 N 个 headless 分片跑，事后合并快照 | ★本机 CPU 有**确诊硬件故障**，CLAUDE.md 明写「多进程正是最容易触发的负载」 |
| P3 **降规模** | 比如 200 只 | 与原话 800 不符，要你点头 |

### §5 并行分片（用户 2026-09-02 拍板走 P2）—— 已实现并实测

工具：[tools/cohort_shard.py](../../tools/cohort_shard.py)（起 N 片 → 等 → 合并 → 逐条查 id 唯一）
`tests/_cohort.gd` 侧加了 `COHORT_SHARD`，改动四处，**非分片模式行为逐字不变**（片号 -1 走老分支）：

| 改处 | 为什么非改不可 |
|---|---|
| 每片种子 = `base + shard × 1000003` | 不改的话各片造出**一模一样**的机器人、打一模一样的场 —— 跑 N 片只是把同一份结果复制 N 遍 |
| `ghost_id` 带片号 | 原来是 `coh_<bot>_b<n>`，而 bot 编号**每片都从 0 开始** ⇒ 合并必撞（memory `fb-id-without-owner-dimension`：单机够用的 id 一接共享就塌） |
| `profile.id` 带片号 | 同上，它也是跨片会撞的标识 |
| 产物名带片号 | 否则同一个 `COHORT_OUT` 下各片互相覆盖 |
| 每片独立 `APPDATA` | Godot 在 Windows 从 `%APPDATA%` 解析 `user://`，共用会让 N 个进程抢同一个存档目录（门禁那边踩过） |

★合并这一步**逐条查 id 唯一性并在撞了时报错退出** —— 不是相信上面两条，是**验证**它们。

**实测吞吐**（本机 i9-14900HX：24 核 / 32 线程 / 32 GB）：

| 并行度 | 实测 | 效率 |
|---|---|---|
| 单进程（基线） | 600 秒 16 场 | — |
| 4 片 | 600 秒 48 场 | **3.0×**（75%） |
| 12 片 | 480 秒 114 场 | **8.9×**（74%） |

★效率从 4 片到 12 片**没有塌**（75% → 74%）。按 74% 外推：

| 并行度 | 800 只 × 40 轮 = 16000 场 |
|---|---|
| 12 片 | **18.8 小时** |
| 16 片 | **14.1 小时** |
| 20 片 | **11.3 小时** |

⇒ **一个通宵能跑完**。可续跑：哪片挂了 `--resume` 只补那片。

### §6 策略向量与 14 个流派（用户 2026-09-02:「只有6种流派也少了啊」→「够吧」）

**不做 6 个硬编码流派**，改成【命名锚点 + 随机扰动】：每只机器人抽一个锚点，再对数值项抖 ±35%
⇒ 800 支是 800 个样子，不是 14 个。（开关项如 `minion_first` 不抖 —— 二选一抖了就没意义。）

**★核心张力（这游戏里真实存在的分流，不是我编的）**：羁绊按 **id 去重** ⇒ 买第 2、3 张同 id
对羁绊**零贡献** ⇒ **「追三合一★3」与「追羁绊档位」是直接冲突的两条路**。门禁 ③ 专门焊死这一条。

| 锚点 | 覆盖 | 锚点 | 覆盖 |
|---|---|---|---|
| `hi_cost` 高费流 | 用户点名 | `low_flood` 低费海 | 与高费对立 |
| `line_top` 单线顶档 | 用户点名（高羁绊） | `star_rush` 三星速成 | 冲突轴的另一边 |
| `dual_mid` 双线中档 | 用户点名（高羁绊） | `fast_level` 速升级 | 经济向 |
| `wide_syn` 多羁绊铺开 | 用户点名 | `snowball` 滚雪球 | 与速升级对立 |
| `reroll_mad` 疯狂刷新 | | `no_reroll` 不刷新 | 与之对立 |
| `leader_all` 统领梭哈 | | `minion_up` 小将优先 | 与之对立 |
| `mix` 混合 | 最常见打法 | `random` 随机 | **下界对照组**（所有分布断言的分母） |

**策略作用在五个决策点**（★前四个过去全是写死的 ⇒ 对应流派在旧实现里根本不可能存在）：

| 决策点 | 原来 | 现在 |
|---|---|---|
| 买什么 | 四种策略只改这里 | 统一打分 `CohortSim.buy_score`（**纯函数**，门禁直接调） |
| 留多少币给装备 | 写死 `P2.AI_GEAR_RESERVE = 12` | 向量 `reserve` |
| 每次买几回经验 | 写死 `P2.AI_MAX_XP_BUYS_PER_VISIT = 3` | 向量 `xp` |
| 刷新几次 + 主动刷 | 写死"买不到才刷、最多 2 次" | 向量 `refresh` / `eager` |
| 装备先给统领还是小将 | 写死"先统领" | 向量 `minion_first`（`_equip` 拆成 `_fill_leaders`/`_fill_minions` 按序调） |

★向量里没有某项时**缺省仍是项目原口径**（行为不变）。

**门禁**：[tests/verify_bot_archetypes.gd](../../tests/verify_bot_archetypes.gd) —— 24 条全过。
判据是**排序关系**不是绝对分值（改权重数值不该红，改偏好顺序才该红），并且：

- 每条方向断言都配**反向那一边**（高费流 vs 低费海；锁剑 vs 锁盾）—— 只验一边等于没验
- 随机对照组必须**打分全平**（不平就不是对照组，后面所有分布对比全废）
- **源码守卫**：六个决策点逐个断言"真的在读向量" —— 没有这条的话，上面全是"表里写了不同的数"，
  而消费侧可能照样读写死常量（memory `fb-zero-caller-is-a-whole-class`：今天已经栽过两次）

反向验证：清掉高费流/三合一流/单线顶档/多羁绊 四个流派的偏好，**各自让门禁红**，产品代码逐字节还原。
