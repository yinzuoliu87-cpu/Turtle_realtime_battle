# 摸鱼模式（游戏内竖版小窗口）— 方案书

**日期** 2026-07-29 ｜ **状态** 待用户拍板未决点
**需求来源** 用户 2026-07-28

---

## 1. 需求原文（逐字）

> 针对ios手机出一个摸鱼模式，放置在设置里面一个按钮，点击后整个游戏在手机上以小窗口的形式运行，就像框中框的形式一样，竖着的，可以正常点击交互，再次点可以还原这样子，是否可行

**追问确认**：
- 我问是 (A) 游戏内缩成小窗、周围留黑，还是 (B) 真正浮在微信/文档等其他 App 之上
- 用户答：**「A小窗口也行的」**、**「留黑就好」**

---

## 2. 可行性结论（先说结论）

| 方案 | 可行性 | 说明 |
|---|---|---|
| **(A) 游戏内小窗 + 周围留黑** | ✅ **可行** | 本方案要做的 |
| (B) 悬浮在其他 App 之上 | ❌ **iOS 做不到** | 系统只允许**视频类** PiP（`AVKit`/`AVPictureInPictureController`），不开放任意 App 内容悬浮。这不是 Godot 的限制，是 iOS 的限制 —— 越狱/私有 API 除外，那样上不了 App Store |

**所以本方案只做 (A)：整个游戏画面缩到屏幕中央一块竖版区域，其余留黑，可正常触摸交互，再点还原。**

⚠ 需要说清楚的是：**(A) 并不能让你一边看微信一边玩** —— 它只是把画面变小、不那么显眼。
如果你要的"摸鱼"是前者，那这个需求在 iOS 上无解。

---

## 3. 现状（查实）

`project.godot`：

```
window/size/viewport_width=1280
window/size/viewport_height=720
window/stretch/mode="canvas_items"
window/stretch/aspect="expand"
```

- 基准分辨率 **1280×720 横版**
- `stretch/mode = canvas_items` + `aspect = expand`：**画布按窗口比例拉伸并扩展可视区**
- UI 大量使用 `SafeArea.margins()` 做刘海/手势条避让（`scripts/util/safe_area.gd`）

---

## 4. 三条技术路线（含取舍）

### 路线 1：改 `content_scale_size` / `content_scale_factor` — ❌ 不选

`get_window().content_scale_*` 能整体缩放 UI，但**不会把 3D 视口一起缩进小框**，
而且会打乱 `SafeArea` 的既有计算（它按 viewport 尺寸算边距）。

### 路线 2：整个游戏塞进 `SubViewportContainer` — ⚠ 改动最大

把现有场景树整体挪进一个 `SubViewport`，外面套 `SubViewportContainer` 控制大小与位置。
**优点**：最干净、缩放最真实。
**缺点**：所有场景（主菜单/战斗/图鉴/商店…）的根节点都要改挂载方式；
输入事件坐标要经 `SubViewport` 转换；`_ui_layer`（CanvasLayer）行为要重新验证。
**这是伤筋动骨的改法。**

### 路线 3：★缩小窗口内容区 + 黑边 — ✅ 推荐

不动场景树，改 **`Window` 的 viewport 呈现区域**：

- 用 `get_window().set_content_scale_size()` 配合一个覆盖全屏的**黑色遮罩 CanvasLayer**，
  在遮罩上开一个竖版"窗口洞"；或
- 直接改根 `Viewport` 的 `canvas_transform`（缩放 + 平移），
  再在最外层 CanvasLayer 画黑边遮住溢出部分

**优点**：不动场景树，可全局开关、随时还原。
**缺点**：需要**同步改输入坐标映射**（点击位置要经同一变换），
以及 `SafeArea` 的边距基准。

★ **必须实测哪条真的在 iOS 上成立** —— 见 §6.1，这是本方案最大的未验证点。

## 6. 已知风险与未决点

### 6.1 ★三条路线都没在 iOS 真机上验过 —— **最大风险**

本项目**没有 macOS 环境**，iOS 包只能靠 `.github/workflows/ios-build.yml` 出 unsigned IPA，
再用 Sideloadly 装机（见 CLAUDE.md §6）。也就是说：

- **每验一次都要走一整轮 CI 出包 + 装机**
- Windows 本地**做不出 `.ipa`**（`xcodebuild`/`codesign` 只存在于 macOS，实测过）

→ **建议先在 Windows/编辑器里把路线 3 做出可切换的原型，确认坐标映射正确，再出一次 iOS 包验真机。**
不要一上来就假设某条路线成立。

### 6.2 输入坐标映射是最容易出错的地方 —— **需要专门的测试**

缩放画面后，**触摸点的屏幕坐标 ≠ 游戏内坐标**。项目里有多处直接读屏幕坐标的地方，
例如 `team_select/layout_editor.gd:102` 的 `host.get_viewport().get_mouse_position()`。
这类地方在小窗模式下**全都会偏**。

→ 验收清单第 4 条不能靠目视，**要写成门禁测试**（模拟点击某坐标，断言命中预期控件）。

### 6.3 `SafeArea` 的基准要重新定义 —— **未决**

现有 `SafeArea.margins(vp, ...)` 按**整个视口**算刘海/手势条边距。
小窗模式下，小窗本身可能完全在安全区内 —— 那么：

- **(a)** 小窗内 UI 仍按全屏安全区留白（会显得内边距过大）
- **(b)** 小窗内 UI 按小窗自身尺寸重算（更合理，但要改 `SafeArea` 的调用口径）

**未决**：选哪个。

### 6.4 ✅ 已拍板：**小窗保持横屏比例（16:9），手机竖持、上下留黑**

用户 2026-07-28 两次澄清后的最终形态：

> 「摸鱼模式就跟手机横屏完全一样的比例，只是小屏方便摸鱼，**所以不用去专门适配**」

即：**手机竖着拿 → 屏幕中间一条 16:9 的小横窗 → 上下大片留黑**。
这比"竖版窗口"简单得多，而且**所有界面都不需要重新布局**（比例没变，只是整体缩小）。

★ 这条直接消掉了原先"1280×720 横版内容塞进竖窗必然大量留黑或裁内容"的矛盾 ——
现在是**主动**留黑，且内容完整。

### 6.4-旧 竖版比例未定

需求只说"竖着的"。具体多大？

| 选项 | 效果 |
|---|---|
| 9:16 占屏高 60% | 比较隐蔽，但战斗画面（1280×720 横版内容）会被压得很小 |
| 3:4 占屏高 50% | 更方正，浪费的黑边少 |

⚠ **本质矛盾**：游戏是 **1280×720 横版**设计的，塞进竖版小窗必然
要么**大量留黑**（左右黑边 + 上下黑边），要么**裁掉内容**。
**未决**：接受"横版画面居中放在竖版窗里、四周留黑"，还是要为小窗做专门的竖版布局？
（后者是另一个量级的工作。）

### 6.5 未验证：小窗是否影响性能

理论上渲染分辨率变小应更快，但若走路线 2（SubViewport）会多一次纹理拷贝。**没测过。**
