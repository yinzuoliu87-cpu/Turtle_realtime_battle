# 摸鱼模式（游戏内竖版小窗口）— 方案书

**日期** 2026-07-29 ｜ **状态** ⛔ **两条路线都被引擎约束否掉 —— 待拍板第三条**

> ## ★实施时推翻了 §4 的三条路线
> 三条路线（改 content_scale / 塞进 SubViewport / canvas_transform+黑边遮罩）**一条都没走**。
>
> 因为这个需求其实是 Godot 的**内置能力**：`stretch/aspect = "keep"` 就是标准 letterbox，
> 切竖屏方向后 1280×720 的内容自动变成「中间一条横带、上下留黑」，
> 而且**输入坐标由引擎在 stretch 层统一换算**——
> 也就是说 §6.2 那个「最大风险」（触摸点坐标会偏）**根本不需要我处理**。
>
> 自己写 canvas_transform + 黑边遮罩，反而是把那个风险**亲手引入一遍**，
> 等于重造引擎已经做对的事。实现最后只有两行开关。
>
> 门禁 `verify_idle_mode`(8 条)，含 §6.2 点名要写成门禁的那条：
> 小窗四角/中心精确映射到画布四角/中心、黑边内的点映射到画布外（不会误命中）。
>
> **仍未验**：iOS 真机上运行时切方向（`DisplayServer.screen_set_orientation`）——
> 本项目无 macOS，只能出包装机验。
**需求来源** 用户 2026-07-28

## 1. 需求原文（逐字）

> 针对ios手机出一个摸鱼模式，放置在设置里面一个按钮，点击后整个游戏在手机上以小窗口的形式运行，就像框中框的形式一样，竖着的，可以正常点击交互，再次点可以还原这样子，是否可行

**追问确认**：
- 我问是 (A) 游戏内缩成小窗、周围留黑，还是 (B) 真正浮在微信/文档等其他 App 之上
- 用户答：**「A小窗口也行的」**、**「留黑就好」**

---

## 2. 可行性结论（先说结论）

| 方案 | 可行性 | 说明 |
|---|---|---|
| **(A) 游戏内小窗 + 周围留黑** | ✅ **可行** | 本方案要做的 |
| (B) 悬浮在其他 App 之上 | ❌ **iOS 做不到** | 系统只允许**视频类** PiP（`AVKit`/`AVPictureInPictureController`），不开放任意 App 内容悬浮。这不是 Godot 的限制，是 iOS 的限制 —— 越狱/私有 API 除外，那样上不了 App Store |

**所以本方案只做 (A)：整个游戏画面缩到屏幕中央一块竖版区域，其余留黑，可正常触摸交互，再点还原。**

⚠ 需要说清楚的是：**(A) 并不能让你一边看微信一边玩** —— 它只是把画面变小、不那么显眼。
如果你要的"摸鱼"是前者，那这个需求在 iOS 上无解。

## 3. 现状（查实）

`project.godot`：

```
window/size/viewport_width=1280
window/size/viewport_height=720
window/stretch/mode="canvas_items"
window/stretch/aspect="expand"
```

- 基准分辨率 **1280×720 横版**
- `stretch/mode = canvas_items` + `aspect = expand`：**画布按窗口比例拉伸并扩展可视区**
- UI 大量使用 `SafeArea.margins()` 做刘海/手势条避让（`scripts/util/safe_area.gd`）

## 4. 三条技术路线（含取舍）

### 路线 1：改 `content_scale_size` / `content_scale_factor` — ❌ 不选

`get_window().content_scale_*` 能整体缩放 UI，但**不会把 3D 视口一起缩进小框**，
而且会打乱 `SafeArea` 的既有计算（它按 viewport 尺寸算边距）。

### 路线 2：整个游戏塞进 `SubViewportContainer` — ⚠ 改动最大

把现有场景树整体挪进一个 `SubViewport`，外面套 `SubViewportContainer` 控制大小与位置。
**优点**：最干净、缩放最真实。
**缺点**：所有场景（主菜单/战斗/图鉴/商店…）的根节点都要改挂载方式；
输入事件坐标要经 `SubViewport` 转换；`_ui_layer`（CanvasLayer）行为要重新验证。
**这是伤筋动骨的改法。**

### 路线 3：★缩小窗口内容区 + 黑边 — ✅ 推荐

不动场景树，改 **`Window` 的 viewport 呈现区域**：

- 用 `get_window().set_content_scale_size()` 配合一个覆盖全屏的**黑色遮罩 CanvasLayer**，
  在遮罩上开一个竖版"窗口洞"；或
- 直接改根 `Viewport` 的 `canvas_transform`（缩放 + 平移），
  再在最外层 CanvasLayer 画黑边遮住溢出部分

**优点**：不动场景树，可全局开关、随时还原。
**缺点**：需要**同步改输入坐标映射**（点击位置要经同一变换），
以及 `SafeArea` 的边距基准。

★ **必须实测哪条真的在 iOS 上成立** —— 见 §6.1，这是本方案最大的未验证点。

## 6. 已知风险与未决点

### 6.1 ★三条路线都没在 iOS 真机上验过 —— **最大风险**

本项目**没有 macOS 环境**，iOS 包只能靠 `.github/workflows/ios-build.yml` 出 unsigned IPA，
再用 Sideloadly 装机（见 CLAUDE.md §6）。也就是说：

- **每验一次都要走一整轮 CI 出包 + 装机**
- Windows 本地**做不出 `.ipa`**（`xcodebuild`/`codesign` 只存在于 macOS，实测过）

→ **建议先在 Windows/编辑器里把路线 3 做出可切换的原型，确认坐标映射正确，再出一次 iOS 包验真机。**
不要一上来就假设某条路线成立。

### 6.2 输入坐标映射是最容易出错的地方 —— **需要专门的测试**

缩放画面后，**触摸点的屏幕坐标 ≠ 游戏内坐标**。项目里有多处直接读屏幕坐标的地方，
例如 `team_select/layout_editor.gd:102` 的 `host.get_viewport().get_mouse_position()`。
这类地方在小窗模式下**全都会偏**。

→ 验收清单第 4 条不能靠目视，**要写成门禁测试**（模拟点击某坐标，断言命中预期控件）。

### 6.3 `SafeArea` 的基准要重新定义 —— **未决**

现有 `SafeArea.margins(vp, ...)` 按**整个视口**算刘海/手势条边距。
小窗模式下，小窗本身可能完全在安全区内 —— 那么：

- **(a)** 小窗内 UI 仍按全屏安全区留白（会显得内边距过大）
- **(b)** 小窗内 UI 按小窗自身尺寸重算（更合理，但要改 `SafeArea` 的调用口径）

**未决**：选哪个。

### 6.4 ✅ 已拍板：**小窗保持横屏比例（16:9），手机竖持、上下留黑**

用户 2026-07-28 两次澄清后的最终形态：

> 「摸鱼模式就跟手机横屏完全一样的比例，只是小屏方便摸鱼，**所以不用去专门适配**」

即：**手机竖着拿 → 屏幕中间一条 16:9 的小横窗 → 上下大片留黑**。
这比"竖版窗口"简单得多，而且**所有界面都不需要重新布局**（比例没变，只是整体缩小）。

★ 这条直接消掉了原先"1280×720 横版内容塞进竖窗必然大量留黑或裁内容"的矛盾 ——
现在是**主动**留黑，且内容完整。

（以下为拍板前的原始分析，保留备查）

### 6.4-旧 竖版比例未定

需求只说"竖着的"。具体多大？

| 选项 | 效果 |
|---|---|
| 9:16 占屏高 60% | 比较隐蔽，但战斗画面（1280×720 横版内容）会被压得很小 |
| 3:4 占屏高 50% | 更方正，浪费的黑边少 |

⚠ **本质矛盾**：游戏是 **1280×720 横版**设计的，塞进竖版小窗必然
要么**大量留黑**（左右黑边 + 上下黑边），要么**裁掉内容**。
**未决**：接受"横版画面居中放在竖版窗里、四周留黑"，还是要为小窗做专门的竖版布局？
（后者是另一个量级的工作。）

### 6.5 未验证：小窗是否影响性能

理论上渲染分辨率变小应更快，但若走路线 2（SubViewport）会多一次纹理拷贝。**没测过。**

# 第二版：路线 2（SubViewport 缩放）— 2026-07-29 返工

## R1. 第一版为什么废了

第一版走「切设备方向 + letterbox」。**用户实测：iOS 上摸鱼模式关掉也还是竖屏。**

根因：**iOS 在启动那一刻就按 Info.plist 决定方向。** plist 一旦允许竖屏，
用户竖着拿手机启动，App 就直接以竖屏起来；而代码里「锁回横屏」跑在启动之后，
iOS 16+ 收窄方向掩码**不会自动转回去**（要 `setNeedsUpdateOfSupportedInterfaceOrientations`，
引擎侧的事，GDScript 够不着）。

→ **「允许运行时切竖屏」与「默认必须横屏」在 iOS 上不可兼得。** 这条路作废。

★ 更该记的是**我为什么没查出来**：门禁全绿、还专门拆开 IPA 验过 `Info.plist`，
但我验的是「竖屏写进去了没有」（写进去了），真正该问的是「这么写会不会把默认体验搞坏」。
**验收清单只列了要做到什么，没列不许破坏什么。** 见 R4。

## R2. 新形态（用户 2026-07-29 拍板）

> 「要，可切换的，默认原版，切换摸鱼后则变为小窗口」

- **默认 = 原版全屏横屏**，一点不变
- 切到摸鱼 → 画面缩成**屏幕中间一小块**，四周留黑，**手机仍然横着拿**
- 可以来回切

## R3. 做法

```
root (Window, 始终横屏)
└─ IdleWindow (autoload)          ← 只有开摸鱼模式时才建下面这些
   ├─ ColorRect(全屏纯黑)
   └─ SubViewportContainer        ← 缩到中间一小块
      └─ SubViewport (1280×720)
         └─ 【当前场景】          ← 从 root 挪进来
```

**为什么用 `SubViewportContainer` 而不是 `RenderingServer.viewport_attach_to_screen`：**
后者代码更少，但**输入坐标要自己映射**——而 `SubViewportContainer` 是 Godot
专门为这件事做的控件，**输入变换由它负责**，桌面和 iOS 行为一致。
上一版的教训就是"自己处理平台差异"最后栽在平台上。

**关键难点：场景切换。** `change_scene_to_file()` 永远把新场景挂到 `root` 下。
所以要监听 `get_tree().node_added`，当新场景成为 `current_scene` 时**延迟一帧再挪进 SubViewport**
（在 `node_added` 回调里直接 reparent 不安全）。

## R5. 已知风险与未决点

### R5.1 ★改动面：32 处 `change_scene_to_file` + 30 处视口尺寸读取

不改调用点（靠 `node_added` 统一接管），但**每次场景切换都多一次 reparent**，
时序上容易出问题（`_ready` 已经跑过、`get_viewport()` 在 reparent 前后不是同一个）。
→ 用**延迟一帧**规避；场景自己的 `_ready` 里如果缓存了 `get_viewport()`，reparent 后会失效。
**这是最可能出岔子的地方。**

### R5.2 SafeArea 基准会变

`SafeArea.margins(vp,...)` 按视口尺寸算刘海避让。进 SubViewport 后视口恒为 1280×720，
**刘海边距会失去意义**（小窗四周本来就是黑边，不会被刘海挡）→ 预期表现是"内边距略大"，可接受。

### R5.3 小窗多大 —— **未决**

用户只说"小窗口"。建议默认 **屏幕的 55%**（够小到能摸鱼，又不至于看不清），
将来可加滑条。**先按 55% 做，你看了实机再调。**

### R5.4 3D 性能

SubViewport 会多一次纹理拷贝；但渲染分辨率也变小了。**净影响没测过。**

## R6. ★路线 2 也不成立（2026-07-29 实测）

写完 `IdleWindow` autoload（SubViewportContainer + 把当前场景搬进 SubViewport）后，
门禁的几何与坐标映射都过了，A3/A4（进小窗、换场景被接管）也过了。**但探针查出致命问题：**

```
① 开摸鱼后: current_scene = (null)
```

**场景一旦被挪出 `root`，Godot 就把 `SceneTree.current_scene` 置空。**
（引擎本来就断言 `current_scene->get_parent() == root`。）

后果：

| 受影响 | 后果 |
|---|---|
| `reload_current_scene()` | `ERR_FAIL_COND(!current_scene)` → **直接失效**。战斗调试台/评审台 **6 处**在用 |
| `MainMenuScene.gd:831` `current_scene != self` 守卫 | 走错分支（那行注释自己写着"这时 change_scene 会搅乱人家的场景树，smoke 报 44 条 null"） |

→ **不能靠搬运 `current_scene` 来实现。** 已回滚。

## R7. 剩下的第三条路（未动手，待拍板）

**自己接管全部场景切换**：把 `run/main_scene` 换成一个常驻的宿主场景，
里面固定挂 `SubViewportContainer + SubViewport`，所有页面都作为 SubViewport 的子节点加载/卸载，
**不再使用 `change_scene_to_file`**。

| | |
|---|---|
| 改动面 | **32 处 `change_scene_to_file` 调用点**全部改写；`reload_current_scene` 的 6 处要另找替代 |
| 风险 | 场景生命周期、教学浮层、`current_scene` 语义、冒烟测试全要重验 |
| 好处 | 一次做对之后，小窗只是改一个 rect；将来做"游戏内嵌任意子窗口"也直接可用 |

★ **这是重构量级的改动，不是功能量级的。** 我没有自作主张开工。

## R8. 这个需求给我的教训

两条路线都是**做完、门禁全绿、才发现被引擎约束否掉**：

- 路线 1：门禁绿 + 拆开 IPA 验过 `Info.plist`，但**验的是"想要的写进去了没有"，不是"这么写会不会把默认体验搞坏"**
- 路线 2：门禁绿（几何/映射/搬运都过），但**没先问"引擎允不允许我这么搬"**

→ **动引擎级机制（场景树、屏幕方向、渲染管线）之前，先写探针问引擎答不答应，再写功能。**
  功能门禁验的是"我写的对不对"，验不出"我这么做引擎认不认"。
