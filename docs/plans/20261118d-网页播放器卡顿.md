# 网页录像播放器卡顿：粒子着色器首次编译（浏览器里一次 1~8 秒）

日期：2026-11-18　|　状态：**实施中**

## 1. 需求原文

- 用户 11-17（联调结束后）：「流程就用户用起来是不是很丝滑？主要这个…在这个其他播放器里面看着很卡顿耶，你有没有发现？这个到时候再搞吧。」
- 用户 11-18：「网页播放器卡顿和语音选项可能要搞一下，你自己看来吧。」

## 2. 调查结论

**量法**（工具都在仓库 / 会话里留了）：
- 网址带 `perf=1` ⇒ 左上角性能读数（`scripts/systems/replay/web_perf_overlay.gd`，接线在 `scripts/scenes/WebPlayerScene.gd` 的 `_maybe_perf`）：帧率、真时钟帧时长、绘制调用、**长帧（≥ 50 ms）总数与最慢 10 次**，每次长帧拆成「脚本段」（所有 `_process`）与「其余段」（渲染 + 物理 + 等垂直同步）。
- 本机测量台：同一局（正式服偷袭 `523f78e7…`，0.23.4，112 块）拉到本机，本机静态站点播；另起一个**独立 Chrome**（临时配置目录、静音）用 DevTools 协议抓 GPU 追踪。

**结果**（11-18 上午，本机台式机 Chrome、右屏）：

| 量什么 | 结果 |
|---|---|
| 引擎帧率（本机构建，开打后） | 100~150 帧/秒（不是低帧率） |
| 一局里 ≥ 50 ms 的长帧 | **95~103 次**；最慢：1823 ms（开打 t=0）、1741（t=55.1）、1715（t=32.9）、1448（t=47.2）、869（t=19.4）…… |
| 长帧拆段 | 几乎全在「其余段」（渲染）：1779 ms 里脚本 1 ms、1667 里脚本 22 ms |
| 同一局桌面版原生跑 | 同几个时刻也有长帧，但只有 50~360 ms；第二次跑（显卡驱动缓存热了）局中那几次没了 |
| Chrome GPU 追踪（全新配置 = 第一次来看的人） | 一局 **112 次 D3DCompile、合计 18.4 秒**；渲染线程等「链接好了没」合计 24 秒；**最慢两次 6.2 / 6.0 秒，其次 6 次各 0.8 秒，其余 104 次各约 30 ms** |
| 最慢那 8 个是什么 | **全是 GPU 粒子的「运算」着色器**（ParticleProcessMaterial 生成的顶点着色器，带 `_lifetime` `_emission_*` `_uattractors`…）；6 秒的两个多了 `_noise_` / `_noise_direction_` = **开了湍流（turbulence）** |

⇒ **卡顿 = 浏览器（Windows 上 Chrome 走 ANGLE → D3D）第一次用到某种粒子配置时当场编译着色器，引擎同步等它编完**；开了湍流的一次要 6 秒。原生版有显卡驱动的着色器缓存，所以 App 里不明显。

**代码事实**：
- 建 GPU 粒子的地方全仓只有 12 处：`arcane_eq_vfx.gd:894 / :1181`、`battle_vfx.gd:776`、`battle_world_builder.gd:1383`、`synergy_vfx.gd:209`、`venom_drone_vfx.gd:452`、`RealtimeBattle3DScene.gd:4959 / :5847 / :6051 / :7288`、`ice_system.gd:475`、`lava_system.gd:193`。开湍流的两处：`arcane_eq_vfx.gd:914`、`venom_drone_vfx.gd:471`。
- 网页播放器不跑这些函数：`StreamMirror`（`scripts/systems/stream/stream_mirror.gd:5`）按流里的 NODE_NEW / RES_DEF 按类名现建节点与资源（`:104` `:263`），粒子材质也是这样来的。
- 播放器开播时**整局的块一次拉完**（本机测量台日志：112 块在开播头一秒内全部请求）⇒ 开播前就能知道这一局会用到哪几种粒子配置。

## 3. 需求 ↔ 代码的出入

- 11-18 凌晨我记的「开打后掉到 21~23 帧/秒」**不可信**：同一套录屏方法（gdigrab 60 帧 + 数不重复帧）今天量本机构建与正式站都只录得到约 35 帧/秒 —— 录屏工具自己跟不上。真实问题不是帧率低，是**偶发的长卡顿**（一次 1~8 秒）。memory 里那条已更正。

## 4. 方案

- **P1 开播前预热粒子着色器（不改任何画面）**：播放器拿到全部块后、开播前，扫一遍流里的 RES_DEF，挑出 `ParticleProcessMaterial`（以及粒子的绘制材质），在一个看不见的小 SubViewport 里各放一个 1 颗粒子的 GPUParticles3D 跑两帧 ⇒ 编译发生在「正在载入录像」那一屏。同一种配置只编一次（引擎按功能组合缓存）。
  - 代价：第一次来看的人载入多等 ≈ 这一局粒子配置的编译总和（本机这局约 17 秒；其中湍流两种占 12 秒）。浏览器会把编好的着色器存盘，同一台电脑再看快很多（待量）。
- **P2（要用户点头）网页版关掉粒子湍流**：只在网页播放器里把 `turbulence_enabled` 置否 ⇒ 每种 6 秒降到约 0.8 秒，预热总时间约 17 秒 → 约 7 秒。代价：这两种粒子（奥术装备 / 毒刺无人机一类）在网页上少了湍流抖动。用户 11-06 要求网页播放器「特效完整」，所以不自己定。
- **P3（以后）**：把 12 处粒子的功能组合收拢成少数几种（同样的画面用同一组开关），从根上减少要编的种类；另起。

## 5. 已知风险与未决点

- **U1【已答 11-18】网页版关粒子湍流（P2）**：用户「嗯，可以关吧，应该影响也不大吧」⇒ 关。只关网页播放器进程（`WebPlayerMode.active()`），App 回放照原样。受影响的两种：法器装备翻涌的雾（`arcane_eq_vfx.gd:914`）、092「剧毒飞行物」的毒雾（`venom_drone_vfx.gd:471`），网页上不再打旋。
- 风险（未验）：别的电脑 / 浏览器。Mac 上 Chrome 走 Metal、Safari / Firefox 各自一套，编译耗时不同；Windows 上普遍是 D3D 这条最慢的路。
- 风险（未验）：预热放在看不见的 SubViewport 里，引擎会不会因为「不可见」跳过粒子运算从而没编译 —— P1 实现时用 GPU 追踪量「开播后 D3DCompile 次数」证明。
- 风险（未验）：载入本来就要 27~49 秒（151 MB 首次下载，见 `server/player/README.md`）；再加预热会更久。下载量另有拆包计划，不在本方案书。

## 6. 验收标准

- 同一局、全新 Chrome 配置：开播后（对局时钟 t > 0）GPU 追踪里粒子运算着色器的 D3DCompile = 0；`perf=1` 读数里开播后 ≥ 500 ms 的长帧 = 0。
- 证明会红：把预热关掉（或少预热一种）⇒ 追踪里开播后又出现对应的 D3DCompile、读数里又有秒级长帧。

## 8. 实施回填

- 11-18 上午：测量工具 `perf=1` 读数进仓库（`web_perf_overlay.gd` + `WebPlayerScene._maybe_perf`，平时不挂）；本机测量台与 GPU 追踪分析脚本进 `tools/webperf/`（README 写了用法）。
- 11-18 上午 P1 第一版（按运算材质去重预热）A/B：最长的 15.6 秒挪进了载入（载入一帧卡 22 秒，可能触发「网页无响应」），播放中仍剩 3 次约 1.7 秒 ⇒ **不推**，停在本地分支 `wip-local/webplayer-warmup`；下一版改成照流里 GPUParticles3D 的 NODE_NEW 原样复刻（节点属性 + 运算材质 + 绘制网格 / 材质）+ 分帧预热。
- 11-18 上午 **P2 网页关湍流**：`StreamMirror._apply_props` 在网页播放器进程里把 ParticleProcessMaterial 的 `turbulence_enabled` 置否（定义与后改都管），计数 `turb_off`；`verify_web_player` 加一条（网页进程关、非网页进程照开、别的属性照设；删掉那一行 ⇒ 红，逐字节还原）。同一局、独立 Chrome 关磁盘缓存：播放中最长一次 **15.6 秒 → 1.8 秒**；剩下 5~6 次约 1.7 秒（t=1.4 / 23.8 / 33.0 / 34.7 / 42.3 / 47.2）等 P1 第二版。生效时间：随下一版装到裁判机的网页播放器（播放器按录像版本分目录，0.23.4 的旧录像仍用旧播放器）。
