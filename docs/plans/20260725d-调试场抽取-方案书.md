  (`class_name BattleDebugArena`·RefCounted·`_init(battle)` 注入)、去 `_edit_` 前缀、外部调用加 `battle.`、`--headless --import` 注册、函数总数对账。

## 二、⚠ 待你拍板的两个架构点（这刀不 blind 做的原因）

### 未决点 1：`_unhandled_input` 输入路由怎么切
现在 `_unhandled_input`(L21688, 63 行) 一坨里混了**三层**：`_cam_handle_input`(相机·正式对局) →
`_dl_handle_place_input`(双路摆放·正式对局) → `_edit_handle_mouse_button/motion`(编辑·dev)。抽调试场要先把这三层解开。

| 选项 | 做法 | 权衡 |
|---|---|---|
| **A. 路由层留主场景** | `_unhandled_input` 只保留"相机→双路→(若 edit_mode) `_debug.handle_input(event)`"三行分派；编辑输入实现搬进新类 | 改动最小·正式对局输入路径几乎不动(最安全)。**推荐** |
| B. 抽独立 InputRouter | 再建一个 `BattleInput` 类统一分派相机/双路/编辑 | 最干净, 但把**正式对局输入**也一起动了=风险面扩大, 要 F5 相机/双路全测 |
| C. 暂不抽 edit 输入 | 只搬 51 个非输入 `_edit_` 函数, 输入两个 handler 留主场景 | 最安全, 但收益少(输入 handler 还在主文件) |

### 未决点 2：`_edit_unit_at_screen` 归谁（它被正式对局复用）
它同时被**正式对局**(双路拖拽 L2744 / 双路摆放 L21717)和**编辑**(L21734/21783/21793)调。

| 选项 | 做法 | 权衡 |
|---|---|---|
| **A. 留主场景** | 它是"屏幕坐标→命中单位"的通用几何, 本就该属主场景; 新类要用就 `battle._edit_unit_at_screen(...)` | 语义正确·正式对局零改动。**推荐** |
| B. 搬进新类 | 主场景双路那两处改调 `_debug.unit_at_screen(...)` | 把正式对局依赖 dev 类=方向反了, 不推荐 |

## 三、护栏（同 `_ts_` + 本刀特有）

1. 切块遇任何列首注释就停；每块恰 1 `func`；**函数总数对账**。
2. 新 `class_name` 先 `--headless --import`。
3. 本刀特有：**正式对局输入**(相机 pan/zoom、双路拖拽/摆放)与编辑输入共用 `_unhandled_input`——
   动它就要 **F5 眼验正式对局的相机和双路摆放没坏**(headless 门禁到不了)。

## 四、已知风险与未决点

- **风险**：输入路由是正式对局路径, `verify_debug_arena` 只覆盖调试场那半边; 相机/双路摆放必须 F5。
- **风险**：30 个状态成员里 `_edit_mode` 被 sim 主循环读(L4852 `not _edit_mode` 门 sim)——它要么留主场景镜像、要么 `_debug.is_editing()`, 别漏。
- **未决**：两个架构点(上 §二)先定 A/A(推荐·最小动正式对局) 还是 B/C。定了我按 `_ts_` 那样机械执行 + 你 F5。
