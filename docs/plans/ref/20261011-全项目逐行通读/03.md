# 第 03 块通读笔记 —— data/ghost_seed.json（18001–36000）

### data/ghost_seed.json（已读 18001–36000 行，共 18000 行；全文件 46217 行）
- 作用：内置陪练（队列模拟产出的快照）种子池 v13，顶层 `{_note, by_battles:{"<场次>":[snapshot…]}}`。本段覆盖桶 14（后 6 条）、15–25 全部、26（前 6 条多），共 143 条快照（ghost_id 从 `seed_autoplay_coh_s0_28_b14` 到 `seed_autoplay_coh_s3_26_b26`）。
- 关键内容：每条快照字段固定 17 个：`_strategy / equipped / ghost_id / is_bot / lane_assign / leaders / loadouts / minions / pet_levels / profile{avatar,id,name} / schema_ver / season_eggs_killed / season_level / season_total_battles / trainer_skill / chest_treasures_won / chest_treasure_value`。
  - 读取链：`scripts/net/backend.gd:_load_seed()`(889) → `_ensure_seeded()`(945) → `seed_as_human()`(1017) 转成真人形状后 `pool_add` → `find_opponent()`(1194) → `pool_find_battles()`（按 `season_total_battles` 完全相同选靶）。只有 `MatchmakingScene.gd:134` 这一处调用 `find_opponent`，而且只在非周六时调；周日走 `BracketMapScene.gd:2155`，周六走 `find_gauntlet_opponent`（种子没有 `gl_*` 标签，进不了闯关池，见 backend.gd:59-63）。
  - `seed_as_human` 只把 `leaders / lane_assign / minions / equipped(非空) / loadouts / trainer_skill / chest_* / season_total_battles / profile.avatar` 带进战斗快照。`_strategy / season_level / profile.name / profile.id / pet_levels / season_eggs_killed / is_bot` 在入池时会被丢掉或重新生成。
  - 读文件本身的离线读者：`tests/verify_seed_battles_gear.gd`（桶键=场次、0~RANKED_QUOTA 每格非空、装备容量、bot 曲线拟合）、`tests/verify_ghost_seed.gd`、`tests/verify_bot_snapshot_shape.gd`、`tools/cohort_strategy_report.py`。
- 交叉核对结果（脚本对本段 143 条逐条核，读的是 `data/pets.json`、`scripts/gamedata/equip_stats.gd` STATS、`data/phase2-equipment.json`、`SkillChoice.playable_indices`、`RealtimeBattle3DScene.TRAINER_SKILLS`）：
  - 龟 id：全部在 pets.json（28 只）里。`two_head` 这个 id 还在（变脸龟只是改了名字，id 没改）。
  - 装备 id：本段用到 72 种，全部在 STATS（96 个键）和 phase2-equipment.json 里，没有 `shopAvailable=false` 的；star 只出现 1 和 2；每件装备只有 `{id,star}` 两个键。
  - loadouts：键集合 == leaders；每个位次都在 `playable_indices`（impl=true）里，**0 条不合法**。
  - trainer_skill：只出现 hook / glacier / fury_potion / magic_stone / whistle，都合法（magic_stone 是被动，battle_spawn.gd:586 专门处理了）。
  - 结构：字段集合 143/143 完全一致；桶键 == `season_total_battles` == ghost_id 的 `_b<N>` 后缀；`lane_assign` 上下两路合起来 == leaders；每路「统领+小将」= 3；精英规则符合 backend.gd:1840（只有「该路 0 统领且是第一只小将」才是 elite，elite=0 的 41 条都是 2/1 分路）；单只单位最多 3 件；全队件数都不超过 `team_equip_cap(season_level)`；没有同一场次的三件同款同星没合成的情况（同一单位上两件同款同星合法，MERGE_COUNT=3）。
  - 全文件 ghost_id 396 条互不重复。按人看，season_level 不下降；按 cost×3^(star-1) 算装备价值，没有一次跌超过 25%（本来怀疑 s1_27 在 b21→b22 掉档，实际是拿 2★ 低费换了 1★ 5 费，价值没掉）。

- 问题：
  - [死代码或无人读写] data/ghost_seed.json:19871–36000（桶 16–26，本段约 132/143 条；全文件桶 16–35 共 192 条）—— **积分赛选靶永远够不到这些场次**。依据：`find_opponent` 只在 `MatchmakingScene.gd:134`（非周六）调用，入参是开局前的 `season_total_battles`。积分赛配额 `RANKED_QUOTA=16`（phase2_config.gd:77），`GameState.ranked_quota_full`(923-937) 拦第 17 场，`start_new_season`(GameState.gd:2638) 每周清零，所以入参只可能是 0–15。周六走闯关池（种子进不去），周日走对阵图。周一休赛不开战（phase2_config.gd:363），周日积分赛也被拦了（phase2_config.gd:391-399）。影响：全池 396 条里将近一半永远不会被匹配到。剩下唯一的用途是 `verify_seed_battles_gear` 拿它拟合 bot 曲线（门禁要求「≥25 个场次」，phase2_config.gd:855-858 写的是「0~35 场次」）。这批数据是 v12（2026-09-25）按旧的无上限/24 场配额跑出来的，而 16 场配额是 2026-09-30 才定的。
  - [疑点] 同上的连带后果：`BOT_LV_MIN_BATTLES=[0,1,1,3,5,9,13,18,22,28]`（phase2_config.gd:868）的 Lv8–10 档（18/22/28 场）是用桶 16–35 的数据量出来的，积分赛里根本到不了，bot 最高只到 Lv7。这算不上 bug，但曲线约 1/3 的拟合依据落在不可达区间。等配额定了，「拟合要求 ≥25 个场次」这条判据是否还合理，需要重新定（没跑探针，记为疑点）。
  - [注释或文档与代码不符] scripts/gamedata/phase2_config.gd:859、scripts/net/backend.gd:1011、tools/cohort_to_seed.py:82 都说曲线由 `tools/bot_level_fit_audit.py` 每次门禁复量。这个文件**全仓不存在**（全仓 Grep 只搜到这 3 处引用）。真正做拟合判据的是 `tests/verify_seed_battles_gear.gd:188-229`。`tools/nine_bracket_audit.py:172-180` 只对比 gd 与 py 两份镜像是否逐格相同，不和数据比。
