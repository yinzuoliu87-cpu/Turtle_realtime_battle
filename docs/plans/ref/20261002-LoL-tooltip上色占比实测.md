## 1. 样本怎么来的

### 1.1 走通的三路

| 来源 | 张数 | 格式/分辨率 | 版式 | 形态 |
|---|---|---|---|---|
| **Surrender@20**（surrenderat20.net，36 篇英雄/PBE 文章，共下 3,430 张图自动筛） | 49 | PNG，580×157 ~ 1133×527，**原生 1:1 裁切** | 当前版式 | 展开版(Shift) |
| 同上（迪安娜 5 技能一组） | 5 | PNG，813×175 ~ 949×239 | 旧版式 | 默认版 |
| reddit 整屏截图（经 Bing 图搜拿到 `preview.redd.it` 带签名直链） | 2 | PNG **2560×1080** | 旧版式 | 默认版 |
| interfaceingame.com | 1 | JPEG **1920×1080** | 旧版式 | 默认版 |
| Riot 设计师推文（`api.fxtwitter.com` 取 media） | 1 | PNG 605×247 | 版式交接期 | 展开版 |

**⚠ 任务要求「短边 ≥ 540」，只有 3 张整屏截图满足。** 其余 54 张是**客户端原生像素的 tooltip 裁切**
（S@20 的做法就是截屏后把 tooltip 抠出来，没有放大也没有二次压缩），短边 157–527。
对**量颜色**来说它们比整屏 JPEG 更可信：整屏 JPEG 走 4:2:0 色度二次采样，彩色小字的边缘会被糊掉；
原生 PNG 裁切没有这个问题。所以我没有因为「短边不够 540」丢掉它们，**但这条要求确实没满足，记在这里**。

### 1.2 没走通的（省得下次重走）

| 路 | 结果 |
|---|---|
| `reddit.com/r/*/search.json` | **403**（无 OAuth 一律拒） |
| `reddit.com/r/*/search.rss` + `curl -L` | **200 能用**，但只回标题+少量缩略图；连抓两轮后被限流到 7 条 |
| redlib / libreddit 公共镜像 | catsarch 429；privacyredirect 返回反爬挑战页 |
| `i.imgur.com` 直链 | **区域封锁**：返回一张紫底「Content not viewable in your region」的 336×478 图（PIL 能解码，**不报错**，差点当成真图量了） |
| DuckDuckGo `i.js` 图搜 API | 拿到 vqd 之后仍回错误串 |
| Qwant images API | 403 + DataDome 验证码 |
| Google `udm=2` / Yandex images | 返回 200 但是纯 JS 壳，HTML 里没有图片 URL |
| gameuidatabase.com `series=118` | **「League of Legends」那个条目是《破败之王》单机衍生作**，不是 MOBA 本体 |
| Bing 图搜 | **query 依赖极强**：`league of legends ability tooltip in game` 一直好用；稍微改写就返回完全无关的结果（霍莉·瓦伦斯、阿拉米图库、瓷砖产品图）。不是被封，是它自己跑题 |
| Brave 图搜 | 头两轮好用（`properties:{url:"…"}` 里有带签名的 `preview.redd.it` 直链），第三轮起返回 0 条 |

**真正解决问题的是换思路，不是换搜索引擎**：Surrender@20 每次新英雄上 PBE 都会把
**客户端里每个技能的 tooltip 单独截一张**传到 blogspot，文件名就是 `belq.png` / `samiraq.png` / `udyrw.png`。
抓 36 篇文章 → 3,430 张图 → 用「深色面板 + 暖灰正文色 + 金棕分隔线」的像素签名自动筛，一次就出 60+ 条可用 tooltip。

### 1.3 ★ 量之前先发现：LoL 的 tooltip 有**两代配色**，混着量会得到假数

| | 旧版式（≈2018–2020） | 当前版式（2020-08 改版之后） |
|---|---|---|
| 正文色（实测众数） | `#c8c8c8` 中性灰白，V=200 | `#a09888` 暖灰，V=160 |
| 技能名 | 金黄 | 米白 |
| 伤害数值 | 只有系数括号上色：`100 (+0)`，绿/粉/橙 | **整个伤害短语上色**：`54 = (30 +40%⚔) physical damage` |
| 控制词 | 不上色 | 紫 |
| 属性词 | 不上色 | 上色（护甲橙 / 魔抗蓝 / 攻速黄 / 移速白高亮） |
| 斜体细则行 / 分档表 | 无 | 有 |

实测的正文色众数 `#a09888`（V=160, S=0.150）**和 §6 记的 `#a09b8c` 基本对上**，这条旧结论站得住。
`#0acbe6` 也对上了：实测魔法伤害众数 `#08c8e0`。

所以本文把两代**分开报**。原 §6 的 4 张图是当前版式。

## 2. 口径与标定表（必须先放，否则下面的数没法比）

### 2.1 定义（与任务给的口径逐字一致）

- 明度 **V = max(R,G,B)**；饱和度 **S = (max−min)/max**（即 HSV）
- `V < 90` → 算背景，跳过
- 其余 → **文字像素**（分母）
- 其中 `S ≥ 0.18` → **上色文字**（分子）

### 2.2 正文区怎么框出来的

1. **面板矩形**：找「金棕描边」色（r>80,r<240,g>60,g<215,b<175,r−b>30,g−b>8）占比 > 40% 的行/列
2. **分隔线**：面板内，比上下各 3 行都亮 ≥14 的像素占该行宽度 > 70% 的行
3. **正文区** = 第一条分隔线下方 → 面板下边框（于是**自动去掉了技能名标题行、冷却/耗蓝行、技能图标**，正是任务要求的裁法）
4. 有 ≥2 条分隔线时，再拆成**段落区**（首条→末条）与**分档表**（末条→底）

框得对不对**不是推理出来的，是画框出来看的**：`C:/tmp/loltip/vb.png` 把红框(正文区)/绿框(段落区)
画在原图上逐张核过（韦鲁斯…不，是 Vex Q / 妮菈被动 / 维克托被动 / 卑尔维斯被动四张，覆盖
「有分档表 / 无分档表 / 全白字 / 满篇黄字」四种形态）。
文字像素占正文区面积 **5%~10%**（旧版式白字 14.5%），数量级合理，没有把背景当文字。

**6 张面板边框没检到的样本单独标出来**（`剔` 列），正文区可能多吃了面板外的一行游戏提示文字；
下面每个数都给了「剔掉它们」的复算值。

### 2.3 标定表 ★（拿已知答案的合成图先量一遍，证明尺子本身不骗人）

同一句话（LoL 风格的一行伤害描述）渲染在 `#080c10` 近黑底上，17px Arial：

| 合成用例 | 预期 | 文字像素 | 上色像素 | **实测占比** |
|---|---|---|---|---|
| 纯白 `#ffffff` | 0% | 2274 | 0 | **0.0%** ✔ |
| 纯红 `#ff0000` | 100% | 2198 | 2198 | **100.0%** ✔ |
| LoL 正文 `#a09b8c`（S=0.125） | 0% | 1820 | 0 | **0.0%** ✔ |
| LoL 技能名 `#e6ddc9`（S=0.126） | 0% | 2128 | 0 | **0.0%** ✔ |
| LoL 魔法伤害 `#0acbe6`（S=0.957） | 100% | 2180 | 2180 | **100.0%** ✔ |
| LoL 控制紫 `#ad76c4`（S=0.398） | 100% | 2064 | 2064 | **100.0%** ✔ |
| LoL 物理伤害橙 `#ff8c42` | 100% | 2198 | 2198 | **100.0%** ✔ |
| 中性灰 `#808080`（S=0） | 0% | 1424 | 0 | **0.0%** ✔ |
| 一半白一半红 | ~50% | 2140 | 1045 | **48.8%** ✔ |

**噪声底**：同一句白字叠在**有颜色的背景**上（模拟半透明 tooltip 透出草地） → **9.7%** 假阳性。
这是抗锯齿边缘像素与彩色背景混色造成的，不可能清零。
⇒ **本文所有占比带着约 ±10 个百分点以内的、方向只向上的系统性噪声**，低值（<10%）尤其要当上界看。

### 2.4 灵敏度（换阈值，结论会不会翻）

| 变体 | 新版式展开版合并占比 |
|---|---|

## 4. ★ 没量到的：**当前版式的默认版（不按 Shift）**

**一张都没拿到，N=0。** 不估、不推、不拿展开版的段落区冒充。

为什么拿不到：

## 5. 属性词在 LoL 里是图标还是文字（Q2）

### 5.1 口径

- **属性词** = 攻击力 / 法术强度 / 攻击速度 / 移动速度 / 护甲 / 魔法抗性 / 生命 / 法力 / 技能急速 / 暴击 这一族
- 三类计法：**图标**（行内小图替掉这个词）/ **彩色文字**（写出来、非正文色）/ **正文色文字**（写出来、和正文一个颜色）
- **「每级成长 ⬆」单列**，它标的是「随等级」不是某个属性
- `max Health magic damage` 里的 `Health` **不计**（它是伤害短语的一部分，不是在引用属性）
- 分母 = **14 条我逐张按原分辨率读过的 tooltip**（不是 49 条全部 —— 这一问靠肉眼读字，没有 OCR，读不准的不编）

### 5.3 结论（**分母 54 次属性提及，N≠0**）

| | 次数 | 占比 |
|---|---|---|
| **图标** | 26 | **48.1%** |
| **彩色文字** | 21 | **38.9%** |
| **正文色文字** | 7 | **13.0%** |

两条更硬的子结论：

1. **26 枚属性图标，26 枚都在「数值推导式的括号里」**：`(30 +40%⚔)`、`(10%🛡) 护甲`、`(+116 💚) 护盾`。
   **行首当装饰用的 0 枚。** §6 那句「嵌在算式里替掉文字，不是放在行首当装饰」 —— **26/26 成立**。
2. **图标与文字不是二选一，是分工**：
   - 括号里（算式）→ **图标**
   - 正文叙述里 → **写出来的词，而且基本上色**（21 彩色 : 2 正文色 = 91% 上色）
   - 底部分档表的行标签 → **写出来的词，正文色**（7 个正文色里 5 个在这）

   同一条 tooltip 里「护甲」会同时以**图标**（`5 = (10%🛡) 护甲`）和**橙色文字**（「护甲」）
   和**正文色文字**（分档表行「护甲与魔抗」）三种形态出现 —— 芮尔 W 一条就占齐了。

## 6. 正文色与上色文字的明度差（Q3）

### 6.1 按 V = max(R,G,B)（本文口径）

| | 正文色文字 V 中位 | 上色文字 V 中位 | 差 |
|---|---|---|---|
| 新版式·展开版 | **141** | **195** | **+54** |

### 6.2 按纯色众数 + 感知亮度 Y（0.2126R+0.7152G+0.0722B）★ 这才是关键

| 颜色 | V | S | Y | **Y − 正文** |
|---|---|---|---|---|

| **魔法伤害 `#08c8e0`**（实测众数） | 224 | 0.964 | 160.9 | **+8.4** |
| 物理伤害 `#f06020`（实测众数） | 240 | 0.867 | 122.0 | **−30.6** |
| 物理伤害 `#e88830`（另一峰） | 232 | 0.793 | 150.1 | −2.5 |
| 关键词黄 `#d8d870` | 216 | 0.481 | 208.5 | +55.9 |

| 控制紫 `#ad76c4` | 196 | 0.398 | 135.3 | **−17.2** |
| 法强图标蓝紫 `#7868f8` | 248 | 0.581 | 117.8 | **−34.7** |
| 技能名 `#e6ddc9` | 230 | 0.126 | 221.5 | +68.9 |
| 旧版式正文 `#c8c8c8` | 200 | 0 | 200.0 | +47.5 |

**⇒ LoL 的上色文字并不是「更亮」，是「更有色」。**
按 V 看是 +54，按人眼亮度 Y 看：青色只高 8，橙色**比正文还暗 31**，控制紫**比正文还暗 17**。
它靠**色相 + 饱和度**把语义分出来，**明暗几乎不动**。
唯一真的靠明暗分的是**黄色关键词**（+56~+92）和**技能名**（+69）—— 这两类不是"类型标注"，是"这里有个专有名词"。

对比我们这边：我们正文接近纯白（Y≈240+），**上色文字只可能比正文更暗**，
所以同样的上色占比，在我们这儿是「一堆暗色块砸在白字里」，在 LoL 那儿是「同亮度的换色」。
**这不是占比的问题，是底色的问题** —— 这条本文只给数，不给建议。

## 7. 顺带量到的、和旧记录对不上的

### 7.1 「只有伤害数值上色，别的不上」—— 在当前版式的**展开版**里不成立

实测上色像素里 **19.0% 是黄色**，它标的不是伤害：
- 专有名词：`Gloom`（Vex）、`Lavender`（卑尔维斯）、`Possessing`（佛耶戈）、`Grit`（瑟提）
- 段落标签：`Awaken:`（乌迪尔）、`Claw Stance:`、`Storm Stance:`
- 属性词：`Attack Speed`（黄）、`Armor`（橙）、`Magic Resist`（蓝）、`Move Speed`（白高亮）

⚠ **但不能直接判 §6 写错了**：§6 那句话是看**默认版**（阿利斯塔）得出的，而默认版我**没量到**（§4）。
两者可能都对 —— 展开版多出来的斜体细则行与属性推导本来就带更多关键词。
**这条只能记成「展开版里确实不止伤害上色」，默认版待验。**

### 7.2 分档表靠明暗、不靠颜色

39 张带分档表的里，**中位数 0.0% 上色**。它的层次完全由
「当前档 **白** / 其余档 **灰** / 行标签 **正文色**」三级明度做出来。
这是 LoL 在同一个框里**同时**用两套手段：**上半段用色相分语义，下半段用明度分主次**。

### 7.3 LoL 一条 tooltip 的上色占比方差极大，不是一个固定配额

0.0%（维克托被动：一整段纯叙述，没有任何伤害/控制/属性）到 56.5%（卑尔维斯被动：每句都在说攻速）。
**它是「该标的标、不该标的一个不标」的结果，不是「控制在 25% 左右」的设计目标。**
我们那三个数（74.8 / 38.8 / 25.7）的离散度本身并不异常，异常的只有线条龟那个 74.8%
—— 它比 LoL 49 条里最高的那条（56.5%）还高 18 个点。
