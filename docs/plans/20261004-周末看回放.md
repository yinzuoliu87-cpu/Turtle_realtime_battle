# 周末看回放（周六赛况板 + 周日对阵图点格看回放）

日期：2026-10-04　|　状态：**实施中**

## 1. 需求原文

用户 2026-10-04，按时间逐字：

> 「回放在哪里」
> 「没有，回放不是让你做周六周日的吗」
> 「那就是还没规划好呗」
> 「这样不行，周六连对阵图都没有吗，我觉得周六的规则有点问题吧，周六是怎么样的比如100位玩家开打」

主会话解释了周六闯关（异步打同战绩快照，4 胜晋级 / 3 负出局 / 最多 6 场），给了两个选项：
A = 保留异步闯关 + 加「周六赛况板」；B = 改定时瑞士轮。**用户选「A」**。

主会话定下的范围（派活原文要点，逐条钉住）：

- 周六「赛况板」：入口在周六主菜单/闯关页一个明显位置，用现有像素皮肤、不新加素材（别搞出 ai 味）。
  内容 = 本周所有闯关参赛者的**实时战绩**（名字 + #ID + 几胜几负 + 状态：在打/已晋级/已出局，按战绩排序）；
  **最近打完的对局**流水（谁 vs 谁·谁赢）；**点任一场 → 看回放**；点某个玩家 → 看他今天打过的几场及回放；自己也在里面。
- 机器人对手要和真人看不出区别（memory project-bot-opponent-must-look-human）：赛况板里机器人也要有像人的名字和 #ID，**不许出现「机器人」字样**。
- 录像只装战斗需要的数据（S2 瘦身规则不变）。
- 周日对阵图：已揭晓的场次（`winner_side` 已在 done 里）点那一格 → 看这场回放；当前轮/未揭晓的格子点不开（不剧透）。观众也能点。
- 周日录像用**裁判采纳的那一份** = `finals_results` 里先报上去的那方。
- `BracketMapScene.REPLAY_LIVE` 按「只开已揭晓场次」的规则打开。
- 播放复用 S3（`replay_fetcher.gd` / `ReplayRecorder.play`），看完回到原页面。
- 服务端 SQL 只写进 `schema.sql`，**绝不对生产执行**；SQL 未上线时客户端优雅（不报错），上线后自动生效。

## 3. 需求 ↔ 代码的出入

1. **「周日录像有两份」—— 现状一份都没有**：`should_record` 只录周六，周日的对局从没录过、也没上传过。⇒ 先得让周日也录、也传。
2. **「周日用先报上去那一份」—— 服务端没记是谁报的**：`finals_results` 没有报告人列。但它存了 `seed_used`，而那正是报告方那一局录像的种子（两边各自 `randomize()`，撞同一个 int53 的概率可忽略）⇒ **不加列**，按 `(周, 组, 轮, 场) + seed = seed_used` 认出采纳那一份。
3. **周日录像一传上去就剧透**：`matches_read_all` 让任何登录用户直连 `/rest/v1/matches` 读到 `result.won`。⇒ ① 客户端：周日录像**等那一场揭晓后才传**（不依赖 SQL 上线）；② 服务端：读策略把 `phase='finals'` 的行收成「只有上传者自己读得到」，决赛录像只经 `finals_replay()` 给出、且只给已揭晓的场次。
4. **周六赛况板不需要新 SQL**：`matches` 现有读策略已允许读 `phase='gauntlet'` 的行，PostgREST 直接按 JSON 路径只取 `profile` 与战绩标签，不碰阵容。缺的只有「这一局打完后的战绩」⇒ 客户端上传时把 `gw/gl` 写进 `result`（jsonb，零迁移）。

## 4. 方案

### 4.1 周六赛况板

- **数据**：`GET /rest/v1/matches?phase=eq.gauntlet&season_week=eq.<周>&select=match_id,created_at,result,lp:left_snapshot->profile,rp:right_snapshot->profile,rw:right_snapshot->gl_w,rl:right_snapshot->gl_l&order=created_at.desc&limit=1000`
  （`SupabaseNet.gauntlet_board_query` / `fetch_gauntlet_board_async` / `parse_gauntlet_board`）。
- **聚合**（纯函数 `scripts/systems/replay/gauntlet_board.gd`）：
  - 人按 `profile.tag` 认（两侧一视同仁，不看是不是机器人 —— 也根本看不出来）。
  - 战绩证据取「场次最多」那一条：自己上传的行用 `result.gw/gl`（这局打完后的战绩），只以对手身份出现的用快照标签 `gl_w/gl_l`（那一刻的战绩）。真人没传上来录像时与机器人走**同一条**规则。
  - 状态 = `Phase2Config.gauntlet_state(w, l)`；周六收盘后仍「在打」的显示「已出局」（没打满 = 没晋级，与 `gauntlet_backfill_owed` 同一口径）。
  - 排序：胜多在前 → 负少在前 → 名字。
  - 流水：按 `created_at` 倒序；每条 = 左（上传者）vs 右（对手快照方）· 谁赢。
- **页面** `scenes/GauntletBoard.tscn` / `scripts/scenes/GauntletBoardScene.gd`：TopBar「周六赛况」；左栏战绩榜、右栏对局流水；点人 ⇒ 右栏换成「他今天的几场」；点对局 ⇒ `ReplayFetcher.open(..., back = 本页)`。皮全用现有 `slot-frame.png` / `chip-frame.png` / `panel-frame.png`。
- **入口**：主菜单赛程条右端那一块在周六（闯关赛上线时）变成一扇门（与周日「决赛日 看对阵图」同一张 `ui/panel-wide.png`），第一行仍是收盘倒计时，第二行「全场赛况」。

### 4.2 周日录与传

- `should_record()`：周日决赛场（`SETTLE_FINALS` 且 `finals_match` 非空）也录。
- `ReplayUploader.enqueue`：单子多带 `ph`（gauntlet/finals）、周六的赛前战绩 `gw0/gl0`、周日的 `fk = {b, r, m, s}`。
- `build_row`：`phase` 按单子；周六 `result.gw/gl` = 赛后战绩；周日 `result.fb/fr/fm`。
- `retry()`：周日单子**揭晓前不发**（`finals_upload_ready`：本机缓存的对阵数据里那一场已在 `done` 里，或那一周已过完）；对阵图每次拿到新数据都 `retry()` 一次。

### 4.3 周日点格看回放

- `REPLAY_LIVE = true`；`can_open` = 已翻面（`ST_DONE`）或「我上场打」；点下去分两支：上场 / 看回放。
- 取录像：`POST /rest/v1/rpc/finals_replay {p_week, p_bucket, p_round, p_match}` → `{ok, match_id, replay}`（`SupabaseNet.fetch_finals_replay_async`，进 `READ_RPCS`）→ `ReplayFetcher.open_finals` 解码/认场/缓存/播放（与 S3 同一条）。
- 函数没上线（404）⇒ 那一格点了说「这场的回放还没开放」，不报错。

### 4.4 播放回原页面

`ReplayRecorder.play(tree, r, back)` 记下回哪一页；`battle_hud._replay_exit` 读 `ReplayRecorder.exit_scene()`（没给就回战绩页，与原来一致）。回放结束那句话：给了双方名字就说「X 赢了」，没给照旧「胜利/失败」。

### 4.5 服务端 SQL（只写进 schema.sql，待用户审后上线）

`schema.sql` §3c：① `matches_read_all` 改成决赛行只有上传者读得到；② `finals_replay()`（security definer，只给已揭晓、只给 `seed = seed_used` 那一份）；③ 一条决赛查询的部分索引。

## 5. 已知风险与未决点

| # | 内容 | 状态 |
|---|---|---|
| R1 | 机器人从不「自己打」，只以对手身份出现 ⇒ 点开一个机器人只看得到 1 场、战绩停在快照标签。没传上录像的真人（旧版本 / 一直离线）长得一模一样，所以单看一个人分不出；但统计上「只出现一次、永远在打」的人偏多。 | **未决**（要不要再藏，例如只列「自己打过 ≥1 场」的人 —— 那样机器人就不进榜，只在流水里出现名字；请用户拍板） |
| R2 | 战绩来自录像上传：没传上来的场次不计入（补传后自动补上）。周六 `gauntlet_ghosts` 有更准的战绩但机器人不在里面，混用会让真人与机器人走两条规则 ⇒ 故意不用。 | 已知·有意接受 |
| R3 | PostgREST 的 `别名:列->键` 选择语法未在生产上实测（不许碰生产）。语法按 PostgREST 文档写，回包形状门禁用假服务器量。 | **未验**（上线后看一眼赛况板即知） |
| R4 | 周日采纳认领靠 `seed = seed_used`。超时补判（`finals_advance`）的场次 `seed_used` 可能是 0 ⇒ 没有录像，点了说「这一场没有留下回放」。 | 已堵（RPC 回 `no_replay`） |
| R5 | SQL 上线前，周日录像揭晓后才传，`matches_read_all` 仍对它开放 —— 但那时结果已经公开，不算剧透。 | 已堵（客户端闸） |
| R6 | 回放只能在**同版本**客户端播（`ReplayRecorder.play` 版本闸）。周六换版本后旧录像播不了，说清原因。 | 已知·沿用 S3 |
| R7 | `matches` 查询上限 1000 行（≈166 人×6 场）。人数再多要分页。 | 已知 |
| R8 | 主菜单周六那一块从两行字变成门：原来的「本地 周六 23:00 收盘」第二行让位给「全场赛况」。 | 已知·倒计时仍在 |

**与方案的偏差**

- 主菜单那扇门第一版把第二行（收盘时刻 / 「明天决赛日 · 几点开打」）让给了「全场赛况」，`verify_week_strip` ⑥ 当场红 —— 改成「贴内容的牌子 + 透明按钮」，原两行一字不动、加第三行。

**新发现的坑**

- 主菜单在测试里设成当前场景时，开场可能自己换场景把自己释放掉 ⇒ 门禁里一条 SCRIPT ERROR 打断协程，**前面的 PASS 照样打出、照样 ALL PASS**（memory fb-null-readback-makes-test-silently-abort 同族）。已加末尾分母断言「六段都走到了最后一条」。
