### 2.2 「小」的根因：五条，各有出处

**根因 A：设计框的高度永远是 720，而字号是在电脑窗口上挑的。**
`project.godot:41-44`：基准 1280×720，`stretch/aspect="expand"`。
手机横屏不管物理像素多少，**逻辑高永远是 720**（屏幕更宽只会多出宽度，见 2.1 的 1560×720）。
所以每一个写死的字号，到手机上都是固定的点数：13 px × 0.542 = **7.0 pt**。
iOS HIG 正文默认 17pt、**最小 11pt**。这一屏的表格字只有最低线的 64%。
在 1280×720 的电脑窗口上，13px 看着是正常的（1:1 像素，人离屏幕 60cm）。
**这些数字从来没有拿手机的点数核对过**，而本仓库其实早就有这把尺子
（info_panel.gd:1370 / BracketMapScene.gd:139 都按 44pt = 81px 算触控），只是没用到字号上。

| 写死的字号 | 位置 | 手机上 |
|---|---|---:|
| 名字 13 | battle_hud.gd:1783 | 7.0 pt |
| 数值格 13 | battle_hud.gd:1799 | 7.0 pt |
| 表头 / 页签 `UIPalette.F_BODY`=14 | battle_hud.gd:1739 / 1917，ui_palette.gd:95 | 7.6 pt |
| 「还有 N 只」13 | battle_hud.gd:1928 | 7.0 pt |
| 奖励标签 13 / 数值 24 | battle_hud.gd:1609 / 1615 | 7.0 / 13.0 pt |
| 后果一句 17 | battle_hud.gd:1425 | 9.2 pt |

**根因 B：表格只分到屏高的 23%，因为它和其他所有东西叠在同一列里。**
720 的高度实测是这样分的（见图 01；y 区间来自探针量到的控件高度）：

```
卡外屏幕边距 32+32 = 64     九宫格框内边距 30+32 = 62      间距 12×6 = 72
「失败」大字 79             后果一句 25        各路战果 33        奖励 5 块 56
战报标题+页签+面板边 88     「还有N只」+面板边 42           按钮 46
──────────────────────────────────────────────────────────────
表格以外合计 555            ★表格本体 165（23%）
```

外层预算 `settle_outer_budget()`（battle_hud.gd:1233）＝ 720 − 62 − 70 − 安全区 − 40 ＝ 536；
内层表格 ＝ 536 − 卡内其他所有东西（`settle_inner_avail`，battle_hud.gd:1241）＝ **165**。
表格是**最后一个分高度的**，前面每多一行字它就少一截。2026-09-29 那次修预算修的是「两处算账差了 56px」，
修得对，但它只保证「不溢出」，**没有人问过这一列该不该把六样东西都装下**。

**根因 C：屏幕更宽，卡片却不变宽。**
卡片由 `CenterContainer`（battle_hud.gd:1328）按**内容最小宽度**居中，没有任何东西让它跟着视口变宽。
内容宽是写死的列宽撑出来的：名字列 126（:1742/:1775）＋ 4 列 × 72（:1805）＋ 列距 ＝ 每队约 454，两队并排约 908，
加上面板边距和卡边距 ⇒ **1077**。手机上逻辑宽 1560，**左右 483 逻辑 px（31%）是空的**，
透出底下的战斗血条和头像框（实拍图 02 左右两侧）。
横屏最富余的是宽度，而这一屏把宽度扔掉了，再去挤高度。

**根因 D：两队并排，所以每一列都只能窄。**
`cols.add_child(_stats_column("我方"…))` ＋ `cols.add_child(_stats_column("敌方"…))`（battle_hud.gd:1891 / 1902）。
一行要放 2 × (名字 + 4 个数) ＝ 10 格。要把字放大到 22px，一队就要约 900 宽，两队 1800，
1280 和 1560 都放不下。**只要两队还并排，字号就放不大**，这是几何上的硬约束，不是手感问题。

**根因 E：结算卡是叠在战斗场景上的一层浮层，不是一个独立的屏。**
回合制时代结算是独立场景 `BattleEndScene`（2026-06-27 `d2b3ed27` 作为死代码删掉，331 行，整屏 1280×720 自己用）。
实时版把它的 `_stats_table` 「1:1」搬进了战斗场景的 `_ui_layer`（`c7bb1bd7`，2026-07-11），
从此它是战场上的一张卡：底下的 PK 条、头像框、右上角按钮都还在（实拍可见），卡片只能让出四周。

### 2.3 「只有一页」的根因：从来没有人设计过分页，是一路打补丁打成的

按时间线（`git log -S` 逐条核过）：

| 日期 | 提交 | 发生了什么 | 「一页」怎么被固定下来的 |
|---|---|---|---|
| 2026-06-27 | `287b8399` / `d2b3ed27` | 从回合制版分叉；回合制结算屏 `BattleEndScene` 当死代码删掉 | 独立的结算屏没了 |
| 2026-07-11 | `c7bb1bd7` | 「照回合制 `BattleEndScene._stats_table` 1:1 落地」，5 列改 7 列，双队并排 | 回合制是 3v3、一张表，搬过来变成两张表并排 |
| 2026-07-19 | `161f39c9` | 「结算页要含前面战场」⇒ 上路/下路/终极/合计页签 | **唯一一次「分页」，分的是路，不是内容**；页签只切表，标题和奖励不动 |
| 2026-08-02 | `c6d36615` | 「整页重做」：原来五行按屏高比例摆 ⇒ 改成**一张居中的卡片**（标题→后果→比分→奖励→表→按钮） | 修的是「换分辨率就要重调比例」。**「一张卡」是那次修法的手段，不是用户提的要求**。从此所有东西都在一张卡里 |
| 2026-08-10 / 08-12 | `7305b263` | 名单一长按钮就被挤出屏 ⇒ 表加高度上限、按钮移出滚动区 | 在一张卡里给表**封顶** |
| 2026-09-29 | — | 两处高度预算差 56px ⇒ 统一成 `settle_outer_budget` ＋「还有 N 只在下面」提示 | 在一张卡里把滚动**做对** |
| 2026-10-02 | — | 零值不印数字 | 在一张卡里**减字** |

⇒ **一页不是谁定下的设计**。方案书和提交里找不到任何一句「结算屏只要一页」。
它是 07-11 照搬时的形状，08-02 为了修比例布局收成一张卡，之后四次修复都是在这张卡里面挪：
封顶、挪按钮、修预算、减字。**每次修的都是「在一页里怎么塞得下」，从来没有问过「为什么非得一页」。**

用户问的「为什么这么小」和「为什么只有一页」，其实是**同一个根因**：
所有东西装在一列里，表格排最后分到 23% 的高度；两队并排把宽度吃完；字号又是在电脑上挑的。

### 4.2 设计：三页，左侧竖页签

示意图是**引擎里的原型实拍**（`tests/_proto_settle_pages.gd`，用的是同一局的真实数据：
`_st_lane_hist`、`_st_row`、`_st_merge_all`、`lane_results`、`_build_reward_chips`，只是换了排法）：
[02-现状vs原型-手机2340x1080.jpg](img-20261004-结算屏重做/02-现状vs原型-手机2340x1080.jpg)、
[03-现状vs原型-1280x720.jpg](img-20261004-结算屏重做/03-现状vs原型-1280x720.jpg)。

```
┌──────────┬────────────────────────────────────────────────────┐
│  失败    │  第1页「战果」        失败（84px）                 │
│┌────────┐│                     消耗 1 点生命                  │
││ 战果 ◀ ││                 [上路 负] [下路 负]                │
│└────────┘│      深海币 +15  剩余生命 5/6  赛季胜场 0 …        │
│┌────────┐│           本场 MVP  [头像] 石头龟  打出 1572       │
││ 我方   ││                                                    │
│└────────┘│  第2页「我方」 / 第3页「敌方」：一队一页          │
│┌────────┐│     [合计][下路][上路]                             │
││ 敌方   ││     头像 名字 22px │ 打出 24px+占比条 │ 扛住 │ 治疗 │ 击杀
│└────────┘│     8 行 × 56 = 一页放下，不滚                     │
│ ←滑动翻页→│                         [前往商店] [返回主菜单]    │
└──────────┴────────────────────────────────────────────────────┘
```

**为什么页签竖着放在左边**：横屏多出来的是**宽**（根因 C：手机上空着 31% 的宽），缺的是**高**（根因 B）。
页签横着放在顶上要占 60~90 的高度；竖着放在左边只占宽度，每个按钮还能做到 96 高（52pt，超过 44pt 触控线）。

**三页分别放什么**：

| 页 | 内容 | 来源（全部是现有读数，不新增数据） |
|---|---|---|
| 1 战果（默认） | 胜负 / 封存时写「结果已封存」+ 后果一句 / 各路胜负（每路一块大字）/ 奖励块 / 上传正反馈 / **我方 MVP 一行** | `_banner_sealed` `_result_subtitle` `lane_results` `_build_reward_chips` `_attach_upload_flash` `_st_mvp_index` |
| 2 我方 | 一队一张表，4 列不变（打出/扛住/治疗/击杀），零值仍印「·」，MVP 角标，**打出列加一根占比条**；右上切换 合计/下路/上路（默认合计） | `_stats_column` 的数据口径原样 |
| 3 敌方 | 同上 | 同上 |

**尺寸（手机上的最小可读线）**：

| 元素 | 现在 | 方案 | 手机上 |
|---|---:|---:|---:|
| 表格名字 | 13 | **22** | 11.9 pt（过 11pt 下限） |

## 7. 决策记录

**我的建议**：采用 §4.2 的三页方案。理由是「小」和「一页」是同一个根因，
不改「全塞进一列」这个结构，任何字号调整都会被高度预算吃掉（根因 B），
任何加宽都会被两队并排吃掉（根因 D）。上一篇的四个选项里，只有「页签」（C）碰到了结构，
但它当时只打算切我方/敌方、还留在那张卡里，所以照样小。

**等用户拍板：**

- **U1** 三页（战果 / 我方 / 敌方）还是两页（战果 / 战报，战报页我方敌方上下排）？
  两页能直接对比，但 16 行要挤进约 480 的高度，行距只剩 30 左右，字号估计只能到 18px 上下
  （9.8pt，低于 11pt 线；这是按原型的页体高度推算的，没有实拍）。**我建议三页。**
- **U2** 第 1 页要不要等几秒自动翻到「我方」？CoD Mobile 是自动走的（右上有 11s 倒计时）。
  **我建议不自动翻**：玩家想看的是奖励，而按钮就在第 1 页。
- **U3** 第 1 页要不要加「看战报 ›」按钮（左边页签之外的第二个入口）？
- **U4** 龟蛋和训龟大师：①照旧占行 ②移到表底，用一条分隔线隔开 ③不进表，第 1 页单独一行写「龟蛋承受 4539」。
  **我建议 ②。**
- **U5** 名字前面用头像（原型的做法）还是保留稀有度色点？头像能一眼认出是哪只，但小将六只长得一样。

**历史上已经拍板、这次不动的**：见 §4.2「必须保留」一节。
