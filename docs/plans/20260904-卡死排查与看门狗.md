## 3. 调查：修掉的真 bug

### 3.1 现象

`STRESS` 压测 420 秒里 **137 条错误**，其中 **113 条（82%）** 全在同一行：

```
SCRIPT ERROR: Trying to assign invalid previously freed instance.
   at: SignalWaveSystem._place_nodes (res://scripts/systems/equip/signal_wave_system.gd:182)
   [2] tick_global (res://scripts/systems/equip/equip_system.gd:1920)
```

`tick_global` 每帧调 ⇒ **每帧刷一条**。

### 3.2 根因

```gdscript
var im: MeshInstance3D = w.get("mesh", null)      # ← 这一行就报错了
var imesh: ImmediateMesh = w.get("imesh", null)
if not is_instance_valid(im):                      # ← 已经晚了一步
```

换路清场把 `_world` 下的节点 `free` 掉了，而 `w` 字典里的引用**没跟着清**。
从字典取出**已释放**的对象、直接赋给**带类型标注**的变量时，
Godot 在**类型检查那一刻**就抛错 —— 下一行的 `is_instance_valid()` 根本来不及。

### 3.3 修法

先用**无类型**变量接住，验过再进带类型的：

```gdscript
var _raw_im = w.get("mesh", null)
var im: MeshInstance3D = _raw_im if (is_instance_valid(_raw_im) and _raw_im is MeshInstance3D) else null
```

### 3.4 同形状扫全仓

`hookbomb_system.gd:947`（海盗钩索的数字标签）**一模一样**，一并修。
那次压测没触发它只是因为没带那件装备。

`battle_spawn.gd:813` 的 `var tex: Texture2D = su_sd.get("tex", null)` 形状相同但**风险低** ——
`Texture2D` 是 Resource 不是 Node，不会被 `queue_free` 变成 invalid instance，且那个字典不跨帧存活。未改。

### 3.5 验证

| | 修前 | 修后 |
|---|---|---|
| 压测总错误 | 137 | **25** |
| 那一行 | 113 | **0** |

## 4. 方案：`WATCHDOG=1`

现成的卡死看门狗（独立线程盯心跳、冻结 >4 秒打出最后操作）**只在 `STRESS` 下开**，
而用户正常玩不带那个 env ⇒ 卡住时现场什么都没留下。

| env | 冻结时 |
|---|---|
| `STRESS=1` | 打 FROZEN 行 → `OS.crash()`（外层脚本读日志定位） |
| **`WATCHDOG=1`** | **追加写 `user://freeze_report.txt` → 继续盯**（不崩溃，玩家还得能退出/截图） |

「追加写 + 继续盯」是为了能分辨**只卡一次**（首次资源加载）和**反复卡**（真死循环）——
多条报告里 `battle_t` 有没有推进，一眼就看出来。

报告含：`last_op`（卡在哪只龟/哪个技能/哪件装备）、`fps`、`tweens`、`pending`、`world/ui` 子节点数、`objs`。

代码抽成 `scripts/scenes/battle/battle_watchdog.gd` —— 它不在 `_sim_step` 调用链上，
按 CLAUDE.md §5 的判据本来就该独立。主文件 8925 → **8918** 行（比动之前还少）。

**用法**：`WATCHDOG=1` 启动，卡住后看
`C:\Users\Louis\AppData\Roaming\Godot\app_userdata\斗龟场 实时版\freeze_report.txt`

## 5. 需求与代码的出入 + ★★★我栽的坑：漏接心跳，照着假报告追了一晚上

加 WATCHDOG 时我接了看门狗线程、接了 `_dbg_op` 打点，**唯独漏了心跳** ——
`_hb += 1` 那一行写在主文件的 `if _stress:` **里面**。

⇒ `_hb` 恒为 0 ⇒ 看门狗**从第一次检测起就一直报 FROZEN**。

我照着这些假报告"定位"出一串**根本不存在**的结论：

| 我"定位"到的 | 实际 |
|---|---|
| 卡在训龟大师的 tick | 噪声 |
| 卡在 `p2eq_066` 的 on-kill | 噪声（那件装备的 on-kill 分支根本不存在） |
| "`battle_t` 停住 5 分钟" | **那一局打完了** —— `_t` 在战斗判定结束后本来就冻结（CLAUDE.md §3.5 写着） |

**线索早就在报告里**：`fps=137`。帧率正常却说主循环冻结，两件事不可能同时成立。
那个字段是我自己加的，打出来了，却没停下来问一句。

修好心跳后 **0 次报警** —— 这一步本该在信任任何报告**之前**做。

## 6. 已知风险与未决点

### 未决

**① 用户报的卡死仍未复现**
无头 / 带画面各三轮，心跳修好后 0 次报警。信号波那个 bug 会让游戏**发卡**，
但「画面完全不动」需要主循环真的停住 —— 那个还没抓到。
⇒ 等用户下次卡住时带 `WATCHDOG=1`，把 `freeze_report.txt` 发回来。

**② 硬件因素已排除，但只排除了近 3 天**
查 Windows 事件日志：近 3 天**无** TDR（显示驱动重置 4101/4102）、**无** WHEA、**无**异常关机。
⚠ 但 CLAUDE.md 记着这台机器 **CPU 有确诊硬件故障**（WHEA `Internal parity error` 累计 20 条、
两次异常关机连转储都没写出来）。近 3 天干净不等于以前干净 —— 如果用户的卡死发生在更早，
这条排除不成立。
