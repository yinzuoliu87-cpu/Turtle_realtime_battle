## 1. 先修 bug：砸落比落地早（实测早 3.59 米）

### 现象（探针实测，非推理）
```
[PROBE] ★砸落结算 t=2.6000  此刻 height=0.9065  airborne=true
[PROBE] ★砸落结算 t=7.7333  此刻 height=3.5931  airborne=true
```

### 根因
`_sim_step` 里：
- `_equip_sys.tick_global(dt)`（→ `_tick_slams` 倒计时）在 **第 2207 行，无条件执行**
- `_t += dt` 与 `_tick_unit`（airborne 积分在里面）在 **第 2246 行，被 `if frozen / elif in_ts / else` 三层门控**

⇒ **顿帧（hitstop）与时停期间，跳跃冻结、砸落倒计时照跑**。探针里连续四步
`_t` 停在 2.0000、`height` 停在 6.566，而 `t_left` 每步照扣 0.0167。
飞行途中挨打越多、顿帧攒得越多，砸落提前得越多（实测 `_t` 走 1.400 秒，倒计时消耗 1.667 秒，快 19%）。

### 为什么门禁没抓到
③L 比的是「起跳写入的 `vy`/`g` 算出的落地时刻」≡「砸落倒计时初值」——
**两个写入值之间的代数恒等**，且两边都在 `_feed` 里，而 `_feed` 不跑顿帧、不跑主循环。
代数上永远相等，物理上从来不等。同 memory [[fb-write-without-reader-and-fake-gates]] 第②型
（读了但那个值根本没人写）的变种：**读了、也有人写，但两个数走的是两条不同的时钟**。

### 修法
砸落**不再由倒计时触发**，改由**真实落地事件**触发：`airborne` 由 true→false 的那一帧结算。
倒计时降级为**兜底**（携带者中途死亡/被位移/永远落不了地时不至于卡住在途表）。
⇒「砸击命中 = 落地那一刻」变成**构造上成立**，而不是两个时钟碰巧对上。

## 2. 演出重做：三条腿，各用对的工具

### ① 雷雾 → `GPUParticles3D` 真体积粒子
- 发射体 `EMISSION_SHAPE_RING`（内径 0、外径 = `SLAM_R_PX`），粒子在**整个圆盘**里生
- 开 `turbulence`（Godot 4 内置）+ 每颗独立 `angle`/`scale_curve`/`color_ramp`
- 敌方红雾 `暗红→亮红→透`，己方蓝雾同构；朝上微弱初速 + 轻负重力 ⇒ 翻涌
- 数量按面积给，不是固定 14

### ② 电弧 + 冲击波 → PixelLab 逐帧动画贴图
这两样的精髓是**逐帧变形**，几何算不出来。
- **雷弧循环**：`create_1_direction_object`（sidescroller）+ `animate_object`（v3，8~16 帧），
  沿圆周摆一圈、**各自随机起始帧**（比"每 0.07 秒整批重生随机折线"自然）
- **冲击波爆开**：top-down 一次性帧序，**逐帧有形变与厚度**，不是一个环在被拉大
- 播放方式照抄项目已有：`QuadMesh` + `region_rect` 按 `.json` 的 `duration` 切帧
  （`battle_ballistics.gd` 就是这么干的 —— 不另起一套）

### ③ 砸落的水 → GPU 粒子 + 拖尾
现在是 46 个 `BoxMesh` 各自算抛物线。改成一次性 emit 的 GPU 粒子（重力 + 阻尼 + 尺寸曲线），
大颗挂 `RibbonTrailMesh` 拖尾。

### 素材纪律
**全部新生成**（memory [[fb-no-asset-reuse-unless-told]]）。用户 2026-08-09 明确：
**不与现有 vfx 库对齐，像素风格即可** ⇒ 不传 `style_images`，用默认风格。
生成后先 `get_object` 看候选、剔掉畸形的再 `select_object_frames` 入库
（memory [[fb-pixellab-sprite-tuning]]：best-of-N 挑 + 剔非人类畸形）。

## 4. 已知风险与未决点

**风险 1：粒子在无头 CI 下不推进。**
`GPUParticles3D` 走 GPU 模拟，headless 很可能不出结果 ⇒ **门禁不能量"粒子实际位置"**，
只能量**配置**（发射形状/半径/数量/颜色/材质在位）。这与 CLAUDE.md §3.5「别让数值测试依赖演出 tween」
同一条原则：**判据落在能同步读到的东西上**。若需要量真实粒子，只能靠实拍截图人工判。

**风险 2：PixelLab 出的效果图不一定能用。**
它的模型是给角色/物件设计的，VFX（尤其"扩散的环"）可能出成一个静态图标而不是可播的帧序。
兜底：若 `animate_object` 出来的帧序不成立，退回**用 `create_image_pixflux` 逐帧手工出图再自己拼表**，
或该条保留现有几何实现并**如实告知**，不硬塞。

**风险 3：改砸落触发方式会动到"法力锁"的解锁时机。**
规格明写「造成伤害后才重新记录法力值」。落地事件触发 ⇒ 解锁时机跟着变，
必须确认 `_mana_unlock` 仍在**伤害结算之后**发生（现有门禁有这条，别弄红）。

**风险 4：`airborne` 是共享字段。**
被别的技能击飞也会置 `airborne`。若砸落监听"airborne 转 false"，
携带者在起跳途中被**别人**击飞再落地，可能被误判成砸落落地。
⇒ 需要一个**本次起跳专属的标记**（如 `_pestle_air_id`），落地时核对是不是自己那一跳。

**风险 5：性能。**
1000 码圆盘铺粒子 + 一圈电弧精灵 + 水花粒子，同屏多个携带者时可能掉帧。
⇒ 粒子数按面积给但要设上限；电弧数量沿用 `WARN_ARCS = 22` 先不加。

**未决点 1 —— 已解决（用户 2026-08-09 拍板）**：半径 1000 → **500**。
理由与后果都量过：`ARENA = Rect2(70,110,1596,728)`，1000 ⇒ 直径 2000 比长边还长；
500 ⇒ 直径 1000 横向放得下、纵向（728）仍超 ⇒ 上下被战场边界切平，但已读得出"这是一个范围"。

**未决点 2（等用户拍板）**：上一轮我列的「整个流程里没有『杵』」——
起跳/峰顶/落地三段龟都是空手，没有道具也没有砸的动作。用户对这条回了「不要」，
故本次**不做杵**，只做雷雾/电弧/冲击波/水花四样的技术升级。
