# 20261002 · CI 专属红三条（本地全绿）

> 状态：**已完成**（v0.19.505 并入主仓）

> 结论先写在最前面：**三条红、两个文件、同一个病** ——
> 判据的**尺子跟机器快慢挂钩**。本地无头帧率极高、CI(ubuntu, 4 核跑 16 个并行 Godot)
> 一帧远超钳位上限，于是**同一句「等 40 秒」/「等 900 帧」在两台机器上买到的游戏时间差一个数量级**。
> 两条判据的数字（`MIN_TOTAL=150` / `MIN_SLAPS=3` / 四张贴图名）**一个字都没动**。

- 来源 run：`37034657957`（`gate` job，`gatefail-verify_*.log` 取自 `ci-logs` 分支）
- CI 实际红的是 **4 条断言**（任务书给了 3 条，`verify_axe_anim_runtime` 那边是 2 条连红：
  「施法播完自己回了 idle」+「④ 攻击」）。两条是同一个根因的前后脚。

## ① + ② `verify_dmg_type_sentinel`：`取用次数 143 ≥ 150` / `本场拍了 2 次 ≥ 3`

### 根因（打的是数值，不是推测）

判据里原来写着：

```gdscript
## ★墙钟，不是帧数、不是游戏时钟（CLAUDE.md §3.5：三把尺子里只有墙钟对）。
var t0 := Time.get_ticks_msec() / 1000.0
while now - t0 < secs: await get_tree().process_frame
```

那句注释对「等一件游戏内效果发生」是对的，对**攒分母**是错的：

**墙钟每一帧最多只能买到 0.1 游戏秒。** `_process` 顶上 `rd = minf(delta, 0.1)` 是防卡死钳位，
一帧真实耗时超过 0.1 秒，多出来的那段游戏时间**直接蒸发**。本场又是全仓最重的场面
（28 龟 × 5 件灵物 14v14 打满），CI 上一帧远远超过 0.1 秒。

| 机器 | 40 墙秒 → 买到的游戏时间 | 取用次数 | 触手拍击 |
|---|---|---|---|
| 本机 `--max-fps 15` | **28.40 秒**（601 帧，0.0473 游戏秒/帧） | 1019 | 14 |
| CI ubuntu（`ci-logs` 实测） | **≈4 秒**（按同一速率反推） | **143** | **2** |

⇒ 「采到多少条」这个分母**跟机器快慢挂钩** ⇒ 本机必绿、CI 必红。
这就是 CLAUDE.md §2 那张表里「采样条数当分母」那一行。

### 改法

不再按「跑了多久」收工，改成按**本文件每一条分母都真的攒够了余量**收工
（各攒到地板的 `MARGIN=2` 倍就立刻走），上限仍是 `secs` 游戏秒 + 一道宽松墙钟硬顶：

```gdscript
enough = sentinel_total() >= MIN_TOTAL * MARGIN     and _pk["queued"]     >= MIN_SLAPS * MARGIN     and _crit_drift       >= MARGIN
```

并且**「尺子自己」也升成一条判据**：`_ok(enough, "分母·尺子: …")`。
攒不够就直接报「这场没跑到位」，而不是让它伪装成「这场碰巧没打够」——
后者正是那四轮 CI 红的样子。

### `--max-fps 15` 前后实测

| | 改前 | 改后 |
|---|---|---|
| 收工条件 | 40 **墙**秒 | 分母各攒到 2 倍地板 |
| 实际跑了 | 40.0 墙秒 / 601 帧 / 28.40 游戏秒 | **14.9 墙秒 / 224 帧 / 12.78 游戏秒** |
| 取用次数（地板 150） | 1019 | **521** |
| 触手拍击（地板 3） | 14 | **6** |
| 暴击漂移（地板 >0） | 59 | **29** |
| 结果 | ALL PASS | **ALL PASS** |

本机**反而快了 2.7 倍**（这是把"按时间跑"换成"按攒够跑"的副产品）；
CI 上它会一直跑到真的攒够，不再 40 秒就交卷。

### 为什么这不是放宽

- `MIN_TOTAL=150` / `MIN_SLAPS=3` **一个字没动**，一条判据都没删。
- 改的是**尺子**（怎么决定收工），不是**判据**（收工时要达到什么）。
- **新增**了一条判据（`分母·尺子`），净变化是判据变多、变严。
- 反向验证（`SENT_SECS=0.6`，把 sim 掐到 0.65 游戏秒）：

```
分母·尺子: sim 走了 0.65 游戏秒 / 10 帧 / 墙钟 0.6 秒
[FAIL] 分母·尺子: 每条分母都攒到地板的 2 倍才收工
[FAIL] 分母·取用次数 0 ≥ 150（太少=空检查）
[FAIL] 分母·本场拍了 0 次 ≥ 3（太少=空检查）
★FAIL x5
```

地板照样咬人 —— 它没有被放宽，只是现在有东西保证 sim 真的跑到位了。

## ③ `verify_axe_anim_runtime`：`④ 攻击 … 实测 eq096-axe-wood-cast.png`

### 根因：**被测对象在量它的半路上被打死了**（判据把这说成了「贴图不对」）

CI 上红的其实是**连着两条**：

```
[FAIL] ★分母: 施法播完自己回了 eq096-axe-wood-idle.png  实测 eq096-axe-wood-cast.png
[FAIL] ★★④ 攻击: 引擎换成了 eq096-axe-wood-attack.png   实测 eq096-axe-wood-cast.png
```

这份判据的尺子已经换过两次，两次都**跟机器快慢挂钩，只是方向相反**：

- 墙钟（2026-09-01）：并行门禁里进程被饿着，3 秒墙钟只摸到几帧 ⇒ 动画根本没推进。
- 帧数（2026-09-27）：一帧推进 `rd = minf(delta, 0.1)` 秒动画 ⇒
  `WAIT_FRAMES=900` 在本机（无头高帧率）= **0.9 游戏秒**，在 CI（一帧 ~0.06 秒）= **59 游戏秒**。**差 65 倍。**

而这只斧头是**在一场真打里站着的召唤物**。探针（本机 `--max-fps 15`，把 900 帧跑满，不提前 break）：

```
[PROBE] 回idle循环: 用了 34 帧 / 游戏时钟走了 2.133 秒 / 斧头 alive=true hp=215.0/500.0
[PROBE2] 帧 100 / 游戏钟 +5.00  秒 / alive=false hp=0.0 / 贴图=idle.png
[PROBE2] 帧 300 / 游戏钟 +11.55 秒 / alive=false hp=0.0      ← 游戏钟从这里起【冻住不动】
[PROBE2] 帧 900 / 游戏钟 +11.55 秒 / alive=false hp=0.0
```

两个数字落地：

1. **斧头 2.1 游戏秒掉到 215 血、5 游戏秒就 0 血死了。** 斧头一死，
   `battle_render._render_step` 的 `if u["alive"]` 把它跳过 ⇒ `_advance_anim` 不再推它的帧 ⇒
   **贴图永久冻在死的那一刻那张**。CI 上它死在施法动画还在播的时候 ⇒ 永久停在 `cast.png`。
2. **主人也会死**（左边被打光 ⇒ `_over` ⇒ 游戏钟冻结在 11.55 秒）—— 这条顺手挡掉了，
   否则新尺子自己会被冻住。

本机为什么永远复现不出来：那个循环在本机只持续 **0.4 游戏秒**（施法动画一播完就 break），
斧头连一次反击都还没吃到。**是尺子把 0.4 秒拉成了 59 秒，顺手把被测对象送进了战场中央。**

### 改法（两件事缺一不可）

1. **尺子换成游戏时钟 `_s._t`** —— 那正是喂给 `_advance_anim` 的那条钟（Σ钳制 delta）。
   新出口 `_wait_tex(u, want, budget)`：等到引擎拿那张图画它，或走完 `budget` 游戏秒；
   帧数退成一道宽松硬顶 `HARD_FRAMES=6000`（只防死循环）。四处等待（①待机/②走路/②回 idle/④等施法播完）全部换过来。
2. **把斧头、主人的血钉成 `1e8`**（对手本来就钉着 `1e8`）。本门禁量的是
   「四条动作播不播」，不是「斧头能不能活过 60 秒」。
3. **新增两条分母断言**，摆在 ④ 之前：
   - `★分母: 量它的时候斧头还活着`
   - `★分母: 这条钟真的走了`

   ⇒ 死斧头 / 冻住的钟再也不能伪装成「贴图不对」。断言条数下限随之 12 → 14。

### `--max-fps 15` 前后实测

| | 改前 | 改后 |
|---|---|---|
| ④ 等施法播完 | `WAIT_FRAMES=900` 帧（本机 0.9 游戏秒 / CI 59 游戏秒） | **0.47 游戏秒 / 9 帧**（任何机器都是 0.47 游戏秒） |
| ② 回 idle | 900 帧 | **2.00 游戏秒 / 32 帧** |
| 斧头状态 | 900 帧跑满时 `alive=false hp=0` | `alive=true hp=1e8` |
| 断言条数 | 19 | **21** |
| 结果 | ALL PASS（本机）/ FAIL x2（CI） | **ALL PASS（21 条）** |

### 为什么这不是放宽

四张贴图名（`idle/walk/attack/cast`）、`axe_cast` 动作名、committed 闸、
⑤「没有 hurt / 没有 death」、⑥ 九把斧按形态换表 —— **一条判据都没改、没删**。
改的是「等多久」和「量的时候被测对象在不在场」，并且**多加了两条分母断言**。

**反向验证直接复刻出了 CI 那一行原话**：把斧头的血改回 `hp=1.0`（让它在量的半路上死掉），

```
[FAIL] ★分母: 量它的时候斧头还活着  hp=0.0/60.0
[FAIL] ★分母: 施法播完自己回了 …idle.png  实测 eq096-axe-wood-cast.png（等了 4.00 游戏秒 / 84 帧）
[FAIL] ★★④ 攻击: 引擎换成了 …attack.png   实测 eq096-axe-wood-cast.png
FAIL x3
```

`实测 eq096-axe-wood-cast.png` —— 与 CI 日志逐字相同。**根因到此是量出来的，不是推出来的。**
（变异已逐字节还原。）

## 普适教训（候选进 CLAUDE.md §2 那张表）

那张表里原来有四种形状。这一轮加第五种，而且它比前四种更阴：

| 形状 | 这一轮的实例 | 改法 |
|---|---|---|
| **墙钟买不到游戏时间** | 「跑 40 墙秒」在 CI 上只买到 ≈4 游戏秒（`rd = minf(delta, 0.1)` 把超出的那段蒸发掉） | 按**sim 真实进度 / 分母攒够**收工，别按墙钟 |
| **尺子把被测对象送进了战场** | 900 帧在 CI = 59 游戏秒，斧头在这 59 秒里被打死，贴图永久冻住 | 判据外还要问一句「**量的时候它还在场吗**」；每条断言配一条在场分母 |

> 一句话：**「等多久」这件事本身就是判据的一部分。** 尺子一变长，被测对象可能已经不是原来那个了。

## 1. 需求原文

用户 2026-10-02：「**你不能跑完这个继续跑别的吗**」之后我去看 CI，发现
**提交门禁在 ubuntu 上已经红了至少 4 次，而我本地每次都报绿**。
CLAUDE.md §7 写着「本地绿 ≠ CI 绿，报绿前用 API 亲自看 CI」——我今天一次都没看。

## 2. 调查

从 `ci-logs` 分支扒 `gatefail-*.log`：CI run `37034657957` 实际红了 **4 条**断言，不是 3 条
（`verify_axe_anim_runtime` 红在**连续两行**：④ 的分母与 ④ 本身）。详见下面各节的实测数字。

## 3. 出入（需求与现状对不上的地方）

| 我以为的 | 实测 |
|---|---|
| 「本地全绿 = 可以 push」 | 本地绿只证明本地；CI 上这两条**必红** |
| 「动画资源配错了」（看报错字面） | **动画从来没坏过** —— 尺子长到把被测对象（斧头）熬死了 |
| 「采样不够就是场景不够热」 | 场景已是全仓最重；真因是**墙钟每帧最多买 0.1 游戏秒** |

## 4. 方案

见下面各节：两条都改成**不随机器快慢变的尺子**（按 sim 进度停 / 按游戏时钟等），
**阈值一个字不动**，并各补分母断言。

## 5. 验收

- 两条在 `--max-fps 15`（CI 时序的本地复现）下绿
- 反向验证**真红**，且 axe 那条**一字不差复现 CI 的报错行**
- 全套 `run-tests.sh` 绿
