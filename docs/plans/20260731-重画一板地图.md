## 2. 先量后画（这一节是全部结论的地基）

不量就画会把心血画在看不见的地方。用真相机参数（`pos(0,28,22) fov40 look_at(0,0.6,0)`）做投影，得到：

| 量 | 值 |
|---|---|
| 战场 `ARENA` | dx∈[−798,+798] dy∈[−364,+364] → **行 3~12 / 列 4~24** |
| 两队站位 | dx = ±420（`dual_lane_flow` 的 `_cx±420`），每路 **3 只**，纵向间距 154 |
| 屏幕可见且不被队伍面板遮 | **列 5~22 / 行 0~14** |
| 永远看不见 | **行 15-16**（58 格）；列 0-1/27-28 屏外；列 2-4、23-26 被面板遮 |

**四档材质在正式对局光照下的实测亮度**（不是 `TILE_COLS` 的 albedo —— 那还要乘灰度贴图、过光照与 filmic tonemap）：

```
void 20  <  淤泥 32  <  石 49  <  沙 61  <  水 98
                                   ↑蓝(+46)   ↑青(+68)
```

→ **只有水是亮的**，构图的全部功夫在「亮青画成什么形状、放在哪」。

## 3. 改前那张图错在哪（v0）

亮青水池恰好铺满 dx∈[−450,+450]、dy∈[−290,+290] —— **所有战斗都发生在最亮的地方**。
深色龟压在亮度 98 的青上，而画面其余部分是均匀铺开的深蓝格子，整幅读作「一块瓷砖地板」。

## 4. 三轮迭代（每轮都渲染了真图再自评）

| 轮 | 做法 | 自评发现的问题 |
|---|---|---|
| **v1** | 一个超椭圆 t 场分四层同心带 + 场心徽记 + 台子沙边 + 潮汐水道 + 礁岩 | ①void 61% 超门禁上限、板子反而更小 ②垂直方向只有 505px 要塞三条带 → 每条不到 1 格 = 全是毛边 ③8 类特征挤在 18×13 的可见区 = 噪点 |
| **v2** | 砍到 4 类大特征、最小 3 格、`N=3` 圆角矩形 | ①`N=3` 的边是**直的** → 水的内缘成两条水平直线 = 读作「两条青色横条」②亮部全在屏幕上下沿，**屏幕正中整片是死的** ③矫枉过正，比 v0 还没看头 |
| **v3** | **梭形岛 `N=1.7`** + 中轴石道 + 特征方块化 | ✅成立。顺带试了「岸线」并**否掉**（见 §6） |

## 5. 定稿构图

```
行 0     void（地平线）
行 1     浅滩淤泥
行 2-3   ██ 潟湖（亮青）
行 4-11  岛心（暗淤泥）+ 两座石栈桥（列7-9/18-20，行5-11）+ 场心沙台（列13-15）
         + 中轴石道（行7-8，串起三个地标）
行 12-14 ██ 潟湖（亮青，靠近相机、屏幕上最大）
行 15-16 void（永远看不见）
四斜角    水扫进来 —— 岛是梭形，两侧收尖
```

分布：淤泥 187(38%) / 水 106(22%) / 石 57(12%) / 沙 15(3%) / void 128(26%)

**三条设计原则**（都是从失败里得的）：

1. **岛心留暗** —— 单位立绘最好读。亮青挪到「看得见但打不到」的带。
2. **梭形而不是环形** —— 见 §6 的几何硬限制。
3. **暗地直接接亮水，不设沙滩过渡** —— 32 直接跳 98 是这张图能拿到的最大对比。
   沙(蓝)因此成了场心专用色 = 全场唯一的蓝 = 焦点。

## 6. 已知风险与未决点

### 已知的硬限制（量出来的，不是选择）

- **完整可见的闭合水环做不出来。** 战场宽 ±798、可见不被遮的窗口只到 dx∈[−673,+632]，
  而岛必须装下最外单位（实测 dx≈±555）⇒ 留给环左右两臂的只有 ~88px = **1.1 格**。
  v3 试过，两臂只剩 1~2 格且被面板切掉。梭形是绕开这条限制的解，不是审美偏好。
- **1 格宽的曲线特征在 29×17 上必然断裂。** 「岸线」试验证明：石从 50 格涨到 72 格，
  岛心读作散落的灰斑，比不加更吵。要做细轮廓得**先加密网格**（tile 76.8→38.4，格数×4）。

### 未决点（需要用户拍板）

1. **要不要加密网格？** 现在 29×17 = 493 格，单格 1.84m。加密到 58×34 能做细边/岸线/更平滑的
   海岸线，代价是 tile 节点数 ×4（现在 365 个可见 tile → ~1460）。**没量过帧率影响。**
2. **高低差仍然是死数据。** `height` 数组在 json 里但 `_tilemap_from_data` 写死 `hh = 0.0`
   （2026-07-15 拍平，因为石台+0.25/水池−0.30 让 40+ 处贴地特效掉到地板下）。
   要恢复得先解决贴地 VFX 的 y 基准，见路线图 P3。
3. **多张地图轮换（路线图 P4）没做。** `arena.json` 路径在 3 处硬编码
   （`RealtimeBattle3DScene.gd:973/1038`、`map_editor.gd:18`）。这次没动 ——
   路线图自己写着「地图形状会影响平衡数据，建议排在平衡收官之后」。
4. **装饰物仍然全部硬编码在 `battle_world_builder.gd` 里**（边框装饰图名数组 `:128`、
   固定装饰坐标 `:453-461`、中景 `MID_OBJS`、障碍 `_obstacles`），`arena.json` 里没有装饰字段。
   这次只重排了地砖层。**装饰的位置是按老地图撒的，跟新构图没有对齐过** ——
   比如底部那几株珊瑚现在长在潟湖里。要不要一起数据化？

### 已知风险

- **平衡数据不受影响**：地砖是纯视觉的，不改碰撞、不改 navmesh（障碍物 `_obstacles` 独立硬编码）。
  胜率表本来也是无装备无大师跑的。
- **MAPEDIT 手刷会与生成器脱钩** —— 已由 `map_composition_audit` ④ 焊死（改一格就红）。
  但代价是：以后想用编辑器微调，必须把改动写回生成器。
