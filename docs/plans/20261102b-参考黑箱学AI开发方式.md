## 3. 需求 ↔ 代码的出入

- 用户说「它也是 AI 游戏」—— 两边的「AI」不是一回事：它是**玩家运行时**用 AI 生成内容；我们是**开发时**用 AI（我）写代码、出图。用户要学的是**开发方式**，所以重点是它的「原子项 + 参数化模板」这套生产结构，而不是把运行时 AI 搬进游戏（那会碰服务器裁判的确定性与公平，另立需求）。
- 它的平衡问题没解决，我们反而有它没有的东西：确定性模拟 + 裁判机 + 机器人对局，可以把「每个新组合先自动跑几百局」做成门禁。

## 4. 方案（穷举清单，11-09 前）

研究（先做，认了再动手 —— memory「参考和走查在动手前」）：
- S1 特效逐帧研究：预告片（Steam HLS，两条）逐帧抽取，挑 3~5 个技能演出各写一份 `docs/studies/` 逐帧记录（`frame_study_audit` 守格式）：层次、发光叠加方式、粒子、拖尾、屏幕震动 / 顿帧、颜色与时长曲线。
- S2 实机：Steam 免费 Demo（5294350）实玩 15 分钟录屏，记「生成一个技能从按下到出效果」的完整流程与 UI。
- S3 音效：Demo 实机录音，逐个技能记「起手 / 飞行 / 命中」三段是否各有声、同类技能是否共用声音模板。
- S4 汇总成对照表：五块 ×「它怎么做 / 我们现在怎么做 / 我们能学哪条 / 代价」。

可能落地的（S4 之后用户拍板再做，见 §5 U1）：
- A1 **原子效果库**：把装备 / 技能里反复出现的效果（投射物、范围、持续伤害、护盾、增减益、召唤、击退……）抽成数据描述的原子，新装备写成「原子组合 + 参数」的数据，不再每件手写代码。
- A2 **参数化特效模板**：特效同样按原子出模板（刀光 / 弹道 / 爆点 / 光环），新内容只调参数（尺寸、颜色、时长、元素）。
- A3 **数值预算**：给每个原子定「强度预算」，新组合自动跑机器人对局，胜率出带就红（扩现有 balance 门禁）。
- A4 **美术**：「AI 出稿 → 手工 / 规则调优 → 用户认」写成固定流水（现有 PixelLab + `pixel_art_audit` 的延伸）。
- A5 **音效**：给原子配声音模板（起手 / 飞行 / 命中），批量生成 + 统一响度。
