### 2.4 AI 的自杀参数

探针跑在旧池 12732 条快照（800 只机器人跑满 6366 场）上：

```
xp ≤ 1 的 6 个流派   最高只升到 5~7 级  ⇒ 装备槽 8~12   达档8率 0.40%
xp ≥ 2 的 8 个流派   能升到 10 级       ⇒ 装备槽 18     达档8率 1.61%
```

根因 `phase2_config.gd:55` — `team_equip_cap(level) = (level-1) × 2`。

| 流派 | 达档8率 | 平均持有 | 4~5 费占比 |
|---|---|---|---|
| `hi_cost`（高费流） | **0%** | 10.7 件 | **7.8%** |
| `random`（对照组） | 1.28% | 19.0 件 | 24.7% |
| `snowball`（xp:0） | 0% | 6.9 件 | 0.9% |

## 4. 方案（穷举清单）

| # | 改哪里 | 为什么 |
|---|---|---|
| 1 | `battle_render.gd` 龟能条填充 | 让「显不显示」与「填多少」由**同一个事实**（`is_summon && maxEnergy>0`）决定；判据用 `is_summon` 把 demo 假人挡在外（`battle_spawn.gd:197` 给它们也写 `maxEnergy` 并灌满） |
| 2 | `ACTION_ELITE` 加 8 个斧头条目 | fps 由真实节拍倒推：普攻 `1/MINION_ASPD=1.25s`×60% ⇒ 8fps；炽天使 `4s÷10 把` ⇒ 15fps；charge/plant 是持续状态 ⇒ 循环 |
| 3 | `axe_system.play_action()` 单一出口 | 八处不各抄一遍 `_resolve_action + _set_anim_sheet` |
| 4 | `axe_passives.swing_kind()` 纯函数 | 「这一下是竖劈还是横扫」收在一处，结算侧与演出侧读同一个答案（否则是第三份副本） |
| 5 | 新建 `axe_passive_vfx.gd` + 5 张素材 | 被动 3/4/5/6 + 主动的场景特效 |
| 6 | `axe_final_forms.gd` 三处接动作帧 | throw / plant / execute |
| 7 | `battle_vfx_lab.gd` 支持 `axe_stage`/`axe_final` | 九档逐档能开窗口 |
| 8 | `vfxlab_cases.gd` 加 9 个 case | 每档的 `dur`/拍点按各自被动的真实触发节奏算 |
| 9 | `_cohort.gd` 的 `MIN_XP_BUYS` + 跑前守卫 | 配了自杀权重直接拒绝开跑 |
| 10 | `ACTION_ELITE` 整表搬到 `gamedata/` | 主文件超 `arch_budget`，按 CLAUDE.md §5 落位表挪走而不是抬台账 |

**「不敷衍」的操作定义** —— 每个演出的形状必须由机制决定：

| 演出 | 形状的依据 |
|---|---|
| 蓄力梯形 | **就是 `AE.in_trapezoid()` 的判定区**，四角逐码对齐 |
| 横扫弧 | 直径 = `atk_range × 2` = `sweep_targets` 的判定直径 |
| 猛砸落地 | 取 `TRAPEZOID_NEAR_W`，**范围由梯形表达**，它只负责"砸得重" |
| 强化砸 | 冲击环，尺寸对应 `SMASH_KNOCK_PUSH`（只打一个人，不做成大 AOE） |
| 主动治疗 | 绿光柱（治疗）+ 金底环（护盾），对应 `_heal` + `_grant_shield` |

★ 梯形半宽按**满蓄高 800** 插值、不是按当前高 —— 与判定同一个公式。跟着当前高插值会
让梯形长大时"变胖"，演出就比判定宽。

`wood / stone / iron` + 四造物 **没有逐档实拍确认视觉** —— 门禁验过建节点、走真入口，
但「看起来对不对」只有实拍说了算。
⇒ 判据同 §4 那张表。实拍会抢 CPU，等快照跑完再补。

**② 流派验收判据「零羁绊 ≤ 20%」本身有问题**
见 §3 出入④。新池跑完若**只红这一条**，是判据的问题不是 AI 的问题。
⇒ 但要**先量再改**，不许因为红了就放宽。建议改成「档 ≥4 的零羁绊率」或按档位分层。

### 已堵

| 风险 | 处置 |
|---|---|
| 调试台写 `GameState` 污染真存档 | 台子里统一置 `test_mode`（`battle_vfx_lab.gd` pre_spawn 最前面）。已写进 memory `fb-debug-stage-writes-real-save` |

### 8.3 新发现的坑（比结论值钱）

**① 连猜三次根因，最后靠染色法一次定位**
梯形**边框看不见**。我依次猜：抬高 y → 设 `render_priority` → 换对比色，**三次全错**。
染成纯品红重拍、数出 **0 个品红像素** ⇒ 确定是"根本没渲染"而不是"不显眼"。
真因：边框是**四条独立的带**，法线由 `Vector2(-d.y, d.x)` 算，四条边方向不同 ⇒
**有些带绕向朝下，被 `CULL_BACK` 整条剔掉**；填充是绕向一致的四边形所以可见。
⇒ memory `fb-probe-before-claiming-rootcause`。

**② 染色判据本身也错过一次**
给横扫染品红后只数到 48 像素，我差点判成"渲染有问题"。真相：**`modulate` 是相乘不是
替换** —— 金色素材 (1.0,0.8,0.3) × 品红 (1,0,1) = (1,0,**0.3**)，蓝分量通不过 `B>170`。
横扫一直在正常渲染。

**③ 三次"台子没配对"被读成"效果没做"**
- 横扫拍点落在斧头**走路**的四秒里 ⇒ 一片空白
- 不给假人加血 ⇒ 斧头 t=0.63 秒把三个假人清空，**整场只触发一次横扫**
- 贴地朝向用 `axis=AXIS_Y + rotation.y` 怎么转都不跟攻击方向走 ⇒ 改调 blade 那份
  **已验收**的 `ground_basis`（头注写着「符号不靠推理」），`aim` 从素材逐帧量出来 = **-20.9°**

**④ VFXLAB 污染了真存档（门禁替我抓到）**
`GameState.save()` 的守卫 `test_mode` **只在 headless 时自动置位**，而 VFXLAB 必须渲染
⇒ 九个窗口把存档改成 `axe_stage:4 / axe_final:"holo"`。表现是 `verify_axe` 当场红：
「斧头最大生命 = 500 期望 · 实测 1500」（钻石斧身板）。
恢复靠**未被污染的** `axe_exp_bar = 51 < 80`（石斧阈值）反推档位必为 0。

**⑤ 「看不见」当成「太细」，把参数往错方向推**
边框宽度 14 → 22 → 14 绕了一圈。看不见的真因是绕向被剔掉，跟粗细无关；修好后 22 码明显
过粗。⇒ memory `fb-my-thresholds-degrade-good-assets`：先确认它到底渲没渲染，再谈阈值。

**⑥ 我给用户报过一个错误结论并当场更正**
第一次 grep 用 `_vfx\.` 而文件里变量名是 `vfx`，据此报「四造物只有 2 处建视觉」——
实际是 **11 处**。用正确模式重查后立刻更正。
