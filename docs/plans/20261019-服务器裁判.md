# 对局结果由服务器算（服务器裁判）+ 强制最低版本

2026-10-19 · 状态：实施中（U1 / U2 / U3 / U5 已拍板，U4 待定）

## 需求原文

- 用户 10-19：「需要强制最低版本，而且我们的所有对局不应该在本机上吧，应该放服务器上吧，其他游戏怎么做的」
- 用户 10-18：「我看到了有诸多问题，在框那里点开始对局有啥意义，就是本地的，又不是服务器的，而且还出现本地因为站位赢了，服务器的判输」
- 用户 10-18：「我们下次内测会安排在4周后的周一，并且应该会连接主站和上架apple store了」
- 原稿 `docs/design/斗龟场大轮赛制方案v2-用户原稿.md` 第 85 行「3 分钟备战购物 → 系统瞬间结算 → 全桶观看 3 分钟战斗重放」；第 103 行「共享种子结算一次 → 双方各自观看同一份重放」。

## 调查（2026-10-19 读代码，行号见各条）

**现在谁算结果：全在客户端，服务端照单全收。**

| 模式 | 结果怎么上去 | 服务端信什么 |
|---|---|---|
| 积分赛 | 本地 `_settle_season`（`RealtimeBattle3DScene.gd:7519-7680`）扣命加胜场，再传快照 | 快照里自带的 `season_wins / hearts`，周榜直接读（`schema.sql:1035`、`:1098`） |
| 周六闯关 | 本地 `GameState.gauntlet_settle`（`GameState.gd:683-693`），传带新战绩标签的快照 | 标签 `gw/gl` |
| 周日决赛 | RPC `finals_report(p_winner_side, p_seed, p_reporter_side)`（`backend.gd:1464-1520`） | 先到先得（`schema.sql:2396-2399`）；过宽限没人报一律判 0 号位（`schema.sql:1291-1295`） |
| 录像 | `matches.result` 客户端自己填（`replay_uploader.gd:200-228`） | 照收 |

**会改结果的输入只有三种**（`replay_recorder.gd:20-24`）：`fight`（开打那一刻全部单位的站位）、`present`（点掉换路幕布——决定下一路在第几步建场）、`surrender`。其余是开局状态 `STATE_KEYS` 21 个（`replay_recorder.gd:52-83`）+ 种子。

**站位不在快照里**：摆位只改本地（`dual_lane_flow.gd:593-630`），`build_ghost_snapshot` 没有站位字段（`backend.gd:1908-1956`）；打快照时对手一方一律固定队形（`battle_spawn.gd:255-264`）。⇒ 10-18「本地站位赢、服务器判输」的根因。

**无头复算已有地基**：
- 中途退出补打用的 `resume` 模式就是「不靠人、循环 `_sim_step` 跑完一局」（`replay_recorder.gd:314-336`），摆位屏自动开打（`:396-397`）。
- 补间动画由 sim 步推进、不影响结果（`RealtimeBattle3DScene.gd:2370-2386`）；`FAST_SIM` 跳过渲染不改结果（`tests/_probe_fastsim.gd`）。
- 实测：无头每步约 1.1 ms；一局约 5000 步 ≈ 6~10 秒墙钟；9457 场里没有一场超过 4 分钟。

**版本闸**：`service_status.min_client_version` 已有，但客户端只提示、不拦人（`supabase.gd:1388-1394`）；只有 `finals_report` 对缺参的旧包回 `update_required`（`schema.sql:2370-2373`）。拉对手快照不按版本过滤（`supabase.gd:756-763`）。

**跨平台确定性**：Windows ↔ Linux（都是 x86）逐位一致、CI 金标守着；iPhone（ARM）的分叉根因（FMA / libm）已改走 DetMath / DetNav 约 1035 处，x86 上扰动模拟全过，**但真机从没验过**（`20261010-跨平台浮点确定性.md` §5 R1）。

**早有的决定**：D7「服务端复算两步走」——先客户端算 + 账目校验，架构预留复算接口，因为 Supabase 跑不了 Godot（`20260916-大轮赛制v2周赛制.md:251-252`、`:348`）。本方案就是 D7 第二步。

## 出入

- 原稿与 D7 都要求「结算权在服务端」，现状是客户端算、服务端全收（见上表）。
- 原稿没有「对局里布阵」这一步；站位应随阵容在备战时定好、进快照（10-19 用户「站位改为在背包里做好了」）。

## 其他游戏怎么做（给用户的对照，未逐家核实）

- 云顶之弈、炉石酒馆战棋：战斗在服务器上算，手机只显示。
- 部落冲突：手机上跑，打完把操作记录交服务器重放核对，对不上作废。
- 本作所有对局都是「打对方的阵容快照」，打的过程中没有实时操作 ⇒ 属于最容易交给服务器的一类：结果 = f(双方阵容 + 站位, 种子)。

## 方案

### 0. 先验真机确定性（一切的前提）

服务器算出的录像要在 iPhone 上「重算播放」；ARM 与 x86 只要分叉一步，玩家看到的过程和服务器判的结果就对不上。
⇒ 第一件事：同一份录像在 Linux 服务器、Windows、iPhone 真机各算一遍，比终局指纹（`ReplayRecorder.digest`）。不一致就先修确定性，或者改成「服务器出逐帧位置、手机只播不算」（体积大，备选）。

### 1. 裁判机

- 一台 Linux x86 小服务器（欧洲机房，内测全在欧洲），跑**与客户端同版本**的无头 Godot。
- 新表 `referee_jobs`（待算的对局：双方快照、站位、种子、模式、所属场次），裁判机轮询领活、算完写 `matches`（录像 + 结果）并调只有裁判机钥匙能调的 RPC 落账。
- 每个版本一套裁判程序（结果只在同版本里成立）；装哪几个版本由「最低版本」决定。
- 吞吐：单核约 6~10 秒一局；周六高峰按 140 人 × 6 场估，4 核足够。

### 2. 站位进快照

- 布阵从「开打前在对局里摆」挪到「备战时摆、随阵容一起提交」。快照加 `positions`；旧快照没有 ⇒ 用现在的固定队形。
- 换路幕布不再需要人点：裁判模式下 5 秒自动推进（已有 `DL_PRESENT_SEC`），录像不再有 `present` 事件。
- 投降：对快照没有对手在线，服务器算的局里不存在投降；玩家「不想看」= 跳过观看，不影响结果。

### 3. 分模式迁移（按问题大小排）

| 顺序 | 模式 | 改成 | 解决 |
|---|---|---|---|
| ① | 周日决赛 | 购物窗关 ⇒ 双方锁定快照 ⇒ 裁判算 ⇒ 所有人看同一份录像；到点没算完的也由裁判真打，不再判 0 号位 | C1、C4、C12、C13 |
| ② | 周六闯关 | 玩家点开战 ⇒ 提交阵容 ⇒ 裁判算 ⇒ 手机播录像；断网 = 打不了（不再出现本地成绩） | B1、作弊 |
| ③ | 积分赛 | 同 ②；命 / 胜场 / 周榜由服务端按裁判结果落账 | 作弊、周榜可信 |

②③ 的手感：现在点开战立刻开打；改后要等裁判算完（约 6~10 秒 + 排队）。缓解：手机同时本地先算、先播（确定性 ⇒ 同一结果），服务器结果到了再落账；两者不一致以服务器为准并上报。⇒ 见未决点 U2。

### 4. 强制最低版本

- 开 App 时读 `service_status.min_client_version`，低于它 ⇒ 整屏「请更新」挡住，只留去商店的按钮（现在只提示不拦）。
- 所有写结果 / 拉对手的 RPC 都带客户端版本，低于最低版本一律拒（服务端也挡，防旧包绕过）。
- 拉对手快照只拉同一「战斗规则版本」的（规则不同算不出同一局）。
- 发版流程加一步：新版战斗规则有变 ⇒ 抬高最低版本。

### 5. 与内测服一起做（问题总表 F3）

裁判机按环境各一套（内测服 / 正式服）；彩排、探针、测试只碰内测服。

## 已知风险与未决点

- **R1 真机确定性没验过**：ARM 一分叉，玩家看到的过程与服务器判的结果对不上。⇒ 方案第 0 步先验；不通过就先修，或走「服务器出逐帧位置」备选（录像体积大很多）。
- **R2 等待手感**：②③ 改后点开战要等服务器；本地先算先播能盖住，但两边不一致时要有说法（玩家看到赢、服务器判输）。
- **R3 运维**：多一台要一直在线的机器（费用约每月几美元到二十美元）、要监控、要随发版更新；挂了 ⇒ 周末出不了结果。需要兜底：裁判机挂超过 N 分钟告警 + 暂停开赛。
- **R4 旧客户端**：已发出的 0.19.570 / 0.19.571 不认新流程 ⇒ 靠强制最低版本挡掉，迁移那版一次性抬版本。
- **R5 布阵挪到备战**：玩家失去「看到对手后再摆」——这正是 10-18 不公平的来源，但手感变化要用户认可。
- **R6 投降 / 跳过**：服务器算的局没有投降；投降原本要付一条命，这条规则的去留要定。

**未决点（要用户拍板）**
- U1 裁判机放哪：自己租一台（Hetzner / DigitalOcean 欧洲，最便宜）还是用托管容器（Fly.io，按用量计费、少运维）。
- U2 周六 / 积分赛：等服务器出结果再播（慢几秒、绝对一致），还是本地先播、服务器落账（快、偶尔要解释不一致）。
- U3 布阵挪到备战页做，确认。
- U4 投降在新流程里还要不要（要的话 = 提交时就选择认输，扣命不看）。
- U5 迁移顺序：先只做周日（下次内测前稳妥做完），还是三个模式一起（工作量约 3 倍）。

## 决策记录

- 10-19 用户：要强制最低版本；对局结果应该放服务器。
- 10-19 用户「租一套欧洲的吧，你看看哪个最适合，周六周日让服务器记」⇒ U1 自己租欧洲服务器（选型见下）；U2 / U5 周六闯关与周日决赛的结果由服务器算、服务器记账（积分赛本轮不动）。
- 10-19 用户「站位改为在背包里做好了」⇒ U3 布阵挪到背包页，随阵容一起提交。
- U1 选型（10-19 查）：Hetzner CX33（4 核共享 x86 / 8 GB / 80 GB / 20 TB 流量，德国纽伦堡或芬兰赫尔辛基）约 €8.49/月（第三方报价，6 月涨价后；官网价格页未抓到具体数字，下单前以控制台为准）。
  选它的理由：① x86 —— 与 CI 的 Linux 金标同架构，确定性已逐位核过（Hetzner 同价位的 CAX 是 ARM，不选）；② 欧洲机房、内测全在欧洲；③ 共享核够用（一局约 6~10 秒，周末高峰 4 核有余），算得慢只影响等待不影响结果。
  备选：OVHcloud VPS-2 约 €7.21/月但要签 12 个月；Scaleway / DigitalOcean 同配置 €31 / $48，贵 4~6 倍。
  ⚠ 官网 cost-optimized 页抓取时各档显示「暂不可下单」，可能是抓取看不到库存；不行就换同家的 CPX（贵一档）。
- 10-19 裁判机已开：Hetzner CX33 `turtle-referee-1`（纽伦堡 nbg1，Ubuntu 24.04，x86_64 / 4 核 / 7.6 GB），IPv4 49.13.166.188，€10.19/月含税（API 实查）。已加固：系统更新、防火墙只开 SSH、只认钥匙不认密码（已实测密码登录被拒）、fail2ban、自动安全更新。凭据（SSH 私钥、API token、2FA 恢复密钥）只在开发机本地，不进仓库。
