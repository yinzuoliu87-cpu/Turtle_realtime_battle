## 2. 调查结论（现状 + 行号证据）

### 2.1 「无装备」是个干净的实验室 —— 而且比预想的更干净

**羁绊/类型系统绑的是【装备】不是龟**：[phase2_types.gd:13](../../scripts/gamedata/phase2_types.gd#L13) 的
`TYPES` 键是 剑/奇械/食物/盾/药水/护符/枪，通过 [`type_of(eid)`](../../scripts/gamedata/phase2_types.gd#L142)
从 `data/p2eq-types.json` 按**装备 id** 映射。

→ **无装备 = 羁绊自动全关**，龟的强度不再依赖"队友带了什么装备"。这消掉了最大的一个混淆变量。

龟自己的 `tags`（物理/法术/守护/元素/…）**已查实也不进战斗逻辑**（见 §5 P1）——
它只被 `preload_cache.gd` 用来预加载标签图标。→ **无装备下，一只龟的强度完全不依赖队友是谁**。

### 2.2 一只龟在无装备下剩下什么 —— **含一个我先前写错、已更正的关键点**

`data/pets.json` 每只龟：`hp / atk / def / mr / crit` + `passive`(1个)
+ `skillPool`(**4 个真技能**) + `initEnergy / maxEnergy`。

**★更正（2026-07-28）**：本方案书初版写「`skillPool` 是 4 个 `None` 的空壳，没有技能选择机制」——
**这是错的**。我的探针读的是 `s.get("id")`，而技能字典用的是 `name` 键，于是全打成 `None`。

**真实机制**：

```
skillPool[0] = 普攻（固定，不可换）
skillPool[1] / [2] / [3] = 三个候选主动技 → 玩家【3 选 1】
```

- 选择存在 [`GameState.loadouts`](../../autoload/GameState.gd#L13)（`{pet_id → idx}`，单个整数，随赛季持久）
- 选龟页 [`skill_picker.gd`](../../scripts/scenes/team_select/skill_picker.gd) 提供 UI
- 战斗端 [`_resolve_chosen_index`](../../scripts/scenes/RealtimeBattle3DScene.gd#L4924) 读它；缺键→回落 `skillPool[1]`
- **真被消费**：`battle_spawn.gd:481-546` 里凤凰强化涅槃／天使祝福／彩虹反射／忍者足／
  命运之轮／糖果炸弹 等一批效果都是「**选中才有**」

**→ 这直接改变本方案的交付物**：一只龟带不同技能是不同的强度，
所以要测的是 **28 龟 × 3 技能 = 84 个组合**，不是 28 个。
（这也正是用户说的「每只龟**和所携带技能**的胜率」。）

`defaultSkills` 恒为 `[0,1,2]`，**只被图鉴用来标"默认技能"**，战斗不读它 —— 别拿它当事实源。

### 2.3 技能多久能放一次（决定"测没测到"）

[skill_energy.gd:13](../../scripts/systems/skill_energy.gd#L13) `CD_FACTOR := 0.075`
→ **充满秒数 = 龟能花费 × 0.075**。默认花费 95 → 7.1 秒；140 → 10.5 秒；170 → 12.8 秒。

各龟 `initEnergy/maxEnergy` 不同（basic 100/150、stone 60/120、bamboo 80/170）。

**一路战斗约 25–40 游戏秒**（实测一场三路 73–113 秒）→ **每只龟每路只放得出 2–5 次技能**。
慢充能的龟放得更少 —— 这本身就是它平衡的一部分，但也意味着**样本必须足够多**，
否则"这局它刚好没放出来"会淹没真实差异。

|---|---|---|
| 单技能审阅台 `REVIEW=1 REVIEW_TURTLE REVIEW_SKILL` | `battle_spawn.gd:39-56` | **不能** —— 它是给人**看**演出的（假人、固定站位），不产胜负数据 |

## 3. 需求 ↔ 代码的出入

### ⚠ 出入1：「龟统领的技能强度」不是一个可以孤立测量的量
真实格式是 **3 统领 + 3 小将 + 龟蛋 + 双路**。一只龟的价值是**在这个格式里的边际贡献**，
不是它单挑多强。任何 1v1 擂台测出来的排名，都不能直接搬到真实对局。
→ 方案必须在**真实 3v3 双路格式**里测（见 §4.A）。

### ⚠ 出入2：「无装备」不等于「双方都弱一半」，而是**改变了强弱结构**
2026-07-27 实测：剥光对手装备后胜率 43.3% → 93.3%，说明装备原本主导胜负。
拿掉装备后，**龟本身的技能/被动/属性成为唯一变量** —— 这正是本次要测的，但也意味着
**测出来的排名只在无装备语境下成立**。有装备时某些龟可能因为吃装备加成而重排。
→ 这是本方案的**已知边界**，不是缺陷，但要写清楚（见 §5 R3）。

### ⚠ 出入3：位置（上路/下路）影响很大，不控制就测不准
上路先打、下路后打，且 `_t` 跨路累加（CLAUDE.md §3.4）。同一只龟放上路和下路不是一回事。
→ 必须控制或对冲（见 §4.A 的"位置对冲"）。

## 4. 方案（2026-07-28 定稿）

### 4.A 测什么

**84 个「龟 × 技能」组合**（28 龟 × 3选1 主动技）。每只龟带不同技能是不同的强度，
所以测量单位是组合、不是龟。用途：**调技能数值/机制**（用户明确）。

### 4.B 怎么打 —— 全循环赛 R=1

```
84 个组合 → 84×83/2 = 3486 对，每对打一场
每个组合打 83 场，对手 = 其余全部组合（所有组合的对手集合完全相同）
```

**为什么不是随机配对**（用户指出）：随机配对会重复撞同一个对手、又漏掉另一些，
于是各组合面对的对手集合不同，胜率里混进"运气碰到谁"。全循环没这问题。

**位置偏差**：每对的左右由**固定种子随机分配** → 每个组合的 83 场里约一半在左一半在右，
偏差在该组合自己的胜率里平掉。**不需要正反各打一次**（用户决定 R=1）。
**验证零成本**：跑完统计全部 3486 场的左侧总胜率，≈50% 即无系统性先手优势 —— 同一份数据换个算法。

### 4.C 单场结构 —— 被测组合独占上路 + 两只近战小将

```
上路(测的就是这条): [被测龟X·带指定技能] + 近战小将 + 近战小将
下路(纯填充·双方完全相同): [F1] [F2] + 小将
判定: 只读 lane_results["top"]，上路分出胜负立即结束本场
```

- **两只近战小将当陪跑**（用户）：小将无技能无被动，是真正的中性填充 → 彻底消掉"队友互动"变量
- 下路两只填充龟只为满足 `_dl_structure_ok` 的"恰好 3 统领"硬要求，双方完全相同且不参与判定
- **只打上路**：完整三路 54–113 游戏秒，单路仅 25–40 秒 → 机时约减半

### 4.D 固定条件

无装备 / 赛季 Lv5 / 关训龟大师 / 同随机种子 / 双方分路与小将配置完全一致。

### 4.E 交付：一张 84 行的表

```
龟        技能          胜率     场次   技能释放/场
石头龟    嘲讽          61.2%    83     2.4
…
雷电龟    雷盾          38.1%    83     0.3  ★释放次数过低
```

按胜率降序。**「技能释放/场」保留**：胜率 38% 的技能，"数值太弱"与"根本放不出来"是两种病，
改法南辕北辙。星号只标释放≈0 的行。

★同龟不同技能的对比**白捡**：全循环里天然包含「小龟+气波 vs 小龟+过肩摔」这类对局，
从同一份数据即可拆出"这只龟该带哪个"，无需额外跑。

### 4.F 机时

3486 场 × 5.4 秒（8 并行实测）≈ 5.2 小时；只判上路后**约 2.6 小时**（待标定）。
精度：每组合 83 场 → 95% 置信区间 **±10.8pp**。
→ 能判"明显过强/过弱"；**不能**判相邻名次。胜率可累加，不够再跑一轮合并即可。

### 4.G 必须做成【可重复使用的工具】（用户 2026-07-28）

> 「把这个技能胜率统计器做成好的工具，方便未来改技能后也能统计新的排行情况」

工具化要求（不是一次性脚本）：

| 要求 | 做法 |
|---|---|
| 参数化 | 轮数/种子/等级/输出目录/分片全走环境变量，改技能后原样重跑即可 |
| 可分片 | `DUEL_SHARD=i/N` → 3486 对按下标取模切片，8 进程各跑一片，互不干扰 |
| 可续跑 | 每片独立落 CSV；中途挂掉只重跑那一片 |
| 报表分离 | `tools/duel_report.py` 只读 CSV 出表 —— 不用重跑对局就能换排序/加列 |
| 自带体检 | 报表里固定输出：左侧总胜率（位置偏差）、技能释放为 0 的行、每组合场次是否齐 83 |
| 有文档 | harness 头部写清跑法与每个开关的含义 |

### 4.H 两条认知更正（写在这里防止后来人重蹈）

**① 固定种子下的全循环是【普查】不是【抽样】** —— 每对打一场且种子固定 → 结果确定。
一个组合的 83 场不是"83 次随机试验"，而是"它打赢了 83 个对手里的几个"，**没有抽样误差**。
所以「±10.8pp 置信区间」的说法是错的（本方案书早期版本写过，此处更正）。
真实的不确定性来自**换个种子胜负可能翻转**（暴击/闪避/命运之轮等 RNG）。
→ **多轮的价值是检验结论对 RNG 是否稳健，不是缩小置信区间。**
→ 第二轮换种子再跑，排名一致才叫可信；差很多说明技能差距本就在 RNG 噪声内。

**② 84 个候选技全部真生效，零静默回落** —— `_resolve_chosen_index` 末尾有一条
「选中候选若未实装 → 回落 idx1」的保护。若有技能命中它，就会把同一组合当成两三个不同组合测，
数据直接作废。已用 `_IMPL_SKILLS`(87) + `PASSIVE_SKILL_TYPES`(2) 逐个核对 84 个候选：
**真生效 84 / 回落 0**。（中途一次用正则只抓到多行 const 首行，误报"46 个回落"——
教训：解析多行 GDScript 常量别用非贪婪正则截断。）

## 6. 验收标准（含"怎么证明这个检查会 FAIL"）

| 验收项 | 通过判据 | **反向验证** |
|---|---|---|
| 真的没装备 | 每场开打后统计双方装备件数 == 0 | **给一边偷偷塞 3 件 → 它的胜率必须显著上升**；若不动，说明装备没生效或统计错 |
| 技能真的放了 | 每只龟平均释放次数 > 0，且逐技能都有记录 | 把某龟龟能设成极高（放不出）→ 它的释放数必须掉到 0 |
| 对局真的对称 | **同一只龟自己打自己（X vs X）胜率必须 ≈ 50%** | 这是**最关键的一条**：若 X vs X 显著偏离 50%，说明存在未消除的位置/先手偏差，整份数据作废 |
| 分母 | 打印总场次与每对场次；N=0 判空跑 | — |
| 排名可信 | Bradley-Terry 拟合的置信区间不重叠的对，才算"确实有差距" | 用随机数据跑一遍拟合，应得出"全部无显著差异" |

**★「X vs X ≈ 50%」这条自检必须先跑**，它一票否决整个实验的有效性。
