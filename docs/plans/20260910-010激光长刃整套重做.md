## 方案

### 一、四张素材全部重做成程序生成的像素画（`tools/gen_laserfan.py`）

沿用 009 `gen_moonslash.py` 那一套：**Bayer 4×4 有序抖动进量化本身**（消等高线色带）、
定死调色板、`TEXTURE_FILTER_NEAREST`、抖动在**最终像素分辨率**上算（`x//SS, y//SS`），16 向预烤。

| 新文件 | 布局 | 内容 |
|---|---|---|
| `vfx/eq010-tel.png` | 4×4 = 16 向 × 1 帧，格 192 | 预警：**填满整个 120° 扇形**的半调网点 + 弧边/两条直边的亮轮廓 |
| `vfx/eq010-slash.png` | 5 帧 × 16 向，格 192 | 斩击：领先边从 −60° 单向扫到 +60°，扫过的整片都上色，尾段靠**碎裂**消散 |
| `vfx/eq010-bar.png` | 4 帧 × 16 向，格 44 | 竖劈：**固定尺寸**的贴地行波条（160 码宽 = 判定半宽 ×2，48 码厚） |
| `equip/eq010-icon.png` | 32×32 | 背包图标：红色能量长刃（用户点名要换） |

**为什么 16 向预烤而不是给 Sprite3D 转角度**：009 已经定死这条 —— 贴地精灵一旦被任意角旋转，
纹素在屏幕上跟着转 → 像素网格被重采样。预烤 16 向 + `rotation=0` 让纹素始终与世界轴对齐。
顺带把「画的方向 == 打的方向」焊死：瞄准角先量化成 16 向之一，再拿它同时喂绘制和判定。

**格 192 是怎么定的**（不是拍的）：
扇形绕顶点转到任意方向时的最坏包围盒是 `1.732·R`（±60° 扇形跨过某条轴时）。
格边 `C = 1.732·R + 4` ⇒ `C=192 → R_TEX=108`。
表高 `16×192 = 3072 ≤ 4096`（老 iOS 的贴图边长下限），表 `960×3072` = 11.8 MB，
**与 009 现役的 `eq009-slash.png`（3072×960）一模一样的预算**。

密度 `pixel_size = rng×WS/108`：

| 场景 | 现在 | 重做后 |
|---|---|---|
| 近战 1★（350 码） | 0.159 | **0.078** |
| 近战 3★（450 码） | 0.204 | **0.100** |
| 赛博龟 3★（900 码） | 0.408 | **0.200** |

⇒ 一律细一倍；常见档（≤450 码）比 009 月之刃（0.105）还细。

### 二、演出改成「预警 → 扫过去 → 伤害落地预警走」

```
t+0.00  预警扇形淡入(整片 120°×450 码, 与判定同一个 dir/rng)  ── 脉动 2 次
t+0.36  斩击第 0 帧 —— 同一帧 **结算伤害**, 同一帧把预警 alpha 清 0
t+0.36..0.60  斩击 5 帧, 领先边 −60° → +60°, 扫过的整片都上色
t+0.60  只命中 1 人 ⇒ 竖劈: 沿路径铺 N 条**暗**行波条(预警) ── 每条就是 160 码宽的真判定带
t+0.80  行波条逐条点亮往前推(这就是气波), 推到哪结算到哪, 推过的条碎裂消失
```

- 伤害仍然是**一次性同步结算**（不依赖任何 tween 跑完，CLAUDE.md §3.5），
  只是把结算时刻挪到「斩击开始那一帧」，并让斩击第 0 帧就**覆盖整个 120°**（后 4 帧是亮边扫过 + 尾迹衰减 + 碎裂）。
  ⇒ 「打击把那一片打满」与「有从一边到另一边的感觉」同时成立，且不再出现「画了 33% 却打了 100%」。
- 竖劈的伤害改为**沿路径逐格同步结算**（抽成 `laser_chop_hits(origin, dir, reach, enemies)` 纯几何函数，
  演出调它、门禁也直接调它），演出只负责把条点亮 ⇒ 不再有「劈完 0.3 秒才掉血」。
- 竖劈的条宽 = `LASER_CHOP_HALF_W × 2`，**同一个常量同时喂绘制和 `_on_line`** ⇒ 画多宽就打多宽。

### 与方案书的出入（写下来，别装作没有）

- 方案里写「斩击第 0 帧就盖满 120°（伤害同帧落地）」，**实际没这么做**。
  照 009 已经用户认可的那套：**每帧径向盖满、角向靠五帧并集**，伤害在斩击第 0 帧落地。
  理由是 009 的门禁与实拍都按这个口径验过，另起一套规则没有依据。门禁 ④⑤ 相应地写成
  「领先边单调推进 + 每帧径向盖满 + 五帧并集铺满」。
- 方案里的门禁是「十条」，实际写成 **29 条断言**（含 6 条 ★分母）。
- 方案里算的是**格 192 / `R_TEX=108` / 表 960×3072**，实际是 **格 224 / `R_TEX=108` / 表 3584×1120**。
  原因：方案里我按「格边 = 1.732·R + 4」算，那是**扇形自己**的最坏包围盒；
  但顶点要放在**格心**（这样运行时 `position` 直接是释放点、不需要按方向记锚点偏移），
  于是格边得是 **2R + 余量 = 224**。两个数都对，只是问的不是同一个问题 —— 我方案里问错了。
  实际表 3584×1120（`pixelize_sheet` 的布局是「方向沿 X、帧沿 Y」），两边都 ≤ 4096。

### 门禁自己被并行门禁抓到的一条：判据不能掷骰子

⑩c 第一版写的是「总承伤 **≥ 首刀 ×1.8**」。单跑三次全绿，进并行门禁当场红：
`总承伤 1156 / 首刀 694 = 1.667 < 1.8`。

根因不是接线断了，是 `_resolve_dmg` 里会掷**暴击**（`_battle_rng.randf() < u["crit"]`，×1.5）：
两刀都不暴 = 2.00 过、两刀都暴 = 2.00 过、**只有首刀暴** = 1.667 红。
⇒ 平台加 `carrier["crit"] = 0.0`（干净合成单位隔离随机，memory `fb-make-assertions-rng-insensitive`），
判据顺势从「≥1.8 倍」**收紧**成「正好两份」（±2）。三次单跑 462 / 924 逐字相同。
**放宽阈值是错的方向 —— 那样「竖劈只打半额」也会绿。**

### 顺手抓到的核心缺陷：`_wait_sim` 会随机多等一步

逐帧数第一版重做的帧 4–16 时发现斩击 5 帧占了 **13 个 25ms 拍点**（应该 10 个）。
探针实测：第一次施放五帧全是 **4 步**、第二次施放全是 **3 步** —— 同一段演出两次施放差 33%。

根因：`_t` 一步一步加出来（每步 `SIM_DT = 1/60`），1/60 在浮点里不精确 ——
3 步加起来 `0.049999999999999996`，而 `t_end = _t + 0.05` 里的 0.05 是 `0.050000000000000003`，
差几个 ulp ⇒ `while _t < t_end` 多等一步；慢不慢**取决于当时 `_t` 的浮点相位**。
**几乎所有演出都在用 `_wait_sim`，这不是 010 的问题。**

已修（`t_end = _t + secs - 1e-6`）并焊进 `verify_interactive_determinism`：
`_wait_sim(k×SIM_DT)` 必须正好等 k 步（10 次不同步数/不同相位）。
反向验证：拿掉 EPS ⇒ 10 次里 2 次变 k+1 步，当场红。
