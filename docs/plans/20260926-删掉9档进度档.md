## 2. 调查（现状，以代码为准）

### 2.1 我 2026-09-25 做错了什么

用户当时说「我的档是 5 场次的，我要和 6 场次的人打？这不合理啊」。
**我把它读成「窗口不对称」**，于是把 `in.(N, N+1)` 改成对称的 `in.(N-1, N, N+1)`，
还新建门禁把「窗口偏移和必须为 0」**焊死**——等于给错误上了锁。

而 D5 就在仓库里，我没去查，自己造了一条「对称就公平」的道理。

★**根因是我把两件事混成了一件**：

| | 该是什么 | 我做成了什么 |
|---|---|---|
| **拉取**（网络预取） | 多拉几格备货 —— 原注释：「N+1 是主要目标：我现在是 N 场，打完这局就是 N+1 场」 | 同左（这半对了） |
| **匹配**（选靶） | D5：**完全相同** | 抄了拉取的理由 ⇒ ±1 |

### 2.3 改动面（grep 实测，不是估）

### 2.4 为什么现在做得成

严格同场次以前会大面积掉 bot —— 旧种子池 184 条**只落在 9 个场次**上（每档一个点）。
2026-09-25 已按**每个场次**重做（0~24 每格 12 支，共 396 条）⇒ **严格同场次的供给够了**。
这也正是用户说的「或者补充了经济达到同场次的人」：配额补发本来就是让场次少的人**经济等效**。

## 3. 与现状最大的一处出入：「同场次找不到人时怎么办」

D5 只说了硬条件，没说兜底。两条路：

| | 做法 | 后果 |
|---|---|---|
| A | 同场次 → **bot** | 干净，与 D5 字面一致；池子薄时 bot 变多 |
| B | 同场次 → 往**低**场次找 → bot | 与「不应该有正负一」冲突 |

⇒ **取 A**。理由：用户这次的原话是「不应该有什么正负一」，B 是换个方向的正负一。
且 2.4 已证明供给够。bot 占比由 `match_src_counts` 记账，真实数据说话。

---

## 4. 方案

1. **池子按场次分桶**：`{_seed_ver, by_battles: {"5": [...]}}`
2. **匹配只有两级**：同场次 → bot（`find_opponent(battles, …)`）
3. **拉取**保留多拉（备货），但**不再是匹配判据**
4. `bracket_for_battles` / `battles_for_bracket` / `pool_find_near` / `pool_find_window` **删净**
5. `make_bot` 收**场次**，不收档
6. 种子池 `data/ghost_seed.json` 重新生成成按场次分桶（`cohort_to_seed.py` 改写出口）
7. 把 2026-09-25 焊错的门禁判据改成「对手场次 == 我的场次」

## 9. 实施回填（做完之后，与方案对照）

### 9.1 与方案不同的地方

| 方案原本写的 | 实际做成 | 为什么 |
|---|---|---|
| 「池子按场次分桶」 | 同时**改了键名** `brackets` → `by_battles`（常量 `POOL_KEY`） | 旧名字是谎：桶里装的从来是「档」。名字不换，下一个人读到 `pool["brackets"]["3"]` 会以为 3 是档。全仓 18 处字面量里，闯关赛那处**抄错了一层**三天没人发现 ⇒ 用常量让编译器帮着数 |
| 「删 `pool_find_near` / `pool_find_window`」 | 连 `pool_find` 一起删，三合一成 `pool_find_battles` | `pool_find(pool, bracket, …, exact_battles)` 的场次只是个**可选**过滤 ⇒ 尺子有三把，谁都能挑一把顺手的 |
| 未提 | **加了一次性存档迁移** `_migrate_brackets_to_battles` | 一个字段都不缺（每条快照自带 `season_total_battles`）⇒ 重分桶是无损搬家。丢掉会连带丢玩家从 Supabase 攒回来的真人快照 |
| 「拉取保留多拉」 | 改成**只往前开**（`PULL_BATTLES_AHEAD`，`in.(N, N+1)`） | 我永远回不到 N-1 ⇒ 那一格拉回来一条都匹配不上，纯占 `PULL_LIMIT` 名额 |
| §6.2 U2「`make_bot` 数值不动」 | **动了**：新曲线由 396 条真人快照量出来 | 量完才知道旧算法在**场次 0** 那格错了 2 件（bot 带 2 件 / 真人全裸），违反「人生第一把没装备」那条锚点。其余 33/36 个场次与旧算法一致 ⇒ 不是改平衡，是修一处一直错的 |
| 未提 | `verify_bracket_gear` **改名** `verify_seed_battles_gear` | 名字里的 bracket 已无所指。同名但无关的周日对阵图门禁 `verify_bracket` 一个字没动 |

### 9.3 过程里栽的坑（都记着）

1. **两条判据一开始没红** —— 详见 §7 那张表。这是本轮最有价值的产出：
   「把 ±1 加回去」端到端**走不到那一级**，「放宽过滤那一行」落在**死代码**上。
   两条都不是脚本问题，是判据有洞。
2. **heredoc 把 `\n` 变成真换行**三次（改 Python/GDScript 字符串时）。
   memory `fb-heredoc-backslash-n-corrupts-json` 说的就是它 ⇒ 带转义的补丁一律**落盘脚本**，不写在 heredoc 里。
3. **本仓行尾是混的**：同一个文件里 `cat -A` 显示 LF，python 读出来是 CRLF ⇒
   跨行的字符串匹配连着失败三次。多行替换一律**按行**匹配或做行尾自适应。
4. **`var x := <三元表达式>`** 在本仓被当错误（"Cannot infer the type"）⇒
   表现是 rc=0、**没打 ALL PASS**、0 条 PASS，极像断言失败（CLAUDE.md §2 那个坑）。
5. **改判据要连"作废的那条"一起删**：我只替掉了旧断言的前半段，
   留下的 `ws.size() == 3` 让它继续红 —— 而红的理由已经不存在了。
