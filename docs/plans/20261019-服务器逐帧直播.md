**能从参考里带走的三件事：**

1. **结果只在服务器上成立。** 确定性的作用是让服务器能自己重放自己，不是让每台手机各算一遍。本项目的服务器裁判已经做到了这一点（x86 Linux 和 Windows 逐位一致，见上游方案书的决策记录）。
2. **客户端拿到的是服务器下发的状态。** 回放和观战用同一种数据：一段段 chunk，每隔一段放一个完整的 keyframe。拖进度、迟到入场都是「先跳到最近的 keyframe，再往后放 chunk」。
3. **只保证同一版本能看。** LoL 的回放跨版本就失效。本项目的录像本来就带版本号，周赛录像最多保留 8 天（隐私政策第 79 行），这个限制可以接受。

### 2. 现状：直播和录像传的都是**输入**，播放全靠**本机重算**

| 位置 | 事实 |
|---|---|
| `scripts/systems/replay/replay_recorder.gd:3-35` | 录像里装的是「重算这一局需要的全部输入」：`seed` + `state`（21 个 `STATE_KEYS`）+ `events`（fight / present / forfeit）+ 每 60 步一个校验点 `cps` + 终局指纹 `end`。播放就是在本机重算一遍 |
| `scripts/systems/replay/live_upload.gd:1-23`、`:115-137` | 周六直播上传的那一行 `live_matches` 里装的是 **`replay`**（到目前为止的输入录像，base64）+ **`horizon`**（打的人推进到第几步）+ `ended`。**一个画面状态都不传** |
| `scripts/systems/replay/live_spectate.gd:13-28` | 观众端写明「播 = 本机重算（与回放同一条路）」，这一层只负责决定每帧跑几步 sim。cap = horizon，跟播时落后 `LAG_STEPS` = 360 步 |
| `scripts/systems/replay/referee_watch.gd:1-17` | 服务器裁判局（周六 / 周日）：账按服务器的结果记，**画面**却是拿服务器的录像在手机上重算出来的；重算对不上就在结算屏加一行「录像无法在本设备播放」（`TXT_UNPLAYABLE`） |
| `scripts/systems/replay/replay_uploader.gd:47` | 录像 base64 的上限是 `REPLAY_MAX_B64` = 65536（约 48 KB）。这个上限是给「输入录像」定的，状态流比它大一到两个数量级 |
| `scripts/referee/referee_runner.gd:1-60` | 裁判机直接实例化完整的战斗场 `RealtimeBattle3D.tscn`，关掉 SubViewport 渲染、静音，每帧在 `referee_budget_us`（100 ms，`replay_recorder.gd:152`）预算内尽量多推几步 sim |

⇒ 现在只要 iPhone（ARM）和服务器（x86）在**任何一步**算出不同的结果，玩家看到的过程就和服务器判的不一样。校验点每 60 步比一次，所以从分叉到发现之间，屏幕上最多有约 1 秒是错的；最坏情况下，画面上已经播出一次「击杀」，而服务器那一局里这次击杀根本没发生。用户 10-19 说的「一点概率都不能出现」，指的就是这一类。

### 3. 画面和计算的耦合（这一节决定方案走哪条路）

**结论：画面不是从单位状态里读出来的；大部分演出是 sim 步在执行过程中直接造出来、直接推着走的。** 所以「把状态喂给现有渲染层就能播」这条路**只覆盖一半**。

#### 3.1 主循环里两条路分开跑

- `RealtimeBattle3DScene.gd:2091-2120` `_process`：先推 sim（`_advance_sim_accum` 按固定步长 SIM_DT = 1/60 秒，在 `:2116`），再**每帧调一次** `_render._render_step(rd, …)`（`:2120`）。
- `RealtimeBattle3DScene.gd:2140-2247` `_sim_step`：十几个羁绊和装备的 tick、`_tick_unit`、弹道、`_check_end`，最后是 **`_step_sim_tweens(dt)`（`:2245`）**，以及信号 `sim_stepped.emit()`（`:2247`，可以直接拿来当录流的挂点）。
- `RealtimeBattle3DScene.gd:2309-2325` `_reg_tween()`：**所有演出 tween 都由 sim 步按 SIM_DT 推进**，不由 SceneTree 推。也就是说，tween 推一步就是 sim 推一步。

#### 3.2 「读状态」那一半：`battle_render.gd` 的 `_render_step`（`:219-257`）

每帧做这些事，都是**根据单位字典的状态**算出来的：

- 立绘帧动画 `_update_run_anim` / `_advance_anim`（`:67`、`:96`），用 `anim_action` / `anim_t`，大熊和大师走单独的分支
- 世界坐标 `_update_world_transforms`（`:511`），读 `pos` / `height` / `_prev_pos`（用来插值）/ `face_right` / `size_mult` / `_atk_voff` 等
- 震屏 `_update_camera_shake`（`:578`）
- 跟着状态走的特效：真火（`true_fire_until`）、冰寒标记、电弧、涨潮、HOT、跟随特效、技能环、深海币、忍者标记、连笔线（`:244-253`）
- 血条、龟能条、等级牌 `_update_overlay`（`:594`）：这些是 **2D 的 Control**，每帧把单位头顶的世界坐标用 `unproject_position` 换算到屏幕上（`:674`）；`HpBar.update_state(u)` 读 `hp` / `maxHp` / `shield` 等
- 顶部 PK 条、DOT 累积数字、法术圆盘（`:255-257`）

⇒ 这一半**可以喂状态**：手机上复制出一份「单位代理字典」，填好这些字段，现有代码就能原样跑起来。

#### 3.3 「sim 里直接触发演出」那一半（全仓统计，2026-10-19）

统计范围：战斗相关的 117 个文件，包括主文件、`scripts/scenes/battle/*`、`scripts/systems/**`、`scripts/combat/*`。不算 HUD、面板、实验室、调试场、回放、音频。统计脚本是只读 grep，没有留在仓库里。

| 种类 | 调用点数 | 说明 |
|---|---|---|
| `_vfx.xxx(...)` 直接调特效 | **599** | 例：`battle_damage.gd` 16 处、`equip_system.gd` 31 处、主文件 85 处 |
| `_reg_tween()`（由 sim 推进的演出 tween） | **515** | `star_system.gd` 48、`headless_system.gd` 29、主文件 92 |
| `tween_callback(...)` | **444** | 其中**至少 46 处**在回调里结算伤害、治疗或命中（按回调后 4 行内出现 `_apply_damage` / `heal` / `_kill` / `_hit` / `dmg` 粗筛）。例：`pirate_system.gd:100`、`:130`，炮弹落地才结算 |
| `Sprite3D` / `MeshInstance3D` / `GPUParticles3D` / `Label3D` `.new()` | **496** | 节点就在 sim 调用链里当场 new 出来、`add_child` 进去 |
| `_shake` / `_add_hitstop` | **139** | 震屏和顿帧。顿帧会改 sim 的节奏（`:2192`） |
| `_float_text(...)` 飘字 | **67**（分布在 28 个文件） | **但只有一个实现**：`battle_vfx.gd:268`。它在创建那一刻用本机相机 `unproject` 算屏幕位置，跳的方向带 `randf()`（纯外观随机）。同目标同类型同一帧的伤害会合并 |

| 程序生成网格（`ArrayMesh` / `ImmediateMesh` / `SurfaceTool`） | 19 个文件 | 触手 `tentacle_vfx.gd` 每步重算网格（`:2177` 那行 tick），还有 `spirit_eq_vfx` 50 处、`synergy_vfx` 32 处 |
| 程序生成贴图（`VfxTex.` / `Image.create` / `ImageTexture.create_from_image` / `GradientTexture`） | `VfxTex.` 236 处（41 个文件）；裸 `ImageTexture` 67 处（18 个文件） | 这些贴图没有 `resource_path`，不能只传一个路径 |
| `set_shader_parameter` | 139 处（12 个文件） | shader 参数每步都在变 |
| 音效 | 实现集中在 `scripts/systems/audio/audio_system.gd` 的 6 个入口（`:27-58`） | 只有一个出口，容易做成事件 |

**可以利用的好消息：**

- 战斗 VFX 节点**没有一个自带 `_process`**（grep `^func _process` 只命中实验室、`sim_driver` 和 `ui_frame`）。也就是说，**世界里每个特效节点在某一步的样子，完全由「sim 步 + 渲染步」决定**，没有第三个时钟在推它。
- sim 步和渲染步的边界已经被门禁守着：裁判机每帧推几十到上百步、只跑一次渲染步，客户端每帧推 1 步、跑 1 次渲染步，两边逐步指纹一致（`verify_referee_job_roundtrip` 65/65）。⇒ **渲染步不影响结果**，有实测依据。（这只是间接证据，S1 要单独做一条门禁钉住它。）
- 飘字、震屏、顿帧、闪屏（`battle_vfx.gd:2881`）、音效、换路幕布（`dual_lane_flow.gd:67` / `:104` / `:148`）各自**都只有一个实现函数** ⇒ 这些做成「事件」只需要改几处。

#### 3.4 结论：播放模式选哪条路

| 路线 | 改法 | 判断 |
|---|---|---|
| A. 纯状态驱动（LoL 式：实体状态 + 语义事件，客户端自己按事件演出） | 把 599 处 `_vfx` 调用、515 个 tween、496 处 `new` 逐个改成「发事件 → 客户端演出」 | ❌ 117 个文件全要动，等于把整个演出层重写一遍；每改一处就可能有一处演出和原来不一样 |
| B. 只喂单位状态，特效照旧靠本机 sim | — | ❌ 特效靠本机 sim 产生，又回到了「本机重算」，分叉风险没去掉 |
| **C. 三层复制（推荐）** | ① **单位状态**：喂给现有渲染步和 HUD；② **sim 里生出来的世界节点**：在节点树这一层统一镜像，挂点是 `SceneTree.node_added` / `node_removed` + 每次采样时比属性差异；③ **屏幕空间事件**：飘字、震屏、顿帧、闪屏、音效、幕布、横幅，在它们各自唯一的实现函数里录 | ✅ 117 个文件不用动，改动集中在**几个总闸**上。手机上一步 sim 都不跑 |

这就是 LoL 所说的「服务器出状态，客户端照着画」，只是具体做法换成了「复制节点树」。原因是本项目的特效不是数据驱动的，是 sim 代码当场造出来的。

## 出入

- **「已有周六直播」传的不是状态，是输入**（`live_upload.gd:115-137`）。观众端照样重算（`live_spectate.gd:13`），和裁判录像有同一个 ARM 分叉风险。本方案上线后，周六观赛也要改成走状态流。
- **「服务器算一局约 45 秒」**：上游方案书实测是整进程 35 秒、10469 步，其中有启动开销。按纯算算，大约 300~350 步/秒，是实时速度（60 步/秒）的 **5~6 倍**。~~录状态流会额外花时间（要遍历节点树，未验），按保守估计还能保持在 3 倍实时以上~~ ⇒ **S0 实测推翻了「3 倍以上」**：
  - 同一进程、同一局对比（Windows 本机，无头）：10469 步那局（镜像快照）现状 1587 步/秒；真实快照池那局（8463 步，三路打满，满装备）现状只有 **321 步/秒**（5.4 倍实时）。
  - 加上最朴素的录流原型（每步遍历全部镜像节点、逐属性比）：真实快照那局掉到 **60 步/秒 = 刚好 1.0 倍实时**，追不上。
  - 只比「真的会变的 30 个属性」（白名单，见 §2.1）：111 步/秒 = **1.9 倍实时**。
  - ⇒ 边算边播**能追上，但余量很薄**，而且每局占用裁判机 CPU 的时间变成原来的 3~5 倍，排队（R4）会更严重。录流性能是 S1 的硬指标，见 R5。
  - 真正可能慢下来的另一处仍是**排队**：4 个工作线程，周六高峰可能同时有几十个人开战，见风险 R4。
- **上游方案书第 0 步「先验真机确定性」**：本方案做完以后，**周六和周日的显示不再依赖真机确定性**，那份验收（`verify_referee_device_parity`）对这两种模式就不再是前提。积分赛仍然是本机打、本机记账，本机算的就是事实，不存在「对不上」；所以真机确定性只剩**积分赛录像给别人看**这一个用途，`device_selfcheck` 那条线照常继续。
- **「一点概率都不能出现」的准确口径**：状态流能保证**屏幕上画的每一步都是服务器那一局里真实发生过的**。它保证不了的是：断网、数据传丢或损坏。这些情况下只能显示「同步中」并停住、或者整场播放失败，**绝不会改成本机重算，也绝不会显示一个不一样的过程**。这一点要写进门禁（`verify_stream_never_resim`）。

## 方案

### 0. 总体结构

```
裁判机（Hetzner，无头 Godot，与客户端同版本）
  sim 每推一步 ─ sim_stepped ─► StreamRecorder
      ├ 单位层：代理字段（只发变了的）
      ├ 节点层：sim 步里 node_added 的节点 → 建 / 改 / 删（只发变了的属性）
      └ 事件层：飘字 / 震屏 / 顿帧 / 闪屏 / 音效 / 幕布 / 横幅 / 结算
  每 60 步封一个 chunk（1 秒），每 600 步再写一个 keyframe（10 秒，存完整状态）
  → 写成文件 /streams/<match_id>/<seq>.bin，最后写 end.json
                     │  HTTPS（Hetzner 上的 Caddy，静态文件）
手机（新模式 "stream"：不跑 _sim_step）
  拉 chunk → 缓冲够 3 秒才开播 → 每帧按 60 步/秒推进播放头
      ├ 单位层 → 单位代理字典 → 现有 _render_step / HUD / 血条原样跑（在相邻两次采样之间插值）
      ├ 节点层 → 镜像节点（按 id 建、改、删，transform 插值）
      └ 事件层 → 到对应步号就调现有的唯一实现（_float_text / _shake / Audio…）
```

### 1. 服务器侧：录流（新文件，`scripts/systems/stream/`，不进主文件）

| 件 | 内容 | 估计行数 |
|---|---|---|
| `stream_recorder.gd` | 挂在 `sim_stepped` 上。**采样规则**：离散属性（显隐、帧号、贴图、文字、颜色）每步都比，变了就记；transform 和标量属性每 2 步（30 Hz）比一次 | 400~600 |
| 节点层 | 用 `get_tree().node_added`，**只认 sim 步执行期间加进 `_world` 子树的节点**（`_sim_step` 入口和出口各置一个标记）。渲染步里造的节点由手机自己按状态造，不复制，否则会重复。按类别取属性：`Node3D`（transform / visible）、`SpriteBase3D`（texture / hframes / vframes / frame / modulate / pixel_size / billboard / flip_h / offset / region / alpha_cut / render_priority）、`MeshInstance3D`（mesh 来源 + 材质）、`GPUParticles3D`（参数 + emitting）、`Label3D`、`Light3D`。材质：`StandardMaterial3D` 记常用属性；`ShaderMaterial` 记 shader 路径 + 参数表 | 300~500 |
| 单位层 | 字段名单**不靠手列**（memory「字段白名单天生会漏」）：仿照 `_gs_read_trace` 那套，给单位字典套一层读记录，跑一遍 `_render_step` + `_update_overlay` + HUD + 信息面板，把读到的键量出来。门禁每次重新量，结果必须 ⊆ 复制名单 | 200~300 |
| 事件层 | 6 个总闸各加一行 `_stream.ev(...)`：`battle_vfx._float_text`（记**世界坐标**和参数，不记屏幕坐标，因为手机的相机可能平移或缩放）、`_shake`、`_add_hitstop`、`screen_flash_light`、`audio_system` 的 6 个入口、`dual_lane_flow` 的幕布和横幅，外加结算 | 100~150（散在 6 个文件里，每处 1~3 行） |
| 渲染步对齐 | 裁判机现在每帧只跑一次渲染步（`rd` 是真实帧长）。录流模式下改成**每次采样前用 k×SIM_DT 跑一次渲染步**，让服务器上的立绘帧、跟随特效和手机上一致。`rd` 只影响画面，不影响结果，由新门禁 `verify_stream_capture_inert` 证明 | 30 |
| 编码 | `StreamPeerBuffer` 写二进制；坐标量化成 int16（步长 1/32 码，未验够不够）；整个 chunk 用 Godot 自带的 `compress(COMPRESSION_ZSTD)` 压缩 | 150 |

**长尾（S0 先量清单再逐个处理）：**

- **程序生成贴图**：在 `VfxTex` 里给生成出来的贴图记一个「出处键」（函数名 + 参数），手机按这个键重新生成。这里改 1 个文件就能覆盖 236 处。裸 `ImageTexture` 那 18 个文件逐个处理：改成走 VfxTex，或者在节点上加一个出处键 meta。
- **程序生成网格**：19 个文件。网格创建后不再变的，传「生成函数 + 参数」；每步都重算的（触手），传驱动它的那几个标量，让手机调同一个生成函数。**不传顶点数组**（太大）。
- **跟随类**（`_follow_vfx` / `_hijack_fx_attach` / `ink_links` / 金币）：它们由渲染步移动，跟随关系保存在 battle 的数组里。需要把「跟随谁」做成节点的 meta 一起传，手机端的跟随逻辑就能复用。
- **时停**：渲染步读 `_timestop` 的状态（`battle_render.gd:222-230`），把它并入单位层复制的全局字段。

### 2. 每帧要传什么

**单位层（每个单位，采样时只发变了的字段）**：`pos`、`height`、`face_right`、`alive`、`hp` / `maxHp` / `shield`、龟能相关（`energy` / `skill_cd` / `store_energy` / `rage` / `star_energy` / `bubble_store`）、`anim_action` 加动作起始步、`flash_t` / `flash_col` / 冲击姿势、`stacks`（electric / ink / crystal）、各种 `*_until` 计时（`battle_render` 用来判断状态特效的，如 `true_fire_until`、`spd_dbf_until`）、`size_mult`、`_atk_voff` / `_slam_voff` 等偏移、`side` / `_eff_side`（驯服后会变）、等级牌数字。**最终名单以读记录量出来的为准**（见上）。

**全局**：`_t`、`_sim_step_n`、`_dl_state` / 当前路 / 幕布状态、`_hitstop`、时停状态、PK 条两侧总血。

**一次性事件**：单位登场（spec 只传 id、阵营、皮肤、等级、装备图标这些**外观**信息）/ 离场、技能释放文案、飘字（世界坐标 + 文本 + 颜色 + 类型）、震屏、顿帧、闪屏、音效、换路幕布（进入、退出、内容）、横幅、终局（胜方 + 指纹）。

**数据量估算（未验，S0 实测后回填）：**

| 层 | 假设 | 原始速率 |
|---|---|---|
| 单位层 | 同时在场约 24 个单位，每次采样平均变动约 23 B，30 Hz | ≈ 16 KB/s |
| 节点层 | 混战时同时在场约 150 个特效节点在动，每个约 14 B，30 Hz；建节点一条约 60 B | ≈ 60 KB/s 峰值，平均 ≈ 20 KB/s |
| 事件层 | 飘字、音效每秒约 20~40 条 × 20 B | < 1 KB/s |
| **合计** | 一局可见时长约 150 秒 | 原始约 **3~8 MB**；ZSTD 压缩后（量化后的增量数据通常能压 3~5 倍）约 **0.8~2 MB** |

对照：LoL 一场 30~40 分钟的 `.rofl` 约 10 MB，折合 4~5 KB/s；本估算压缩后是 5~13 KB/s，在同一个量级。

#### 2.1 S0 实测（2026-10-19）

**测法**：探针 `tests/_probe_stream_s0.gd`（下划线开头，不进门禁；**生产代码一行没改**）。战斗场照常实例化（det 场景走 `DetScenarios` 同一套建场；三路局走 `RefereeRunner.run` 真入口），但关掉战斗场自己的 `_process`，由探针逐步驱动：`_phase = sim` 包住 `_sim_step(...)` 整个调用（**包括 `sim_stepped` 里醒来的协程续段**——它们在 emit 里同步执行），每 2 步用 `rd = 2·SIM_DT` 跑一次 `_render_step`（方案的「渲染步对齐」），然后采样。`SceneTree.node_added` 按相位分成「sim 步生 / 渲染步生 / 两者之外（第三条钟）生」。录流原型按 §0 三层真的写字节（varint + 量化：位置 1/128、旋转 1/1024、缩放与其它浮点 1/256、颜色 RGBA8；资源第一次出现时发定义；每 600 步一个 keyframe），每 60 步一块用 `compress(FileAccess.COMPRESSION_ZSTD)` 压缩。同时跑 20 Hz / 30 Hz / 60 Hz 三个编码器做对照。

**⑤ 对方案的影响**：
- **R1 体积没有超估 3 倍**：最重的那局压缩后 2.54 MB，是原估上限 2 MB 的 **1.27 倍**；按每个周末约 1000 场、每场 0.9~2.5 MB，约 **1~2.5 GB / 周末**，Hetzner 80 GB 盘、20 TB 流量够用，不用降采样。峰值 1 秒块 49 KB ⇒ 观看端约 0.4 Mbit/s。⚠ 真实快照只量了 1 局，S5 对拍时要再量一批重装备局。
- **R5 录流开销超过了 50% 的门槛**（朴素 81%、白名单 65%）：真实快照那局只剩 1.0~1.9 倍实时。⇒ S1 **必须**做脏标记（只看本步被 tween / 代码碰过的节点），不够再把比对搬进 C++（GDExtension），目标「最重的一局 ≥ 3 倍实时」。
- **单位层几乎不占体积**，体积全在节点层；节点层的大头是 Sprite3D 的颜色、位置、帧号三项。
- **录流挂点**：不能只挂 `sim_stepped`。同一步里在 `sim_stepped` 上醒来的协程（`lane_step()` / `_wait_sim`）还会接着建节点。录流要在 `_sim_step` **返回之后**采样（本探针就是这样包的）。

**采样频率建议**：服务器 60 步/秒不变；transform 和标量属性 **30 Hz**（每 2 步）；离散属性**逐步**（帧号跳变、显隐这种不能插值，必须准）；事件逐步、精确到步号；chunk 1 秒，keyframe 10 秒。手机端在相邻两次采样之间做线性插值（角度用 `lerp_angle`）。先按 30 Hz 做；S0 量完体积后，再决定能不能降到 20 Hz（LoL 是 30 Hz，见上表）。

#### 2.2 S1 实现：状态流格式 v1、挂点与实测（2026-10-19）

S1 录流已实现，S1 实测见下（标「S1 实测」）。代码全在 `scripts/systems/stream/`：`stream_format.gd`（格式常量、编码器、结构解码器）和 `stream_recorder.gd`（录流器）。主文件只多了 2 行事件挂点，渲染步那一行是原地改的。

**挂点**

| 位置 | 做什么 |
|---|---|
| `replay_recorder.gd` `_referee_frame` | 裁判每推一步：`stream.pre_step()` → `battle._sim_step(...)` → `stream.post_step()`。采样在 `_sim_step` **返回之后**，所以 `sim_stepped` 上同步醒来的协程续段建的节点也算这一步（S0 修正） |
| `stream.post_step()` | 每 2 步用 `rd = 2·SIM_DT` 跑一次渲染步（渲染步对齐），然后采样三层 |
| `RealtimeBattle3DScene._process` | 渲染步那行原地改成 `if _replay.stream == null:`：录流时不再按真实帧长多跑一次渲染步，服务器上的渲染状态只由「第几步」决定 |
| `RefereeRunner.run(host, job, on_battle, stream)` | 第 4 个参数非空就录流：`{"dir": 目录}` 写块文件，`{"keep": true}` 把块字节留在内存。元数据放进结果单的 `stream` 键。不传时行为和原来逐字相同 |
| `referee_main.gd` | 命令行可选 `--stream=<目录>`（或环境变量 `REFEREE_STREAM`）。只写本地文件，传输留给 S4 |
| 事件总闸（各加 1 行 `StreamRecorder.cur.ev(...)`） | `battle_vfx._float_text`（飘字）、主文件 `_shake`（震屏）、主文件 `_add_hitstop`（顿帧，只录真的生效的那次）、`battle_vfx.screen_flash_light` 和 `dual_lane_flow._dl_flash_screen`（闪屏）、`Audio.play_sfx`（音效，裁判机静音也照录）、`dual_lane_flow._dl_enter_present` / `_dl_clear_present_overlay`（换路幕布进 / 出） |

渲染步里发生的事件不录，只计数（`ev_render_dropped`），因为手机自己会跑渲染步，录了会重复一遍。

**文件布局**：一局一个目录。每块一个文件 `<目录>/<块序号 6 位>.bin`，收尾再写一个 `end.json`（元数据，含 `format` 版本号、步数、字节数、各类计数、报警计数、结果单 digest）。

**块文件**（小端）：

| 字段 | 字节 | 说明 |
|---|---|---|
| magic | 4 | `TSTR` |
| 版本号 | 2 | `StreamFormat.VERSION` = **1**。改格式必须 +1；手机只认同版本（R7） |
| 块序号 | 4 | 从 0 起，连续 |
| 首步 | 4 | 本块第一步的 `battle._sim_step_n` |
| 步数 | 2 | 60（最后一块可以少） |
| 标志 | 1 | bit0 = keyframe 块 |
| 原始长度 | 4 | 解压后的字节数 |
| 负载 | 其余 | 原始字节流整块 `compress(ZSTD)` |

**分块与 keyframe**：1 秒（60 步）一块；每 10 块的第一块是 keyframe 块，它的第一步以 `KEYFRAME` 开头，后面跟全部全局字段、全部单位（登场 + 全字段）和全部活节点（建立）。keyframe 块开头把**字符串表和资源定义表都清零**，所以从任意一个 keyframe 块往后解都解得开（拖进度、迟到入场）。同一段里的普通块要按顺序解，共用字符串表。

**原始字节流**：一条操作接一条。

| 操作码 | 名字 | 内容 |
|---|---|---|
| `0xFE` | STEP | 一步开始：sim 步号 |
| `0xFD` | KEYFRAME | 紧跟 STEP：手机清空全部镜像状态 |
| `0x06` | GLOBAL | 变了的全局字段：`dl`（双路阶段）、`lane`、`over`、`ts`（时停携带者数）；30 Hz 再加 `t`、`hs`（顿帧剩余） |
| `0x0A` / `0x0B` / `0x0C` | UNIT_NEW / UNIT_SET / UNIT_DEL | 单位登场（idx、龟 id、阵营）/ 变了的字段 / 离场 |
| `0x01` | NODE_NEW | 节点 id、父引用、类名、**与类默认值不同的**属性表 |
| `0x02` | NODE_SET | 节点 id、变了的属性 |
| `0x03` | NODE_DEL | 节点 id（手机连同子树一起删） |
| `0x04` | RES_DEF | rid、种类、按种类的内容（见下） |
| `0x08` | RES_SET | 材质这类资源的跟踪属性变了 |
| `0x05` | EVENT | 事件类型、参数表 |

父引用有四种：挂 `_world`；挂另一个镜像节点（节点 id）；挂单位外观节点（单位 idx + 单位字典里的键名，如 `sprite`）；兜底用相对 `_world` 的路径（计数 `parent_by_path`，两局实测为 0~25，随特效随机变）。

资源种类有六种。有路径的资源只传路径。参数型资源（材质、基本网格、渐变、`GradientTexture`、`AtlasTexture`）传类名和非默认属性。程序贴图只传类名和宽高。程序网格只传类名和面数。内联 shader 传源码。其它资源只传类名。**程序贴图和程序网格的出处键留给 S3**，现在手机拿到的只是占位。

值前面一个字节标签：nil / 真 / 假 / 整数（zigzag varint）/ float32 / Vector2 / 位置（1/128 量化）/ 旋转（1/1024）/ 缩放（1/4096）/ Vector3 / 颜色（1/255，允许 HDR）/ Rect2 / 字符串表引用 / 资源 rid / 其它（`var_to_bytes`）。字符串第一次出现时写全文，之后只写编号。

**采样规则**：离散量逐步比，包括显隐、帧号、贴图、`hframes`、`region_enabled`、`flip_h`、网格、粒子 `emitting`，以及单位的 `alive`、`anim_action`、`side`。连续量每 2 步比一次（**30 Hz**，U2），包括变换、颜色、`region_rect`、`offset`、`pixel_size`、材质的 `albedo_color` / `uv1_offset` 和 ShaderMaterial 的全部参数，以及其余单位字段。每个节点按类走一条手写的强类型取值路径，先比原值，变了才写。「改属性」的操作头等到第一个变化才写，没变的节点一个字节都不写。

**白名单与报警**：逐步跟踪的属性 = S0 实测的 30 种（`TRACKED`），再加上所有 Node3D 的 position / rotation / scale / visible。其余属性只在建节点时发一次（只发和默认值不同的）。之后每个 keyframe、每次删节点时，录流器把其余属性和基线按原值全量核一遍。变了就报警，计数进元数据的 `alarm`，同时记下是哪一类的哪个属性（`alarm_props`），以及第一次出现在哪一步（`alarm_first`）。**报警不为 0，说明手机上那个属性会一直停在建节点时的值**，这时要把它加进白名单，不能放着不管。

**单位层字段**：先用 S0 静态扫出来的 77 个键（`UKEYS`），另有 3 个逐步比的键（`UKEYS_STEP`）。方案要求最终名单由读记录量出来，这件事还没做，留给 S2 的 `verify_stream_render_fields`。

**S1 实测**（Windows 本机，无头。同一进程轮流跑「不录」和「录流」，各跑 2 遍取最快；探针 `tests/_probe_stream_s1.gd`）：

| 样本 | 不录 | 录流 | 比值 | 录流倍实时 | S0 白名单原型 |
|---|---|---|---|---|---|
| 裁判局 ① 镜像（10469 步） | 1583 步/秒 | 949 步/秒 | 0.60 | **15.8 倍** | 407（0.26） |

最重那局里，录流器一共花了 9.7 秒（整局 34.9 秒），分项如下：

#### 2.3 S2 实现：手机播放、格式 v2 与 parity 剖面（2026-10-19）

**一句话**：手机建一个「播放模式」的战斗场（`ReplayRecorder.mode == "stream"`），`_sim_step` 一次都不调，画面全由 `StreamPlayer` 按流驱动。门禁 `verify_stream_no_sim` / `verify_stream_parity` / `verify_stream_seek` 都绿，都做了反向验证（见下表）。**周六 / 周日还没接到它上面**（S5）。

**文件**（新代码全在 `scripts/systems/stream/`）：

| 文件 | 做什么 |
|---|---|
| `stream_source.gd` | 块来源接口（鸭子类型：`available()` / `chunk(i)` / `ended()` / `end_meta()`）。实现了 `Dir`（本地目录，每次问都看盘，边录边播也能用）和 `Mem`（内存块，`limit` 能模拟「服务器才录到第几块」）。HTTP 那个留给 S4 客户端 |
| `stream_format.gd` | 加了 `parse_chunk`：整块解成「按步排好的操作表」（播放端用）。`decode_chunk` 原样保留 |
| `stream_mirror.gd` | 节点层：按 id 建 / 改 / 删镜像节点；资源表（路径资源 load、参数资源按类名建、内联 shader 建、程序贴图 / 程序网格画占位）；跟着服务器换父节点（`@par`）；keyframe 重建；变换 / 颜色的插值与回真值 |
| `stream_player.gd` | 缓冲 → 播放头（60 步/秒 × 倍速）→ 按步应用三层 → 插值 → 自己跑一次渲染步；跳转；「同步中」/「画面无法播放」标签 |

**接线（改现有文件）**：
- `ReplayRecorder.start()`：`StreamPlayer.pending` 非空 ⇒ `mode = "stream"`、建播放器；`sim_feed` 在 stream 模式返回 0（累加器一步不推）并调 `player.advance(rd)`；`pre_step` 在 stream 模式只计数（门禁要它恒 0）；`allow_input` 一律拒。
- 主文件 **0 行增长**：渲染步那一行原地改成「录流时、播放时都不由 `_process` 跑」。arch_budget 仍是 8563。
- `battle_spawn._spawn_teams` 开头：播放模式不建单位（+2 行）。
- 事件总闸新增 3 个（各 1 行）：`battle_damage._dot_accumulate`（常驻 DOT 数字，是 sim 里直接建的 UI）、`dual_lane_flow._dl_clear_units`（换路清场）、`battle_world_builder._clear_layout_on_obstacles`（sim 里删地图摆件的唯一一处，删的位置同时进全局 `lc`）。
- `battle_damage._dot_bucket_active` 第一行：单位代理带 `@dot` 时直接用服务器算好的结果（真单位不会有这个键）。
- `battle_vfx._juice_bob_for` 的 6.0 抽成常量 `BOB_STILL_SPD`（录流器的 `@mv` 用同一个常量）。

**格式 v2**（`StreamFormat.VERSION` 1 → 2；字节语法不变、语义变了，v2 播放器播不了 v1 的流）：

| 变化 | 为什么 |
|---|---|

#### 2.4 S3 实现：长尾清零、格式 v3 与体积重算（2026-10-19）

**出处键（程序贴图 / 程序网格，选的是方案原文的「生成参数」那条路）**

- 生成方在资源上挂 meta `stream_gen = [脚本路径, 静态函数名, 参数 Array(, 每几步发一代)]`（`VfxTex.tag`）。录流器见到它就发 `RES_GEN`（格式 v3 新资源种类）：类名 + 「路径:函数」 + 参数；参数里的资源（材质 / 贴图）按 rid 先定义、写 T_RES，其余逐位精确（新值标签 `T_F64` / `T_COLF`）。手机按白名单（`res://scripts/**.gd` + 函数名 `gen_` / `_make_` / `_gen_` 开头 + 必须是 static，`StreamMirror.gen_ok`）调**同一个函数**现生成：一份实现、两端逐位相同。
- 生成函数必须是纯函数（只看参数）：`battle._world_pos` 换成逐字同式的 `VfxTex.wpos(center, ws, …)`，相机向量、时间相位、材质都当参数传；原来建网格时取随机数的一律在调用处按原顺序取好再传（随机数消耗次数与顺序不变）。
- **贴图**：`VfxTex` 的 35 个 `_make_*` 全部挂键（覆盖 91 处里的绝大多数）；其余 vfx 文件里 20 来处 `ImageTexture.create_from_image` 改成同文件静态 `gen_*` / `_gen_*`（派生自有路径贴图的传路径字符串）。不重复的贴图本来就只有一百来张、且多半有缓存，手机端再按「出处 + 参数」缓存一次。**没选「首次出现发像素」**：keyframe 要重发全部活贴图才能跳转，一个 keyframe 就要几十张图（估 200 KB 级），一块就超预算。
- **网格**，三种接法：
  1. 建一次、顶点少的：建好后 `VfxTex.snap(mesh)` 一行，把每个面的顶点数组整份当参数（只在录流时做 —— 真显卡上读回网格要等 GPU）。
  2. 建一次但顶点多、或频繁新建的（闪电连线 `BattleVfx.gen_bolt_line`、枪 / 弓 / 剑 / 法器 / 遗物 / 食物 / 毒雾 / 钩爆 / 凤凰 / 熔岩 / 水晶扫描 …）：抽成同文件纯函数 `gen_*`，参数几个到十几个。
  3. **每步原地重画**的（`clear_surfaces()` 再画：触手、触手预警带、钩爆触须 / 火球 / 病毒巢、021 绑定绳、058 炮台线、043 浪墙、090 水带、031 扫描、038 信号波、凤凰扇形、毒雾无人机翅膀尾焰）：原地画录流**看不见**（网格对象没换），改成每次新建一份赋给节点。录流器对「生成网格换成生成网格」按 30 Hz 发（可由出处键自带「每几步发一代」放慢），旧一代在服务器上已释放就在新定义里带上一代 rid，手机当场释放（每步一份的触手网格不能在手机上攒到下一个 keyframe）。
- **触手**（唯一的大头，原 S0 清单「每步重建 39672 次」）：中心线 37 个点量化成整数（相对根部 1/32 米 ≈ 0.7 屏幕像素，存相邻点之差），半径 / 颜色 / 截面朝向全由 `TentacleVfx._tent_rows / gen_tentacle_body / gen_tentacle_halo` 按 4 个状态标量现算；外发光壳与本体共用同一个参数 Array（录流写「参数别名」，一个 rid）；差分太短的点（出土那一瞬）改用解析切向并随参数发。录流里拍击 / 前摇 30 Hz、其余 15 Hz（本机画面不变，只影响流）。
- **参数差分**（格式 v3）：同一个节点的上一代本 keyframe 段发过、同一个函数、参数个数相同 ⇒ 没变的参数写 1 字节 `T_SAME`，等长整数数组逐个相减 `T_IDIFF`，等长字节数组异或 `T_BXOR`。最重局触手中心点「相邻差的逐代差」里 0 / ±1 占 65%(41 万个里 26.7 万)。

**录制侧改动**（追加，`stream_recorder.gd` 两处共 +18 行）：
- `_globals` 里 `if cont or StreamHud.wants_glob(_evs):`，逐项发 `StreamHud.glob(battle)`。
- `_unit_fields` 的采样段末尾逐个发 `StreamHud.UNIT_KEYS`（`@eq` `@hud`），比对和写法与 `@n` 相同。
- 另外在 `dual_lane_flow._dl_finish` 加了 1 行事件 `finish`（胜负 + 延时）。

格式版本号没动：只多了字段名和事件种类，字节语法不变；旧播放器把不认的键照样写进代理，但不读。

**体积**（与 `verify_stream_size_budget` 同口径；同一份 HEAD 关掉 HUD 字段做对照）：镜像局 897 312 → 906 341 B（+1.0%），最重那局 3 130 911 → 3 150 856 B（+0.6%），最大一块 +0.6 KB。原始字节里单位字段多了 24 KB（镜像局），没再压。

**收尾与退出**：播放模式不跑 sim，所以本机那条「`_dl_finish` → 结算屏」走不到。现在服务器那一局的 `_dl_finish(won, 延时)` 录成事件 `finish`；播放端顺播到那一步后，隔同样的延时出收尾。跳转时跳过了那一步 ⇒ 播到结尾时补出。
- 周六看自己那一场（`StreamWatch.current.kind == referee` 且带服务器结果）：走正常结算屏，胜负按服务器结果（与 `referee_watch.dress_settle` 同口径）。
- 其余情况：出回放收尾卡「<胜方名字> 获胜」+「返回」，**没有「再看一遍」**（状态流没有输入录像，再看一遍就成了本机重算）。
- 一进场就建 `ReplayControls`：stream 模式下只有左下角一颗「退出」（`ReplayExit`，连到 `_replay_exit`，与回放退出是同一个），缓冲 / 同步中也能退。
- 主文件 `_exit_tree` 那一行原地改成 `if _replay.is_playing() or _replay.player != null: ReplayRecorder.end_play()`（重复调用是空转；S5 的守卫节点还在，等于两道保险）。主文件行数不变（8540）。

**两处有意放宽**（都计数，都有上限）：
- 路名计时牌：本机秒数恰好压在整秒边界上的那一步，允许差一秒。原因是流里的 `t` 是 float32，本机 `_t` 是 double 累加，恰好 x.000000 时 ceil / floor 落在哪边要看末位。实测两局 3 / 315 次，判据 ≤ 5%。
- 头像框血条比例：播放端刚重建头像框、新框还没排过版的那一次渲染，只不比这一项。这一次槽宽是 0，血条按兜底宽 80 算，下一帧才按真宽 90 算；本机每次建栏那一帧也是这样，只是本机建栏和采样之间隔了一帧。实测每局 1 次，判据 ≤ 3。

**剩余风险**：
- 如果一局里本机没有左方大师，本机会建一个隐藏的圆盘，播放端则不建。门禁里两局都有大师，这种情况没量到。

- stream 模式下没有「再看一遍」，也没有「暂停 / 倍速 / 进度条」，只有「退出」。要做的话按 keyframe 跳转来做（`seek` 已有）。
- 详情面板（点单位看属性，R9 / U4）没做：点头像框能打开面板，但面板读的属性字段流里大多没有。

| 清理 | `turtle-stream-purge.timer` 每小时跑一次，删「(现在 − 1 天) 所在周的周一 00:00 UTC」之前的局目录，等于每周二 00:00 UTC 删本周一之前的 |

**传输**（`StreamSource.Http`，按 server/stream/README.md 的 URL：`<base>/<match_id>/<6 位序号>.bin`、`end.json`，请求头 `X-Client-Version`）：块按顺序一块块拉；404 ⇒ 立刻问一次 `end.json`，没有就退避重试（0.5 → 1 → 2 → 4 秒封顶，拿到一块回到 0.5），播放器自然停在「同步中」；调用方说「早算完了」而 404 连续 60 秒不消失 ⇒ `gone`（已到的块播完后停在「画面无法播放」）；426 ⇒ 版本墙回调、停；断网 / 超时 / 5xx ⇒ 同一条退避一直重试，**永远不判 gone**。`gone` / 426 时来源多报一块空字节，播放器用它已有的判据停在「画面无法播放」，播放器本身一行没改。base 默认 `https://stream.turtlearena.xyz/streams`，环境变量 `TURTLE_STREAM_BASE` 可改。

**需要服务器侧做的（本轮没碰 `server/stream/`、`server/referee/`）**：
- 上 20261019c 迁移（待用户批）；按上面「打开顺序」开录流再翻开关。
- §5 说的「v0.20.1 起的裁判局按需补出状态流」没有做：开流之前算的裁判局（同一版本内）没有流。客户端在「不知道是不是裁判局」的入口退回老路（本机重算 + 校验点对不上就停），在「已知裁判局」的入口直接说「画面无法播放」。要补，需要一个「重放录流」任务（裁判机按 `matches.replay` 重放并录流，结果确定性相同）。

**剩余风险**：
- 收尾屏：stream 模式下没有 sim，也就不会走 `_check_end` → 结算屏；周六服务器结果在 `StreamWatch.current.result`，要由 HUD 那一侧（`battle_hud` / `stream_hud`，不在本轮地盘）在播放器 `state == "ended"` 时画结算屏 / 回放收尾卡。在那之前，播完停在最后一帧，只能按退出离场。
- 主文件 `_exit_tree` 只在 play 模式调 `end_play`；stream 模式靠守卫节点。建议主会话把那一行改成 `if _replay.is_playing() or _replay.player != null:`（守卫重复调用是空转，`_has_backup` 判过）。
- 同一局重录（失败重领）会换一份流：已缓存旧块的手机会解到对不上的后续块 ⇒ 停在「画面无法播放」（server/stream/README.md 已列）。

- 真机未验：iPhone 上 HTTPS（ATS）、HTTP/2 / HTTP/3 下 `HTTPRequest` 的表现、2.5 MB 一局的下载时间都没量（验收「iPhone 真机」那一条）。

**低帧率飘字与 DOT 数字（第 7 项 + 截图验收）**：事件层没有丢（一帧推多步照样逐步放全部事件），是**三个各自独立的根因**，都用探针打出具体数值定的：
- ① **播放端渲染步跟着手机帧率走**（探针 `tests/_probe_float_cadence.gd`：最重那局同一份流按「一帧推 K 步」播，改前 K=1 2430、K=2 2415、K=3 2422，原生 2415）。渲染步里按状态冒东西的是头顶常驻 DOT 数字：桶结束 ⇒ 弹射成一条伤害飘字、下次从 0 记（`battle_render._update_dot_floats`）。服务器每 2 步跑一次渲染步，`@dot` 也只在采样步更新；手机一帧一次渲染步 ⇒ 60 帧（一帧一步）时在采样步之间拿旧的 `@dot` 判成「结束」⇒ 数字提前飞走、从 0 重记 —— **这就是截图里播放端 DOT 数字小 4~14 的原因**；一帧 3~4 步又会把中间采样步上的「结束」跳过。修法（`stream_player.gd`）：`_apply_paced` 一帧推多步（≤ `PACED_MAX_STEPS` 16）时每越过一个采样步就在那一步跑一次渲染步（时长按上次渲染以来的播放头补，总时长不变；一帧最多越过一个采样步时与原来逐字相同；超过 16 步当快进；seek 不走这里）；`at_sample`：渲染步只在落在采样步上时才判「桶结束」（`_update_dot_floats` 读它），采样步之间只挪位置。
- ② **原生端本身就不确定**（探针 `tests/_probe_native_float.gd`：同一局裁判每帧预算 100 ms / 1 ms，原生飘字 2416 / 2418，`get_stack` 定位到冰霜领域每 0.5 秒一跳的 `_ice_frost_tick` 伤害飘字）。伤害飘字「同目标同类型 0.04 秒内合并」只看 `_t`，而换路幕布期 `_t` 不走 ⇒ 整段幕布期的冰霜跳伤能并进几个数字，取决于上一个数字的飞行 tween（按真实时间）还活没活着、排队释放落在哪一帧 ⇒ 机器快慢不同条数就不同 —— **CI 那个 2422 是这一条**。修法（`battle_vfx._float_text`）：合并再加「2 步内」的步号窗（`_float_clock()`：本机 = sim 步号，手机 = 播放器正在应用的那一步 `cur_step`）；排队释放中的数字不再合并 / 累加 / 弹射（`_float_text` / `_dot_accumulate` / `_update_dot_floats`）。改后两种预算都是 2461（原生条数从 2415 变成 2461：幕布期的冰霜跳伤不再被随机并掉，本机打也一样，纯画面、不碰 sim）。
- ③ **播放端合并步号差一步**：事件放的时候用「已应用到」的步号（上一步）⇒ 服务器并掉的一跳在手机上单独冒出来（2461 / 2462）。改成 `cur_step`（这一步）。
- 改后：最重那局原生 2461 条（裁判预算 100 ms / 1 ms 相同）；播放端一帧 1 / 2 / 3 / 4 / 8 步全部 2461 条、首处不同 = 无；DOT 数字采样点上 352 个单位·点（一帧 1 步 740 个）全部相同。镜像局 598 / 598（一帧 1 / 3 / 4 步）。
- 门禁（`verify_stream_parity`）：采样点上逐单位比头顶 DOT 累计数字（最重那局 352 个单位·点，分母 > 0）；每局再按一帧 1 / 3 / 4 步各播一遍（与引擎每帧调 `advance(K·SIM_DT)` 同一条路），飘字序列与原生相同（步号容差 2 + K）、DOT 数字在采样步上与原生相同（K=1 比 740 个单位·点），分母：播到结尾、一帧真推了 K 步；最重那局再用裁判每帧预算 1 ms 原生录一遍，飘字序列必须与 100 ms 那遍逐条相同（②的判据，只看原生）。`verify_stream_hud_parity` 没加（DOT 数字不是 HUD 层的东西，挂在单位上，parity 的单位快照里比最直接）。

**兼容性结论（v0.21.0 录流器 / 播放器都在线上）**：
- 格式版本**不升**（仍是 v3）。改属性操作本来就是「属性名 + 值（资源引用 / 普通值）」，播放端按名字 `set`（`StreamMirror._apply_node_props`，与 tag v0.21.0 逐字相同）：
  - 新录流器 → v0.21.0 播放器：多出来的 `vframes` / `material_override` 改动它照样认（`vframes` 在设帧号之前、帧号最后设，那段逻辑 v0.21.0 已有）；少掉的 `emission_intensity` 本来就是默认值。能播、画面更对。
  - v0.21.0 录流器 → 新播放器：照旧能播；只是少了这两项变化（就是现在线上的样子），`emission_intensity` 那几百条日志照旧有（只是日志，不影响画面）。
  - 播放端节奏修正（`_apply_paced` / `at_sample`）只改手机这边什么时候跑渲染步，不碰流的字节 ⇒ 播谁录的流都一样。
- 新的 SQL（20261020）全是添加 + 给只读函数多回一个键；客户端读不到（没上）⇒ 404 ⇒ 与改之前相同（赛况板只有直播行、补流请求 ⇒「画面无法播放」）。轮询器补流在服务端 404 时本进程不再领。

### 5. 录像

- **裁判局（周六、周日）的录像 = 状态流本身。** 赛后回看和观赛用同一份 chunk 文件，进度条按 keyframe 跳。这和 LoL 一样：回放和观战是同一种数据。
- `matches.replay`（输入录像）**照常保留**：它是服务器复核和调试的依据，相当于 LoL 的 SNR。手机不再用它重算周末的局。
- **旧录像**：
  - v0.20.1 起的裁判局：裁判机上还装着 0.20.1，可以**按需补出状态流**。第一次有人点开时排一个「重放录流」任务，算一次就缓存下来。
    - **2026-10-20 已补（§4.2 第 5 项，SQL / 轮询器只写仓库文件、未上生产）**：客户端请求补流 → 裁判机用原快照 + 种子重算只录流 → 手机「画面生成中」等块。裁判局从此永不本机重算。
    - **S5 实际（2026-10-19）**：「重放录流」任务没做（要服务器侧）。客户端按 §4.1 处理：已知裁判局（周六 / 周日自己那一场）没有流 ⇒ 不播也不重算、屏上「画面无法播放」；不知道是不是裁判局的入口（赛况板 / 战绩页 / 别人的格子）没有流 ⇒ 当本机局走老路。录像版本与本机不同的照旧被版本闸挡住。
  - 更早的 0.19.x 本机局：保留期最多 8 天，**自然过期**；在这之前仍然走本机重算，对不上就照旧显示「录像无法在本设备播放」。不补。
  - 积分赛：结果本来就是本机算的，录像（给别人看的那份）仍然走重算；那条线由真机确定性（`device_selfcheck`）守着。
- 隐私政策要补一句：录像 / 状态流存放在 Hetzner（德国），保留期和现在相同。
