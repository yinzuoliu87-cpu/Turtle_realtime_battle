### 1.2 ★第一个坑：不动产品代码的话，这一条**天生是空跑**

`battle_debug_arena.gd:80` 对 `side == "right"` 一律 `u["active_skills"] = []`——
右队是「不动不打」的假人。而龟壳【复制】的池子是**从敌人身上读 `active_skills`**。

```
实测: 右队 5 只龟, 可抄池 = 0        ← 判据怎么写都恒绿
```

⇒ 场景表 pairs 加第 6 项 `foe_skills`：为 true 时调**产品自己的**
`battle._resolve_active_skills(id, false)` 把真实主动技恢复回去。
**不许在表里手写技能名**（memory `fb-hand-rolled-copies-drift`）。恢复后实测 **可抄池 = 5**。

> 这一维现状调查没写到：它只查到「`shell` 在任何确定性门禁里都不在场」，
> 没查到「就算摆进去，池子也还是 0」。**“摆进去”和“量得到”是两件事。**

### 1.3 ★第二个坑：第一版摆位把龟壳**打死了**

第一版右队挑的是 `basic/ninja/candy/two_head`（四个**伤害技**）。
`foe_skills` 一开，这四只假人就会放技能 ⇒ 实测龟壳 **hp=0 / 只抄到 1 次 /
后 900 步指纹冻住**（`uniqFp` 1200 步只有 336 个）。

改成五只**非伤害技**的龟（石壳 / 竹疗 / 钻石固守 / 泡泡盾 / 水晶壁障）：

| | 第一版（伤害技） | 定稿（非伤害技） |
|---|---|---|
| 可抄池 | 4 | **5** |
| 龟壳结局 | **hp 0 / 死** | hp 1028 / 活 |
| 复制施放 | 1 次 | **3 次** |
| 不同指纹 | 336 / 1200 | 320 / 1200 |

抄到盾/治疗**照样进指纹**（`_fp` 记 hp 与 shield）；而「1 次」时两遍恰好抽到同一对的
概率是 1/12，「3 次」把它压到千分之一以下。

### 1.4 必配的分母（**量的是产品自己的账**）

现有三条（步数 / 指纹随步变化+承伤>0 / 建过 tween）之外加两条：

```
[PASS] 分母 · ⑩ · 可抄池 ≥ 2(实测 5 个可抄技·用 CopyRules.can_copy 过的活敌人技)
[PASS] 分母 · ⑩ · 两遍都真的放过【复制】(A 3 次 / B 3 次, 都须 ≥ 1)
```

- **可抄池**：用产品的 `CopyRules.can_copy(st, battle._IMPL_SKILLS)` 过一遍**活着的右队**的
  `active_skills`。池子 < 2 时「洗牌」无可洗，改坏了也不会红。
- **施放次数**：数 `u["skill_cd"]["shellCopy"]` **抬头**的次数 ——
  那是 `RealtimeBattle3DScene.gd:2618` 在 `_cast_skill` 成功之后写的，**不是我插的标记**。
  （先试过数「龟能掉 ≥100」：**行不通** —— 本作的龟能模型就是冷却本身
  （`skill_energy.gd` 头注：「冷却 与 龟能充能 是同一回事」），单位上没有一个会掉下来的
  `energy` 字段，所以那一版探针数出来恒为 0。**猜字段名会静默数成 0**，
  memory `fb-guessed-field-name-silently-zero`。）
- 哪些场景要这两条，判别靠**摆位里有没有 `shell`**，不另立名单（名单会烂）。

## 2. 任务 B：`tests/verify_sim_step_rate.gd`

### 2.1 判据形状

同一份摆位 + 同一 `TURTLE_SEED`，**唯一变量是每帧喂几个 sim 步**：
A 遍 1 步/帧 × 600 帧；B 遍 k 步/帧（k=2/3/4）。
指纹**按 sim 步号 `_sim_step_n` 对齐**（不按帧号），在两遍都采到的步号上逐个比。

驱动方式把现有两份门禁各缺的一半都补上：

| | 现有 | 本判据 |
|---|---|---|
| 每帧步数 | det 恒 1 步 | `set_process(false)` + 自己喂 `_advance_sim_accum(k×SIM_DT+1e-9)`，**恰 k 步** |
| 协程 | `_interactive` 纯同步喂、**一帧都不 pump** ⇒ 14 处协程全程挂着不动 | **每帧之间 `await get_tree().process_frame`** ⇒ 协程真的醒 |
| tween | —— | `TURTLE_SEED` 设着 ⇒ `_deterministic=true` ⇒ tween 由 `_step_sim_tweens` 按 sim 步喂。**不这样不行**：交互模式 tween 走 SceneTree 真实 delta，两遍墙钟不可能一样 ⇒ 判据会因为 tween 快慢而红，跟 k 毫无关系 |

`+1e-9` 的理由写在文件头：`3 × (1/60)` 的浮点值会差一点点进不去第三步，
实测会跑出 2/4/3 的抖动而步号对不齐。丢掉的余量无所谓（sim 永远只按整 `SIM_DT` 步走）。

### 2.2 两条分母（都量产品自己发布的量）

```
[PASS] 分母 · 协程真的在推进: 忍者冲击(协程位移)命中并写过 `_ninja_dash_until` 的单位 2 个 > 0
[PASS] 分母 · k=2 真的生效(单帧最大步数 2 == 2; `_frame_sim_dt` 峰值 0.03333 == 0.03333)
[PASS] 分母 · k=2 的帧数 300 ≈ 基准 600 的 1/2(=300, 容差 ±2)
```

- `_ninja_dash_until` 由 `ninja_system.gd:149` 在 `_ninja_glide` 这个
  `await process_frame` 协程把 `traveled` 推到命中投影时写，**有两个产品读者**
  （`battle_render.gd:411` 画锁定标记、主场景 `:6831` 选靶）⇒ 它为 0 就说明协程压根没动。
- 摆位里双头龟与目标隔 **200 码**（炮弹射程内）——场景表 ④ 的注释踩过：
  隔 580 码时弹丸在窗口内飞不到，「什么都没发生」在两遍之间是一样的。

### 2.3 ★★结果：**红**，而且红得就是现状调查预言的那个形状

```
分叉汇总: k=2: 全部 294/300@14 · 其中【结果字段】268/300@66
          k=3: 全部 196/200@15 · 其中【结果字段】179/200@66
          k=4: 全部 147/150@16 · 其中【结果字段】134/150@68
首个分叉的那一段: 0/ninja/left:901.000:330.00:300.00  ≠  0/ninja/left:901.000:320.00:300.00
```

**分叉要分类，否则「98% 步分叉」会被误读成「结果全乱了」**：

| 类 | 量 | 含义 |
|---|---|---|
| **相位** | sim 步 **14/15/16** 起 | 只有 `pos` 不同。协程一帧把整帧的量一次加完 ⇒ 同一 sim 步上它在路上的位置不同（忍者 x：基准 320 / k=2 330 / k=3 340 / k=4 350，差值恰好 `600×(k-1)×SIM_DT`）。总位移仍 = 速度 × 总 sim 时间，跑完会追平 |
| **结果** | sim 步 **66/66/68** 起，268/179/134 步 | `hp / 存活 / 护盾 / 龟能` 真的不一样。协程那些 `if traveled >= h["proj"]` 的判定**只有帧粒度** ⇒ **命中落在不同的 sim 步** |

**所以这不是「把判据改绿」的事，是 B2/B4 本体（把 14 处协程搬进 sim 队列）的事。**
按现状调查条目 1 的改动面：14 处 / 5 个文件，`_wait_sim` 一处改 25 个消费者一起对，
**且会动玩法数值**（小熊 `bear.frame >= 3` 的伤害时刻、宽刃命中顺序 ±1 步）。
不在本轮范围内。

### 2.4 为什么没有「强行改绿」，`run-tests.sh` 又是绿的

照 `verify_determinism_cross.gd` 的 `KNOWN_DIVERGE` 同一条纪律：
**存量记进台账 `KNOWN_GAP`，只减不增**。台账里每条带实测数，并且有两道反向闸：

1. 实测分叉数 **>** 台账 ⇒ 红（有人又往协程里塞了一处按渲染帧推进的东西）。
2. 实测分叉数 **== 0** ⇒ **也红**，报「台账过期，删掉那一行」——
   台账不许当垃圾桶，谁把协程搬进 sim 队列就得来清账（memory `fb-gate-can-pin-the-bug-in-place`）。
3. 比对步数 `n` 必须等于台账记的那个（分母被砍也红）。

每轮都把三行 `[台账]` 实测数打在日志里，不是静默豁免。

## 3. 已知风险与未决点

1. **⚠ `KNOWN_GAP` 的三组数是本机（Windows）实测，CI（Linux）没验过。**
   驱动是全受控的（恰 k 步/帧、det tween、钉死周锚点），理论上与机器快慢无关，
   但**我没有 CI 结果**。CI 上对不上**不要放宽台账**，去看为什么——
   那本身就是新信息（memory `fb-ci-vs-local-divergence`）。
2. **⑩ 的 cross 金标只在 Windows 生成过。** CI 第一次跑它可能进 `KNOWN_DIVERGE`
   那一类（像 ③ 场景的浮点末位）。真出现就按那边的台账纪律记，别改金标。
3. **场景 ⑩ 给两根长杆各加了 1200 步**（`verify_determinism_b` 本机 123 秒、
   `_cross` CI 132 秒，它们是测试池排队尾巴的长杆）。实测 `_b` 本轮 47 条全绿。
4. **`foe_skills` 这个开关只有 ⑩ 在用。** 它改变的是「右队假人有没有主动技」，
   也就是说 ⑩ 这一局的右队**会放技能**（非伤害技），与其余 9 条的「不动不打假人」不同形状。
   这是有意的（否则池子为 0），但它意味着 ⑩ 覆盖的是**另一条**路，不要拿它当
   「右队假人那 9 条也验过了」。
5. **本轮没做**：现状调查条目 1/2/4 的本体（协程搬进 sim 队列、38 处 tween 结算分家、
   四处难点按 sim 步排队），条目 3 的工具侧（`rng_discipline.py` 加
   `.shuffle(` / `.pick_random(` / 战斗路径分预算），条目 5（`GameState.battle_seed` 入口）。
   任务只要 A、B 两条。
6. **工作区里有 1138 个 `.import` 文件被标成 modified**：这个 worktree 是新开的、
   没有 `.godot/`，跑测试前必须先 `--import`（否则 `class_name` 全局解析失败、
   音频资源加载报错，表现是 `RB.DEBUG_EDIT = true` 直接 `Invalid assignment`）。
   `git diff` 对这些文件**输出为空**（只是行尾归一化的状态差），内容没变。
   （memory `fb-import-ok-is-not-runnable` 的邻居：**没 import 过的 worktree 连 import 都没跑过**。）
