## 2. 根问题（不是三个 bug，是验收标准失效）

用户报的三件分属三份方案书，**都标着「已完成」、都有验收清单、当时全套绿**，
而用户一上手三件全是坏的。

诊断：**「已完成」是我自己宣称的，不是被证明的。** 同一个形状这一夜出现了十次：

> **门禁绿了，但它证明的是我的实现，不是用户的需求。**

最典型的一例：v0.19.141 凤凰的门禁断言 `u["_phx_onhit_n"] == 1` ——
那是我自己插进去的计数器，**插一行再数一行，必绿**。
它证明「我调了 `_eq_on_hit`」，不证明「竹制弓箭真的射出去了」。

## 3. 调查：怎么定位的

这一夜没有一个根因是「读代码推出来」的 —— 读代码这一夜错了四次
（008 珊瑚刺读到过期注释 / 以为 on-hit 坏了其实一直是通的 /
以为 4 件法器是死件其实是我没喂够帧 / 以为面板不刷新其实是读错字段）。

**全部靠探针打数值定位**，举三例：

- **凤凰复活**：反向验证时打出 `alive=false hp=0` —— 与用户描述的现象逐字相同。
- **香火「20 刀也是 0」**：探针打出「存档 20 道 / 局内 `_marks["left"] = 0`」，
  一眼看出是**没加载**而不是没生效。
- **089 符纸不到期**：探针打出 `el=2.48`（我推了 17 秒 sim 时钟），
  当场排除「符纸永久贴着」这个我差点报出去的假 bug。

## 9. 实施回填 —— 十条教训

1. **判据要量需求，不是量我的实现。** `_phx_onhit_n` 是我插的标记，插一行数一行必绿。
2. **反向验证过 ≠ 判据可靠。** 还要看**裕度**与**重复跑是否同向**——
   031 的裕度只有 0.14（其余是 505~19620），CI 上就翻转了。
3. **判据不稳时先换一个裕度大的量**，别调阈值。~1 的噪声 → ~1300 的伤害，问题自己没了。
4. **尺子必须匹配被测对象用的时钟。** 089 符纸的 `el` 跟真实帧走，我推 sim 时钟推了 17 秒它才 2.48。
5. **对照组要和实验组同时跑。** 前后两段窗口的时相不同，漂移本来就不一样。
6. **哈希/队列长度/节点计数不是判据。** 「能变就行」的量，变了不代表发生了我要的事。
7. **0 == 0 也是「相等」。** 「★1 与 ★3 一样」在两个都是 0 时恒成立，必须先断言非零。
8. **别拿输入当输出。** 我传 20000 伤害，实发 24000（走了增伤）——先打分母再定判据。
9. **★发了 12 个版本一篇方案书都没写。** 用户要求的正式化流程是
   「需求 → 方案书 → 拍板 → 实现 → 门禁 → 版本号 → push」，我这一夜跳过了第 2 步。
   补写不等于没欠——下次新需求先写方案书再动手。
10. **量不到 ≠ 坏了。** 这一夜我三次差点把好装备判成死件（022 没喂够帧、037/040 判据字段漏了、
    031 判据选错层），全是我的测量问题。**别把「我没配对环境」报成「效果有问题」。**
