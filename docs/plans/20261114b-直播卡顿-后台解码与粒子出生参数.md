# 直播卡顿 · 后台解码 + 粒子只发出生参数

日期：2026-11-14　|　状态：**实施中**

## 1. 需求原文

用户 2026-11-14：

> 「我朋友…单杀王那个账号，然后打我，就是路易斯零一的那个账号那场对局，他手机上看，然后发现卡卡的」

查完给出三件事的计划（石头龟岩脊逐步碰撞 / 击退统一抛物线 / 直播卡顿：先后台线程解码，再粒子只发出生参数），用户：

> 「做吧」

## 2. 调查结论（现状）

- 那一局 = 闯关赛 referee job 8653（seed 54440829414211），130 秒 / 130 块；服务器 70 秒算完、直播 17 KB/s ⇒ 不是服务器、不是数据量。
- 按手机播放路径本机重放（`tests/probes/_probe_stream_perf.gd`，无头 `--fixed-fps 60`）：数据块交界那一帧（步号 60 的倍数）中位 22.7 ms、最慢 90 ms；其它帧中位 1 ms；超过 16.7 ms 的 80 帧里 77 帧在交界。单独解码（`PERF_DECODE_ONLY=1`）每块中位 19.8 ms、最慢 90.9 ms —— 对得上。
- 根因：`StreamPlayer._tick` → `_pump` → `_decode` → `StreamFormat.parse_chunk`（`scripts/systems/stream/stream_player.gd` `_decode`）在主线程一帧里解完整块（1 秒 60 步）；手机 GDScript 慢几倍 ⇒ 每秒卡一下。
- 043 海浪第三版（11-14 进 main）的粒子：`tide_vfx._tfx` 每颗是一个 Sprite3D，运动全是游戏钟的函数（`battle_render._tick_anim_fx`），但录流器把每颗的位置 / 缩放 / 颜色 30 Hz 逐采样写进流 ⇒ 同一局 8 秒带浪 173 KB、不带 25 KB（`tests/probes/_probe_stream_043.gd`），解码也跟着变慢。

## 3. 需求 ↔ 代码的出入

| 应该 | 现在 |
|---|---|
| 解码不占播放那一帧 | 块交界那一帧在主线程解完整块 |
| 客户端能算的粒子运动客户端算（LoL 等也是客户端算粒子） | 服务器把每颗粒子每 1/30 秒的状态写进流 |

## 4. 方案

**A. 后台解码**（`stream_player.gd`）：主线程每接上一块，就把**下一块**交给 `WorkerThreadPool` 解（字符串表顺着传一份深拷贝；每次只在途一块）。播放中只有「这一帧真要播到的那几步 + 插值要的下一个采样」必须当场解（`need_now`，后台正在解这一块就等它），其余只取后台已经解好的、没好就下一帧再看；缓冲 / 同步中 / 跳转 / 跳开场仍按原来的 want 当场解（画面本来停着）。追上了才停的判据不变：能拿到的块里，这一帧要播到的那几步一定已经解好 ⇒ 只有块真没到才「同步中」。跳转先丢掉在途那块。没有线程的平台（`OS.has_feature("threads")` 为假）与 `STREAM_SYNC_DECODE=1` 走原同步解码。

**B. 粒子只发出生参数**（`stream_format.gd` / `stream_recorder.gd` / `stream_mirror.gd` / `battle_render.gd`）：`_anim_fx` 里带 `p0` + `life` 的记录（= `tide_vfx._tfx` 造的粒子）在建节点 / keyframe 整份重发时带一个伪属性 `@afx`（18 个双精度：t0 / fps / n / base / life / p0 / vel / grav / s0 / s1 / a0 / a1 / show_at / 标志位）；之后它的变换 / 颜色 / 帧号 / 显隐不再进流（同「主人活着的单位外观」那条先例：缓存跟着走）。手机镜像见到 `@afx` 就把同样一条记录登记进战斗场的 `_anim_fx`（带 `keep`：寿命到了只停止驱动，节点等流里的删除），由手机自己的渲染步按同一个函数算。格式版本不升：旧播放器不认 `@afx`（`Node.set` 未知属性不做事，已实测不报错），粒子停在出生位置；新播放器播旧流照旧（旧流没有 `@afx`）。

都是播放 / 录流侧，不改对局结果、不升规则版本。

## 5. 已知风险与未决点

- 旧客户端看新流：043 浪的粒子停在出生位置直到删除（不报错、不影响别的画面）；过审后强制更新即消失。不升格式版本的代价就是这一条，换来新客户端照样能播旧流。
- 手机算粒子与服务器同一个函数、同一个全局 `t`（双精度进流），采样点上逐位相同；两次采样之间手机按插值的 `t` 连续算（比原来按 30 Hz 插值更顺），不再是逐采样的线性插值。
- 后台线程只碰自己那份字节和字符串表拷贝（`parse_chunk` 是纯函数）；播放器释放时等在途那块收完。

## 7. 决策记录

- 11-14 用户「做吧」：按 §4 做，先 A 后 B，一批推（都是直播侧，与击退 / 岩脊那批分开）。
- 11-15 实施时发现：第一版「主线程每接上一块就把下一块交给后台、需要时取结果」只救得了回放；**跟播直播**时缓冲只有 3 秒，新块一到就落进 want ⇒ 照样在主线程当场解。改成播放中按 `need_now` 分「必须当场解」与「后台解好再取」（§4 A 已按改后写）。

## 8. 实施回填（2026-11-15）

改动：`scripts/systems/stream/stream_player.gd`（`_DecodeJob` / `_prefetch` / `_bg_take` / `_pump(want, need)` / 计数 `chunks_bg` `sync_playing`）、`stream_format.gd`（`AFX_KEY` / `afx_is` / `afx_pack` / `afx_unpack`）、`stream_recorder.gd`（`_afx_of`、`_node_new` 带 `@afx`、`_samp` 粒子当渲染步管）、`stream_mirror.gd`（`_afx_reg`）、`battle_render.gd`（`_tick_anim_fx` 认 `keep`）；新门禁 `tests/verify_stream_tide_particles.gd`。

实测：
- **卡顿**（正式服 job 8653 那一局，`_probe_stream_perf` 无头 `--fixed-fps 60`，同一份代码只切 `STREAM_SYNC_DECODE`，同一时段跑）：块交界那一帧 中位 32.6 → **2.3 ms**、最慢 143.5 → **14.9 ms**；交界处超过 16.7 ms 的帧 86 → **0**；全程超过 33 ms 的帧 67 → 3（剩下 3 帧是开打建场 291 个节点、换路建场，与解码无关，另记）。临时诊断：播放全程 `_pump` 超过 3 ms 的只有开播缓冲那一次（8.5 ms）。
- **数据量**（043 3★ 一局 8 秒，`verify_stream_tide_particles`）：173 KB → **58 KB**（不带 043 约 25 KB）；手机按出生参数登记粒子 567 颗，逐采样点比对（节点 id / 显隐 / 帧号 / 贴图 / 变换 / 颜色 / 普查 / 飘字）全过。
- 两次跑同一局录出来的字节数差几十字节（58109 / 58136）：预算留了约 25% 余量，不按字节数卡。
