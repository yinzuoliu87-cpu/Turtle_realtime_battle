## 1. 需求原文

2026-09-22，我报了「周末三天无限刷」那个洞（已修，v0.19.428）并问了两件事：
配额 24 场要不要调高、周末玩法要不要开始做。

> **「不用改。开始做」**

⇒ ① `RANKED_QUOTA = 24` **保持不动**（写进决策记录，别再问第二遍）
⇒ ② 开始做周六闯关赛 / 周日决赛日

### 原稿里已经写死的规则（逐字，不要再问一遍）

**闯关赛（周六，23:00 截止）**

> 赛制：4 胜晋级 / 3 负出局。不排对阵表、全天自由开打，每人 4~6 场，3 分钟一局，总投入约 20 分钟。
> 匹配：严格同标签 —— 只有战绩标签完全相同者互配（3-1 只碰 3-1）。同标签 ⟹ 同场数 ⟹ 周六内供给完全一致；
> 兜底链：同标签真人排队 → 同标签新鲜快照（30 分钟内）→ 机器人。**永不跨标签**；
> 每场照常结算深海币（**无命**，公式退化为固定数 8）+ 经验 2 + 货架刷新。
> 配额补发（与积分赛同构，只发晋级者）：闯关配额 = 6 场；4-0 补 2 场、4-1 补 1 场、4-2 不补；
> 每场补 8 币 + 2 经验；x-3 出局者不补。

**周六资格**

> 种子前 **30%** 晋级，**≥13 胜** 无条件保送；比例线随人数自伸缩。

**决赛日（周日）**

> 上午·分桶赛：无签到、全员自动入场；按种子蛇形切成 32 人单败桶（人数不整则高种子轮空）；
> 快照代打；桶内逐轮同步推进：3 分钟备战购物 → 系统瞬间结算 → 全桶观看 3 分钟战斗重放；蛋碎即出局；
> 桶内逐轮发放对称轮次币并刷新货架；约 40 分钟后各桶产生桶冠军。
> 晚上·冠军签表：20:00 开赛，全部桶冠军补轮空进最近的 2 的幂签表，单败打到决赛；
> 每轮：购物 → 结算封存 → 1 分钟押注截止窗口 → 全服同步开播 3 分钟重放。
> **奖励**：冠军/亚军/四强/…/桶冠军逐档，**只发头衔/称号**（跨大轮永久保留）。

**母方案书里已拍板的补充**（2026-09-16 三轮问答，不要重复问）

### 2.2 ★不在位的，以及为什么它是硬的

| 缺口 | 说明 |
|---|---|
| **`ghosts` 表没有战绩标签维度** | 主键是 `(account_id, season_week, battles)`，匹配索引是 `(season_week, battles, uploaded_at desc)`。周六要按 **`(胜-负)` 标签**撮合，这张表答不了。需要**新表**或**加列 + 换主键**（换主键要迁移，表里已有真数据）。 |
| **周日的「同步轮次」后端做不了** | 原稿的分桶赛是**全桶同步**：3 分钟购物 → 系统瞬间结算 → 全桶一起看重放。这要一个**服务端赛程推进器**（定时触发、给每个桶配对、算结果、广播）。现有后端是 **Supabase + 异步快照**，没有这个东西；而 Edge Functions **我的后台令牌没有权限部署**（见 [[project-backend-supabase]]）。 |
| **前 30% 晋级线要收盘终榜** | 离线版现在只有硬线 ≥13 胜。真的前 30% 需要在周五 23:00 那一刻对全服排名 —— 有后端之后**可以做**，但要写服务端排名（一条 SQL / 一个 RPC）。 |
| **头衔系统** | D12 定了四档，但**代码里没有任何头衔字段**（跨大轮保留的只有 `install_uid`、龟等级、历史战绩）。 |
| **观赛 / 重放** | 零。属 F 阶段。 |

### 2.3 ★命名撞车（必须先说）

`GameState` 里已经有一整组 `dungeon_*` 字段，注释写的是「**闯关**进度（单次冒险，不持久化，失败重置）」——
那是**深海闯关**（5 关 PvE 冒险，另一个已有功能），和周六的「闯关赛」（瑞士轮式淘汰赛）**完全无关**。

⇒ 本篇一律用 `gauntlet_*` 指周六赛事，**不许**用 `dungeon_*`；
UI 文案上也要想清楚：玩家会不会把「闯关赛」和「深海闯关」当成一回事。

## 3. 与现状最大的一处出入：**人数**

原稿的三个量级是 **1,000 / 10,000 / 100,000 人**，整套规则（前 30%、32 人桶、蛇形切桶、
226 桶冠军进 256 签）都是按这个尺度写的。

**现在的真实人数**：sideload 测试包，测试者**个位数**。

这不是"以后再说"的事，它当场决定两件：

1. **周六资格线**：硬线是 **≥13 胜**。而一周 24 场配额 + 8 命 ⇒ 要拿 13 胜至少得打 13 场、且输不超过 8 场。
   **现实是：测试者很可能一个都到不了 13 胜 ⇒ 周六池空 ⇒ 闯关赛做出来没人能进。**
   （前 30% 那条线在个位数人口下也没意义：3 个人的前 30% 是 0.9 个人。）
2. **周日分桶**：U3 已定「≤16 人 → 16 人桶，再少依次减半（8 / 4）」，所以 3 个人 → 4 人桶 + 轮空。
   结构上成立，但「全桶同步看重放」在 3 个人时体验是什么，得想清楚。

## 4. 方案

拆成两步，**因为它们的技术前提完全不同**：E-A 现有后端就能做，E-B 需要服务端赛程推进器。

### E-A　周六闯关赛（异步，现有后端可落地）

| 步 | 内容 | 落点 |
|---|---|---|
| E-A1 | **资格**：`promoted`（已在位）+ 可选的服务端前 30% | `GameState.settle_ranked_close()` |
| E-A2 | **战绩标签**：`gauntlet_wins/losses` 从死字段接活；标签 = `"W-L"` | `GameState` + 结算 |
| E-A3 | **进/出局判定**：4 胜晋级 / 3 负出局 / 6 场配额封顶 | `phase2_config` 新常量 + `GameState` |
| E-A4 | **同标签匹配**：新表 `gauntlet_ghosts`（PK `account_id, season_week, gw, gl`）+ 兜底链 | `server/supabase/schema.sql`、`supabase.gd`、`backend.gd` |
| E-A5 | **周六结算口径**：**不掉命**；每场固定 8 币 + 2 经验 + 货架刷新 | `RealtimeBattle3DScene._settle_season()` |
| E-A6 | **闯关配额补发**：4-0 补 2 / 4-1 补 1 / 4-2 不补；每场 8 币 + 2 经验；出局者不补 | `GameState`（与 A7 同构） |
| E-A7 | **UI**：主菜单周六态（战绩 W-L、距晋级/出局几场、配额剩余）、进/出局的话要说得准 | `MainMenuScene` |
| E-A8 | **开关**：`WEEKEND_MODES_LIVE` 翻成 `true` 的**前提**是 E-A 全部就位 | `phase2_config.gd:97` |

### E-B　周日决赛日（需要服务端赛程推进器）

原稿要的是**全服同步**。现有后端做不到。两条路：

- **B-1 等服务端**：写 Edge Function（赛程推进器）+ 定时触发。
  ⚠ 我的后台令牌**没有 Edge Functions 权限**，要你在 Supabase 面板上给权限或自己部署一次。
- **B-2 异步降级版**：周日也按周六那套异步打（单败 5 轮，对手从同轮次快照池取，轮次由客户端按 UTC 时刻推进）。
  能立刻做、离线也不退化；代价是**没有"全桶同时看重放"的现场感**，而那正是原稿里周日的灵魂。

**我的建议：先做 E-A，周日等 E-A 跑通、真有人打到周六之后再定。**
理由：周日的价值全在"同步现场感"，而那件事在个位数人口下本来就不成立；
先把周六做出来，也能拿真实数据回答「资格线该多少」。
