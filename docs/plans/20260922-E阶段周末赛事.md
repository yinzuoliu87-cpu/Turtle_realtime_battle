### 原稿里已经写死的规则（逐字，不要再问一遍）

**闯关赛（周六，23:00 截止）**

> 赛制：4 胜晋级 / 3 负出局。不排对阵表、全天自由开打，每人 4~6 场，3 分钟一局，总投入约 20 分钟。
> 匹配：严格同标签 —— 只有战绩标签完全相同者互配（3-1 只碰 3-1）。同标签 ⟹ 同场数 ⟹ 周六内供给完全一致；
> 兜底链：同标签真人排队 → 同标签新鲜快照（30 分钟内）→ 机器人。**永不跨标签**；
> 每场照常结算深海币（**无命**，公式退化为固定数 8）+ 经验 2 + 货架刷新。
> 配额补发（与积分赛同构，只发晋级者）：闯关配额 = 6 场；4-0 补 2 场、4-1 补 1 场、4-2 不补；
> 每场补 8 币 + 2 经验；x-3 出局者不补。

**周六资格**

> 种子前 **30%** 晋级，**≥13 胜** 无条件保送；比例线随人数自伸缩。

**决赛日（周日）**

> 上午·分桶赛：无签到、全员自动入场；按种子蛇形切成 32 人单败桶（人数不整则高种子轮空）；
> 快照代打；桶内逐轮同步推进：3 分钟备战购物 → 系统瞬间结算 → 全桶观看 3 分钟战斗重放；蛋碎即出局；
> 桶内逐轮发放对称轮次币并刷新货架；约 40 分钟后各桶产生桶冠军。
> 晚上·冠军签表：20:00 开赛，全部桶冠军补轮空进最近的 2 的幂签表，单败打到决赛；
> 每轮：购物 → 结算封存 → 1 分钟押注截止窗口 → 全服同步开播 3 分钟重放。
> **奖励**：冠军/亚军/四强/…/桶冠军逐档，**只发头衔/称号**（跨大轮永久保留）。

### 2.2 ★不在位的，以及为什么它是硬的

| 缺口 | 说明 |
|---|---|
| **`ghosts` 表没有战绩标签维度** | 主键是 `(account_id, season_week, battles)`，匹配索引是 `(season_week, battles, uploaded_at desc)`。周六要按 **`(胜-负)` 标签**撮合，这张表答不了。需要**新表**或**加列 + 换主键**（换主键要迁移，表里已有真数据）。 |
| **周日的「同步轮次」还没做** | 原稿的分桶赛是**全桶同步**：3 分钟购物 → 系统瞬间结算 → 全桶一起看重放。这要一个**服务端赛程推进器**（定时触发、给每个桶配对、算结果、广播），现有后端是 Supabase + 异步快照，没有这个东西。<br>★★**2026-09-23 更正**：原文写「而 Edge Functions 我的令牌没有权限部署」——**那句话是我推理的，从来没试过**。实测：Edge Functions 确实 403，但 **`pg_cron` 能用 SQL 装**（1.6.4，实测装上→排任务→回读 active→撤干净），而 SQL 权限一直都有 ⇒ **赛程推进器用数据库定时任务就能做，不需要 Edge Functions，也不需要用户去开任何权限。** |

| **头衔系统** | D12 定了四档，但**代码里没有任何头衔字段**（跨大轮保留的只有 `install_uid`、龟等级、历史战绩）。 |
| **观赛 / 重放** | 零。属 F 阶段。 |

### 2.3 ★命名撞车（必须先说）

`GameState` 里已经有一整组 `dungeon_*` 字段，注释写的是「**闯关**进度（单次冒险，不持久化，失败重置）」——
那是**深海闯关**（5 关 PvE 冒险，另一个已有功能），和周六的「闯关赛」（瑞士轮式淘汰赛）**完全无关**。

⇒ 本篇一律用 `gauntlet_*` 指周六赛事，**不许**用 `dungeon_*`；
UI 文案上也要想清楚：玩家会不会把「闯关赛」和「深海闯关」当成一回事。

## 3. 与现状最大的一处出入：**人数**

原稿的三个量级是 **1,000 / 10,000 / 100,000 人**，整套规则（前 30%、32 人桶、蛇形切桶、
226 桶冠军进 256 签）都是按这个尺度写的。

**现在的真实人数**：sideload 测试包，测试者**个位数**。

这不是"以后再说"的事，它当场决定两件：

1. **周六资格线**：硬线是 **≥13 胜**。而一周 24 场配额 + 8 命 ⇒ 要拿 13 胜至少得打 13 场、且输不超过 8 场。
   **现实是：测试者很可能一个都到不了 13 胜 ⇒ 周六池空 ⇒ 闯关赛做出来没人能进。**
   （前 30% 那条线在个位数人口下也没意义：3 个人的前 30% 是 0.9 个人。）
2. **周日分桶**：U3 已定「≤16 人 → 16 人桶，再少依次减半（8 / 4）」，所以 3 个人 → 4 人桶 + 轮空。
   结构上成立，但「全桶同步看重放」在 3 个人时体验是什么，得想清楚。

拆成两步，**因为它们的技术前提完全不同**：E-A 现有后端就能做，E-B 需要服务端赛程推进器。

### E-A　周六闯关赛（异步，现有后端可落地）

| 步 | 内容 | 落点 |
|---|---|---|
| E-A1 | **资格**：`promoted`（已在位）+ 可选的服务端前 30% | `GameState.settle_ranked_close()` |
| E-A2 | **战绩标签**：`gauntlet_wins/losses` 从死字段接活；标签 = `"W-L"` | `GameState` + 结算 |
| E-A3 | **进/出局判定**：4 胜晋级 / 3 负出局 / 6 场配额封顶 | `phase2_config` 新常量 + `GameState` |

| E-A5 | **周六结算口径**：**不掉命**；每场固定 8 币 + 2 经验 + 货架刷新 | `RealtimeBattle3DScene._settle_season()` |
| E-A6 | **闯关配额补发**：4-0 补 2 / 4-1 补 1 / 4-2 不补；每场 8 币 + 2 经验；出局者不补 | `GameState`（与 A7 同构） |

| E-A8 | **开关**：`WEEKEND_MODES_LIVE` 翻成 `true` 的**前提**是 E-A 全部就位 | `phase2_config.gd:97` |

### E-B　周日决赛日（2026-09-23 重写）

#### 技术前提：**不缺权限，只缺工时**

原文写「要 Edge Function，而我的令牌没权限，得用户去后台开」——
**那句话是我推理的，一次都没试过**，而且已经跟用户说了好几轮。逐条实测之后：

| | |
|---|---|
| Edge Functions | ✗ 403（这条属实） |
| 跑 SQL | ✓ |
| **装 `pg_cron 1.6.4`** | ✓ 装上 → 排任务 → 回读 active → 撤干净，7/7 |

⇒ 赛程推进器 = **`pg_cron` 定时任务 + `security definer` 函数**，全在数据库里，
一行 Edge Function 都不用，也不需要用户开任何权限。

#### 界面：**单独的桶界面 = 一张可拖动的对阵图**（用户 2026-09-23 定）

用户原话：「周日有单独的桶界面，是一个大的可拖动地图」；形态在两版里选了
**抽象对阵图（清爽）**——标准单败对阵树，左→右逐轮，节点是卡片（头像 + 战绩），
拖动 + 缩放。（另一版「画成真的场地地图、16 个小擂台向中央收拢」**没选**，
理由是现在大概率只有 4 人桶、3 场对局，先花大美术量做 32 个擂台可能根本没人走到那个规模。）

★★**这张图顺手解决了「重放/开播按钮放哪」**：不用放——**每一场对局自己就是按钮**，点哪场看哪场。

四个必须解决的硬问题：

| # | 问题 | 做法 |
|---|---|---|
| ① | 32 个节点里**找不到自己** | 开图**自动居中到你那一场**；角落钉一个「回到我」，拖多远都不跑。出局后变两个：「我止步在这」+「看当前轮」 |
| ② | **不能剧透**（原稿：观众观看时不知结果） | **一轮之内不翻面**：整轮打完 + 下一轮配对公布时，上一轮才统一翻面。当前轮节点只写「待开播 / ▶ 你的这一场」，点开看才知道结果 |
| ③ | **代打回来要能补看**（周日中午打开，已经被代打 3 轮 —— 这是常态不是意外） | 走过的路径连着画出来，**按顺序补看**，看完一场下一场亮起 |
| ④ | **形状会变**（U3：桶容量随人数自适应 32/16/8/4，人数不整高种子轮空） | 对阵图按任意 2ⁿ 生成；**人少时自动缩放填满屏幕**，不硬留白。现在真跑起来大概率是 **4 人桶 = 3 场对局** |

#### 用词：写「开播」，不写「直播」也不写「回放」

原稿是「**物理上是回放，体感上是直播**」。那两个词在 UI 上**都不能用**：
写「直播」是假话（它就是回放）；写「回放」会泄露"已经打完了"，把体感毁掉。
⇒ 一律写「**开播**」：「第 4 轮 14:20 开播」。它只承诺"到点能看"，不承诺实时 —— 既不骗人，也不剧透。

## E-B4 快照代打（2026-09-25）：先说清楚**它不做就一定会死**

### 调查（以代码与 SQL 为准，不是推测）

查 `finals_entrants.snapshot` 这个字段**谁写、谁读**，查出一条必然发生的死锁：

| # | 事实 | 出处 |
|---|---|---|
| ① | 快照**写进去了** | `backend.gd:549` → `finals_enter(p_snapshot)` → `finals_pending` → `finals_seat` 抄进 `finals_entrants` |
| ② | 快照**永远读不回来** | `finals_view` 下发的 entrants 只有 `seed / name / account_id`，**没有 snapshot**；`finals_entrants` 表也没给客户端 select 策略 |
| ③ | 读不到对手阵容 ⇒ **没法替不在线的人打**，那一场就没人报结果 | `finals_report` 只能由桶内的人报 |
| ④ | 没结果 ⇒ **那个桶永久卡死** | `finals_advance` 的 `if got < want then continue`。注释写的是「宁可晚一分钟」，**但它没有上限** —— 不是晚一分钟，是永远 |

⇒ **周日只要有一个人不在线，他那个桶就再也动不了。** 这不是风险，是必然；
而测试期人数是个位数，周日晚上「双方都不在线」几乎是常态。

★这正是本仓 [[fb-write-without-reader-and-fake-gates]] 那一族：生产侧写了、消费侧没读，
两边代码**单看都对**。E-B3 的 56 条服务端探针全绿，因为它们从没问过「拿得到对手阵容吗」。

### 方案

**① 对手快照：一次一个，不是全桶下发**

不能把整桶的 snapshot 塞进 `finals_view` —— 那等于把**所有人的阵容**发给所有人
（既是剧透也是侦察优势，与 E-B2 定的「不剧透做在数据层」直接冲突）。

新增 `finals_opponent(p_week, p_bucket, p_round, p_seed)`：客户端说「我认为本轮对手是几号种子」，
服务端只校验**它查得到的部分**（调用者在不在这个桶、轮次对不对、别问自己），
然后把那一个人的 snapshot 给它。

★★**关键约束：每人每轮只能问一个种子**（新表 `finals_scout`，主键
`(week, bucket, round, account_id)`，先到先得）。这一条让「把全桶挨个问一遍」
**在不写第二遍对阵规则的前提下**变得不可能 ——
问错了只是浪费掉自己这一轮的唯一一次机会，**骗人只坑自己**。
这样服务端仍然不需要知道谁打谁（E-B3 定的「对阵规则不在 SQL 里写第二遍」保持不变）。

**② 双方都没打：补判，不是等**

`finals_advance` 加一道**宽限期**：本轮开了超过 `finals_round_sec() × 2` 还缺结果，
就把缺的那几场按 **`winner_side = 0`（上半区晋级）** 补上，然后照常翻面。

★为什么是「上半区」而不是「高种子」：服务端**算不出**第 N 轮某一场里是谁 ——
算得出就等于在 SQL 里写了第二遍对阵规则。而「side 0」它不需要知道任何对阵规则：
缺哪个 `match_no` 就补哪个。
★第一轮里**上半区恰好就是高种子**（座次表 `[0,7,3,4,1,6,2,5]` ⇒ 每场 0vs7 / 3vs4 / 1vs6 / 2vs5，
side 0 全是更高种子）；后续轮它是**上半区那条路径**，不保证是当时的高种子。**照实说，不吹成「高种子晋级」。**
★宽限期取 2 倍而不是 1 倍：`finals_advance` 每分钟才叫一次，
且真有人在打时最后一场可能压着点报上来 —— 1 倍会把正在打的比赛判掉。

## E-B6 让对阵图真的往前走（2026-09-25）

### ★先说清楚这**不是**原稿那个格式

原稿的分桶赛是**同步**的：3 分钟备战购物 → 系统瞬间结算 → **全桶一起看 3 分钟重放**。
这一节做的**不是**它，是「点开你那一场 → 现在就打 → 把结果报上去」——
**异步、没有购物阶段、没有同步开播**。

为什么先做这个：E-B1~E-B5 全部就位之后，周日仍然**一步都走不动** ——
`finals_report` 这个 RPC 从 2026-09-23 就在服务端，而**客户端一个调用者都没有**，
也就是说**没有任何一场比赛的结果能被报上去**。对阵图永远停在第 1 轮，
补判（E-B4）会把每一场都判给 side 0 —— 冠军是一个从没打过的人。

⇒ 这一节的目标只有一个：**让一场真实打完的比赛，结果能进对阵图。**
同步赛制（购物 + 全桶同看）是另一块，**不在本节**，也不假装做了。

### 最容易错的一处：`winner_side` 不是「谁赢」，是「哪一侧赢」

`finals_report(p_winner_side)` 收的是 **0/1 = 这一场的上半/下半**，不是账号也不是种子。
所以客户端必须自己算「我在这一场的哪一侧」，再和「我赢没赢」组合：

```
winner_side = my_side          (我赢了)
winner_side = 1 - my_side      (我输了)
```

★这个映射**反了也不会报错** —— 它会静静地把对手送进下一轮，而屏幕上一切正常。
所以判据要卡的是「**我输了的时候报的是对手那一侧**」这个形状，不是「报了就行」。
★`my_side` 的算法已经在 `_i_won()` 里有一份（`(seat % span) / (span / 2)`），
**抽出来共用，不抄第二份**（[[fb-hand-rolled-copies-drift]]）。

## E-B7 决赛日的结算口径与购物窗（2026-09-25）

### ★先划清：原稿那三段里，有一段**不在本期**

原稿的一轮是「3 分钟备战购物 → 系统瞬间结算 → **全桶观看 3 分钟战斗重放**」。
最后那段**属 F 阶段**（D13 白纸黑字：「周日同步开播 …… 属 **F 阶段**，不在本篇」）。

⇒ 本节做前两段 + 经济口径，**不做重放**。
⚠ 后果要说清楚：一轮 480 秒里，打完到翻面之间会有一段**空窗**——
那正是重放该占的位置。**这是已知的、F 阶段填的坑，不是忘了。**

### 现状（探针实测，不是推测）

拿 `tests/_probe_finals_settle.gd` 三个阶段各输一场：

| 阶段 | 命 | 币 | 积分赛配额 |
|---|---|---|---|
| **finals** | 8 → **7** | 17（积分赛公式） | 0 → **1** |
| gauntlet | 8 → 8 | 8（固定） | 1 → 1 |
| ranked | 8 → 7 | 17 | 1 → 2 |

★**这不是 bug**：`PHASE_MODE_LIVE[FINALS] = false` 时决赛日**按积分赛规则**，
正是当初修「分流给没做的模式＝开后门」时定的（[[fb-branch-to-an-unbuilt-mode-is-a-backdoor]]）。
⇒ 本节要做的是**把决赛日那条分支写出来**，并且**必须自己带上 `phase_mode_live` 这道闸** ——
不带的话它现在（FINALS 还是 false）就会立刻生效。

### 规则（原稿逐字 + 我定的数）

原稿 §四 那两句，抄下来免得下次又去翻：

> 桶内逐轮发放**对称轮次币** ⚙ 并**刷新货架**；全桶同步 ⟹ 场次与供给天然锁死
> **快照代打**……**轮次币、货架刷新、经验一切照常发放** —— 唯一区别是无人做购物调整和摆位微调

⇒ 三条硬规则：
1. **不掉命**。单败淘汰里「输」= 出局，不该再扣赛季的命（与周六同构）。
2. **对称轮次币**：同桶同轮**人人一样**，不看输赢。★这一条是「对称」两个字的全部含义 ——
   按输赢给钱就不对称了，而**输的人下一轮根本不存在**，给差价毫无意义。
3. **不在线 / 轮空的人一样发**（原稿逐字）。⇒ 发钱这件事**不能只挂在"打完一场"上**。
   ⚠ 本节只做「打完那一场」这一半；**轮空与代打的补发挂在 `ensure_season` 上**，
   与积分赛/闯关赛补发共用同一套幂等记账 —— **那一半本节不做，记在风险表 R-B7-2**。

**轮次币取多少**：原稿**没给数**。我定 **8**，与周六 `GAUNTLET_COINS_PER_MATCH` 同值 ——
理由：两者都是**无命模式**，周六那个 8 正是原稿说的「公式退化为固定数」，
决赛日没有理由比它高或低。要改就改常量，不改公式。

### 购物窗：跟服务端的轮次时钟走，不看本机时钟

`finals_view` 已经给了 `round_at` / `next_at` / `now` 三个数。
购物窗 = `round_at` … `round_at + FINALS_SHOP_SEC`（180 秒 = 原稿的 3 分钟）。

★做成**纯函数** `finals_shop_open(round_at, now)`，理由同 `phase_pending_note`：
只写在屏幕里，门禁就只能量"此刻"那一格，其余时段全是空检查。
★**不看本机绝对时钟** —— 用服务端给的时间差（与倒计时同一条纪律，`parse_finals` 那里已经踩过）。
