## 1. 需求原文

- 用户 2026-10-19：「需要强制最低版本，而且我们的所有对局不应该在本机上吧，应该放服务器上吧，其他游戏怎么做的」
- 用户 2026-11-01（主会话问「要不要把积分赛搬上服务器」时的回答）：「我就问你一句话：哪个商业游戏是这么本地做的？你见过吗？」
- 用户 2026-11-01（同日已实现、未发版的另一件）：「我们不应该有什么这种本地排名，我们这个游戏就一定要是要联网的，就是不可能说断网还可以匹配，断网可以打，这是肯定不行的，不能有什么这种本地。」

主会话转述的目标（**主会话的话，不是用户原话**）：积分赛照商业游戏做 —— 服务器挑对手、裁判机算、服务器记账（胜场 / 命 / 周榜 / 币 / 场次等一切进排名或经济的数据），客户端只交阵容、看直播、显示服务器给的结果；客户端再也写不进积分赛成绩；陪练号走同一条路；规则不许变，只换「谁来算、谁来记」。

## 3. 需求 ↔ 代码的出入

1. **「服务器挑对手」与客户端池子不是同一个候选集**：客户端只看得到拉回来的最新 300 份 + 内置陪练；服务端看得到本周全部同场次快照 + 同一份内置陪练。规则（同场次、等概率、合法性筛、回落只有机器人）原样搬过去，候选集从「本机缓存的那一部分」变成「全部」—— 这正是用户 10-08「抽签范围扩大到全部同场次」的本意。
2. **「排除最近 8 个对手」**：客户端排除的是 ghost_id，而 ghost_id 带场次后缀（`_b<N>`）⇒ 换了场次就不是同一份，实际只在同一场重打时起作用。服务端排除「本周积分赛碰过的对手键」，键同样带场次（`acct:<账号>:b<N>` / `seed:…` / `bot:…`），口径相同。
3. **快照池里那一份的内容**：老路是客户端打完再传一份（等级 / 斧头进度是打完 +2 经验、+15 砍伐之后的）；新路是服务端写回那一刻用**开战交的阵容** + 服务端账本的数 + 结果单里宝箱 / 香火石的终值写进去，大轮等级 / 斧头进度是开战那一刻的（晚一场）。阵容、装备、站位一模一样。见 U3。
4. **深海币钱包仍在存档里**：服务器算出这一局发多少（含铸币、出局清零），客户端照数入账；钱包本身（商店花钱、补发）不在本篇。周六 / 周日服务器局一直是这个信任级别。见 U4。
5. **晋级（11 胜）仍按本机胜场线**（`GameState.settle_ranked_close`）：本机胜场从此是服务器账本照抄的，所以按的已是服务端的数；但周六进队（`gauntlet_queue_join`）服务端不查积分赛胜场。见 U5。

### 4.4 容量测算

| 量 | 数 | 来源 |
|---|---|---|
| 一周积分赛局 | ≈ 286 × 16 + 真人约 160 ≈ **4700 局 / 周**（周二 ~ 周五） | 陪练号规模 + 2.3 |
| 现行峰值 | **105 局 / 小时**（p95 63、平均 50） | 2.3 |
| 裁判产能 | 2 个 worker ≈ **240 局 / 小时** | 任务给定 |
| 峰值占用 | 105 / 240 ≈ **44%**（平均 21%） | |
| 每周裁判 CPU | 4700 × 25 秒 ≈ 33 核时（摊到 4 天 ≈ 0.34 核） | |
| 陪练号客户端省下的 CPU | 原来每局本机算约 44 秒 CPU（`project-server-bot-accounts-1026`）⇒ 一周约 56 核时不再在客户端跑 | |

结论：**按现在的陪练号节奏，2 个 worker 够，不用加机器、不用改 WORKERS**；同机 CPU 总量反而下降（一局在裁判上约 25 秒，原来在陪练号客户端上约 44 秒）。
会变的地方：陪练号若设 `SIM_SKIP_WATCH=1`（不看直播），一局墙钟从 130 ~ 150 秒降到约 60 秒，6 个同时打 ⇒ 需求可到约 360 局/小时 > 240 ⇒ 裁判一直满载、陪练号自己等结果（不丢局）；真人的局由 ⑩ 排在陪练号前面，最多等正在算的那两局（≤ 42 秒）。真要更快可把 `WORKERS` 调到 3（配置，不花钱；同机陪练号 CPUQuota 300% 要一起看）；真人周峰值超过约 100 局/小时再考虑换配置（花钱，先问用户，价格以 Hetzner 控制台为准）。见 U2。
