- 说明写「宝箱龟**造成的伤害**」，代码只算直接伤害（F）——用户拍板持续伤害也算，按说明改代码。
- 权威文档 / 说明都写「一大轮累计」，服务器局实际不累计（A）。

## 4. 方案

**B~G（客户端，战斗内）**：战斗场里按左右两侧各记一本「本场宝箱账」（不挂单位字典，换路不丢）：起点左方取存档、右方取快照基数；在两条伤害路径（`_apply_damage_from` / `_apply_damage`）伤害发生那一刻记账（F、G 一起解决，不改 `dmg_dealt` 含义）；开箱 tick、清点财宝治疗、局内财宝条三处统一从一个取数函数读；换路时敌方按账回装；只有计分对局才写 GameState（E）。新门禁 `tests/verify_chest_ledger.gd`。

**A（服务器局回写）**，照战斗内铸币 `coins / coins_b` 的现成通路（`20261020c` / `20261020d`）：
1. `referee_runner.gd`：结果单加 `chest`（左方 A 本局结束时的累计财宝值 + 已开列表）与 `chest_b`（右方 B，周日）。取数走 B~G 的取数口。
2. 服务端：`referee_complete` 存的是整份结果单（去掉录像），**不用改**；新迁移 `server/supabase/migrations/20261022b_referee_chest.sql` 重定义 `referee_job_status`（以 20261020c 版为底，多回 `chest`）与 `referee_finals_coins`（以 20261020d 版为底，按 A / B 回 `chest` / `chest_b`）。
3. 客户端：`referee_net.gd` 解析两个回包里的 `chest`；`RefereeWatch.settle`（周六）与周日取铸币处把它写进存档。写法：财宝值取 max(本地, 服务器)，已开列表取较长的那份（服务器那份是从本地交上去的进度起算的，正常情况下就是服务器那份）。
4. 部署：内测服先执行迁移、装新版本裁判程序彩排；再上正式服；裁判机装新版本 + 登记 `referee_versions` + 机器人池（README「发版时」五步）。

## 5. 已知风险与未决点

1. ⚠ **A 只对新版本客户端生效**：裁判机按玩家的客户端版本算（`/opt/turtle/v<版本>/`），旧版本的服务器局仍不回写。要跟一次发版（升版本号 + 出包），发版需用户点头。
2. ⚠ B~G 会改变带宝箱龟的对局结果（敌方不再丢件、持续伤害计入）⇒ 确定性金标 `data/determinism_cross.json` 可能要更新；新旧客户端对同一局算出的结果不同 —— 但裁判机按客户端版本选同版本算，不会跨版本比对。
3. ⏳ 写回时机：必须在下一场交阵容之前写进存档，否则服务器下一场仍从旧值起算。现有流程是先等结算再进下一场，待验。
4. ⏳ 对局进行中刚好跨周的边界未测（审计没测到）。
5. ❓ 机器人快照的宝箱进度恒为 0（`backend.gd:454-455`）—— 设计口径，不在本次范围。

## 6. 验收标准

- B~G：`tests/verify_chest_ledger.gd` 逐条（B 跨路不丢 / C 财宝条显示累计 / D 敌我同值同回血 / E 调试场不写存档 / F 持续伤害计入 / G 阵亡后计入 / 我方本机结果不变），每条配分母并做变异验证（改坏 ⇒ 红）。
