### 058 的新名字和效果本来就对得上

它的效果原文第一句就是「登场时召唤一座不可移动的**炮台**」——
叫「远古炮台」比「穿甲遗弹」更贴，**现在那张 `pierce-shell.png` 才是对不上题的那个**。

### 036 现在是纯定额，没有百分比那一半

`_tick_hotspring` 只做 `battle._damage._heal(u, ps)`，`ps` 是逐星定额。
新公式要加 `+ 0.3/0.8/1.2% 最大生命`，**这一半现在完全不存在**，是新增。

★`heal_ps` 有两个写入点（`equip_stats_apply` 正常路径 + tick 里的兜底现算），
**两处都要改**，只改一处会出现"正常对局对、合成单位错"或反过来。

### ★036 的两个坑，都在实现里处理了

1. **`heal_ps` 有两个写入点** —— `equip_stats_apply.gd`（正常路径）与 `equip_tick_system.gd`（兜底现算）。
   各写一份数就必然漂 ⇒ 常量收到 `HOTSPRING_FLAT` / `HOTSPRING_PCT` **一处**，两边都引它。
2. **百分比那一半不能写进 `heal_ps`** —— `heal_ps` 是登场时算一次的，而 maxHp 会被装备/羁绊改。
   写进去等于把百分比**冻在开局那个血量**上。⇒ 百分比在 tick 里按**当前** maxHp 现算。

### 门禁 `verify_eq058_036_045` 九条

★036 的判据**拿两种血量各量一次**（1000 / 6000）：只用一种的话
「定额 2 + 0.3%×1000 = 5」和「定额 5 + 0%」给出同一个数，两种实现分不开，
把百分比那半删掉门禁照样绿。（同族：上一轮"多件取最大"就是因为测试数据让两种行为同解才成了假门禁。）

实测六组逐个对上：1★/1000=5 · 1★/6000=20 · 2★/1000=13 · 2★/6000=53 · 3★/1000=22 · 3★/6000=82。

反向验证三条全红：删掉百分比那半 → 两条同时红；定额改回 5/7/10 → 红；百分比写错一档 → 红。

### 老门禁 `verify_equip_batch_20260801` ③ 段同步改了

它钉的是 036 的**旧需求**（纯定额 5/7/10），全套跑出来当场红 —— **这是它该做的事**。
改成钉新需求，两条并存：`heal_ps` 只存**定额那一半**（百分比那半跟当前 maxHp 走、不进 heal_ps），
走 tick 量到的是**两半之和**。只留前一条的话，百分比整半删掉照样绿。
拿产品变异反向验证过：删掉百分比那半 → 三档全红；定额退回 5/7/10 → 六条红。

顺带把 `tools/mutate_verify.py` 的第二只眼修了：判据从"相对 HEAD 无改动"改成
**"还原后的 `git diff` 正文 == 变异开始【前】那一刻的 `git diff` 正文"** ——
干净文件基准是空串、带预期改动的文件基准就是那些改动本身，一条判据管住两种情况。
拿不到 git 结果返回 `None` 显式降级，不拿空串冒充"干净"。
**已拿打瘸版工具（跳过写回那一步）证明它会红**，而且会把没还原的那一行直接打出来。
