## 2. 调查

### 2.1 现在的周日为什么会「两边都赢」

服务端**一场都不打**：只有一张 `finals_results` 表等客户端来报。
A 和 B 各自在自己机器上跑的是**两场不同的对局**：

| | A 机上 | B 机上 |
|---|---|---|
| 左队（活的） | A 的真阵容 | B 的真阵容 |
| 右队 | B 的**快照** | A 的**快照** |
| 种子 | A 这台的 | B 这台的 |

`finals_report` 是 `on conflict … do nothing`（先报的算），后报的那份**静默丢掉**且仍返回
`ok: true`；而那个客户端的 `finals_settle(won)` **一个字都不看服务端答复**，已经发过币、
加过胜场、播过胜利屏。⇒ 不是竞态，是「服务端结算 + 重放」整块没做时的必然结果。

### 2.2 已经有的部分

| | 状态 |
|---|---|
| 一切随机走种子化 PRNG | ✅ 基本做到：sim 路径用 `_battle_rng`；剩下的裸 `randf` 都在演出侧（飘字抖动/火花） |
| 固定步长 | ✅ `_deterministic` 模式每帧恰跑一步 `SIM_DT`；tween 由 sim 步喂（`custom_step`） |

| 服务端结算 + 重放存档 | ❌ 一行没做（B 阶段） |

### 2.3 ★为什么必须实测，静态扫答不了

IEEE-754 **只**保证 `+ − × ÷ sqrt` 逐位一致（它们要求正确舍入）。
**不保证** `sin / cos / tan / atan2 / pow / exp / log` —— 那几个是各家 libm 各自的近似实现，
差一个 ulp 就够让一局分叉。

全仓 sim 路径上确实在用（2026-09-26 扫，已排除 `*_vfx.gd`）：

| 文件 | 处数 |
|---|---|
| `RealtimeBattle3DScene.gd` | 31 |
| `star_system.gd` | 20 |
| `hookbomb_system.gd` | 17 |
| `chest_system.gd` / `headless_system.gd` / `signal_wave_system.gd` | 11 / 10 / 10 |
| `phoenix` / `hiding` / `equip_system` | 9 / 9 / 9 |

★**但原始计数虚高**：逐条看下去，绝大多数是住在 system 文件里的**演出代码**
（`wisp.position = battle._world_pos(center + Vector2(cos(a), sin(a)) * r, h)` 这种），
不进指纹。真正喂到 **sim 状态**（`u["pos"]` / 伤害 / 索敌）的只有这几处：

| 位置 | 干什么 |
|---|---|
| `rocket_system.gd:93` | `uu["pos"] = base - aim * (5.0 * sin(t * PI))` —— 直接写单位坐标 |
| `star_system.gd:755` | `oc["pos"] = c + Vector2(cos(ang), sin(ang)) * rr` —— 环绕体坐标 |
| `RealtimeBattle3DScene.gd:5758` | `u["pos"] = u_start - dir * (18.0 * sin(p * PI))` —— 攻击后仰 |
| `RealtimeBattle3DScene.gd:6510` | `var to = u["pos"] + Vector2(cos(ang), sin(ang)) * SPIKE_FLY` —— 弹道终点 |
| `cyber_system.gd:152` | `var cand = u["pos"] + Vector2(cos(aa), sin(aa)) * 200.0` |
| `crystal_system.gd:318` | `atan2` 吃两只单位的坐标 |
| `shell_system.gd:440` / `hiding_system.gd:542` | 起点/落点，待逐条确认是否进 sim |

⇒ **数数只能列出嫌疑，答不了「差多远」。** 只有把同一份输入在两个平台上各跑一次对一下才知道。

## 9. 实测结论（五轮测量，每一轮都是 CI 实跑，不是推测）

| 轮 | 问什么 | 答案 |
|---|---|---|
| 1 | Windows/MSVC ↔ Linux/glibc 差多远？ | **9 个场景 8 个逐位相同**；只有「③ 3v3 满装备」分叉 |
| 2 | 是哪件装备？ | 24 条二分里 **23 条一致**；只有「basic 同时带 032+058+073」。**18 件逐件都不飘，三件同时在场才飘 ⇒ 组合效应** |
| 3 | 第几步开始飘？ | ⚠ 我报了「第 0 步」，**是我比错了**（见下） |
| 4 | 重新对齐后呢？ | **第 271 步**（≈4.5 游戏秒），前 270 步逐位相同 |
| 5 | 哪只单位、哪个字段？ | **石头龟的 x 坐标：本地 `658.13` / CI `658.12`** —— 血量、护盾、暴击、其余 7 只单位全部相同 |

### 9.1 根因的形状

**一个浮点末位。** 指纹里的 x 用 `%.2f` 打印，两边差 **0.01** ⇒ 底层差的是 float 的最后几位。
其余字段（hp `%.3f` / shield `%.2f` / crit `%.4f`）全同，说明**不是逻辑分叉，是数值精度**。

它只在「三件同时在场」时出现，与那三件的性质吻合：
032 召骷髅、058 召炮台 ⇒ **场上多两个单位** ⇒ 石头龟的推挤/索敌里多了两次距离运算；
073 每次普攻还要抽一个随机敌人。单位一多，非精确运算（`sin/cos/pow`，IEEE-754 **不保证**跨平台
逐位一致）被走到的次数就多，某一次差一个 ulp，位置就差 0.01。

### 9.2 ★我在第 3 轮犯的错（记下来，比结论本身更要紧）

第 3 轮我报「首个分叉步 = 0」。错的。
CI 的失败日志**从后面截断**（600 行只回来 389 行，步号 211..599），而我按**行号**对齐
⇒ 拿本地第 0 步比了 CI 的第 211 步。判据没写错，**对齐错了**。
按步号取交集重比才得到 271；第 0 步的指纹两边 sha256 逐字相同。

⇒ **拿两份日志对比之前，先确认两边的"第 i 行"说的是同一件事。**
行号不是身份，日志里的那个编号才是。

### 9.3 下一步（A2，没做）

- 差 0.01 会不会改变胜负？**没量过。** 一个末位在 600 步里会不会放大成不同结果，要跑长局看。
- 修法两条：① 把 sim 路径上那几处 `sin/cos` 换成自己实现的确定性版本
  （§2.3 已列出真正喂进单位坐标的 7 处）；② 或者接受这个精度，改成「服务端结算一次 + 下发重放」
  —— 那样客户端根本不算，精度差异自然不存在（这正是原稿 §五.3 要的）。
  **②才是原稿的做法，①只是让客户端各算各的也能对上。**
