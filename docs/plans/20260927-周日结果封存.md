## 1. 需求原文

用户原稿 §五.5，逐字：

> **结果封存**：结算结果**不随撮合下发**；选手点开重放时解锁；决赛签表统一至**开播时刻**全服解锁。
> 结算存档做访问审计，防内部泄露。

## 2. 调查

### 2.1 「两边都赢」的确切机制（已查实）

服务端**一场都不打**，只有一张 `finals_results` 表等客户端来报。
A 和 B 各自在自己机器上跑的是**两场不同的对局**：

| | A 机上 | B 机上 |
|---|---|---|
| 左队（活的） | A 的真阵容 | B 的真阵容 |
| 右队 | B 的**快照** | A 的**快照** |

两边都可能算出自己赢 —— 这不是竞态，是**两场不同的战斗**。
然后 `finals_report` 是 `on conflict … do nothing`（先报的算），后报的那份**静默丢掉**
且仍返回 `ok: true`；而那个客户端的 `finals_settle(won)` **一个字都不看服务端答复**，
已经发过币、加过胜场、播过「胜利」横幅（`battle_hud.gd:1303`）。

### 2.2 ★真正的空缺是「谁说了算」，不是「要不要服务端复算」

D7（**已定 2026-09-16**）：

> 两步走 —— 先做②（**客户端算** + 服务端账目校验与抽检），架构上预留复算接口；
> B 阶段确定性加固完成后再决定要不要真开那台机器

D4：Supabase **跑不了 Godot** ⇒ 服务端复算另议。

⇒ 当前批准的设计就是**客户端算**。它在积分赛没问题（每人各打各的快照，只有自己的结果要紧），
但周日一场比赛有**两个**客户端同时主张权威 —— 而「哪一侧说了算」**从来没人定过**。
「两边都赢」就是这个空缺，不是要推翻 D7。

### 2.3 ★权威已经存在，而且原稿说它该晚点才亮

`finals_view()` 下发的 `done`（`{"轮-场": 赢家侧}`）就是唯一权威：一个桶里只有一个值。
而它**只返回 `round < 当前轮` 的结果** —— 当前轮的结果**根本不下发**（不剧透）。

⇒ 也就是说：**「打完之后要等到轮次推进才知道胜负」不是缺陷，正是原稿 §五.5 的「结果封存」。**
现在的实现反而是**违反**原稿的：它在本机当场宣布了一个未经确认的结果。

### 2.4 确定性这条线现在到哪了（决定本方案要不要等它）

[A 阶段](20260926-A跨设备确定性.md) 实测：9 个场景 **8 个跨平台逐位相同**，
唯一分叉是一个浮点末位（石头龟 x：`658.13` vs `658.12`，第 271 步）。

⇒ **本方案不依赖确定性**。只有一侧的结果被采纳，另一侧根本不需要算出同样的数。
（确定性是**重放**（C 阶段）要的：重放若按「种子 + 阵容」重算，两台机器必须得出同一份画面。）

## 4. 方案

**打完 → 结算「与胜负无关的那部分」+ 横幅说「结果已封存」→ 对阵图翻面时补上胜负部分。**

1. `GameState.finals_settle(won)` 拆成两半：
   - `finals_settle_sealed() -> int`：场次 +1、赛季经验、斧经验、返回轮次币（**对称，与胜负无关**）
   - `finals_reveal(won)`：糖罐、`season_wins`、`season_eggs_killed`（**只有这几项吃胜负**）
2. 新增持久字段 `finals_pending_reveal = {"round": r, "match": m}`，随周清。
3. 战斗结束（周日且玩法已上线）：调 `finals_settle_sealed()`，记下 pending，
   横幅显示**「结果已封存 · 开播时揭晓」**而不是 胜利/失败。
4. `BracketMapScene` 的 feed 到手时（已有 `_record_progress()` 那个钩子）：
   若 pending 那一场在 `done` 里有了结果 ⇒ `finals_reveal(那一侧是不是我)` 并清掉 pending。
   **幂等**：清掉之后不会再补第二次。

★不需要新 RPC、不需要改 SQL、不需要把结算改成协程。用的就是已经有的权威。

## 10. 回填：v0.19.451 —— 封存那一屏说清在等什么（2026-09-27）

### 10.1 为什么这条必须补

上一版把胜负封了起来（对的），但屏幕上只剩「结果已封存」四个字。
**一个你看不懂的等待，和一个 bug 长得一模一样。**
玩家在这一刻会问三件事，而屏幕一件都没答：

① 为什么不告诉我输赢 ② 什么时候知道 ③ 去哪看

### 10.2 做了什么

`Phase2Cfg.finals_sealed_sub()`（`scripts/gamedata/phase2_config.gd:550`）：

> 双方同时开打 · 结果统一在本轮开播时揭晓
> 去【决赛日 → 看对阵图】等翻面

`battle_hud.gd:1332` 在 `_banner_sealed()` 为真时把它画成一行小字（`#9fb3c8` / 16px / 自动换行）。

### 10.3 两条刻意的设计

- **文案做成纯函数，不就地写在结算卡里。**
  只写在屏幕里的话，门禁只量得到「此刻」那一格，而**这句话一周只在周日出现** ——
  本仓「判据挂在星期几上」已经栽过五次（v0.19.446 一轮修了四条）。
  现在屏幕与门禁读的是**同一个答案**。
- **不承诺具体秒数。** 揭晓时刻由服务端的轮次推进（`finals_round_sec`）决定，
  客户端写死一个数就是「说了做不到的事」。这一条也焊成了断言：
  文案里出现「分钟」「秒」当场红。

### 10.4 门禁与反向验证

`verify_finals_settle` 55 → **60**，新增 ⑤g 段五条（一条分母 + 三条各答一问 + 一条硬规矩）。

## 11. 回填：S3 闭合 —— 「屏幕上真的写着那几个字」（2026-09-27）

### 11.1 为什么 §9.3 的估计是错的

§9.3 登记「要验得实例化整屏结算卡，成本不小 —— 登记，没做」。
**查了一遍仓库就发现不成立**：`tests/verify_result_reachable.gd` 已经在做这件事 ——
实例化真战斗场景、塞 28 个单位、开伤害统计面板、调 `sc._hud._show_banner(true)`、
然后量结算卡上每个按钮的真实屏幕矩形。挂一段上去就行。

⇒ 又一次「造轮子前先搜仓库」（memory `fb-search-repo-before-building`）。

### 11.2 ⑩ 段 10 条断言

| 类 | 断言 |
|---|---|
| 对照组 | 未封存时屏幕上写着「胜利」／未封存时**没有**封存字样 |
| 分母 | 拿到 GameState／封存那张卡真的建出来了（新增 186 个 Label）／纯函数的副标题非空 |
| 主判据 | 屏幕上写着「结果已封存」／**封存时不许出现胜利或失败**／副标题**逐字**上了屏 |
| 收尾 | `finals_pending_reveal` 已还原（不污染真存档） |

**两处刻意的设计：**

- **对照组不是装饰。** 上面那张卡是未封存的（`_show_banner(true)`），
  所以「屏幕上有『结果已封存』」不可能是因为它恒真 —— 先证明没封存时它写的是「胜利」。
- **只看新增的 Label。** 第一张卡还在树上，整树扫会把它的「胜利」也算进来，
  于是「封存时不许出现胜利」会**假红**。⇒ 取差集。
- **副标题的字不在测试里拼。** 读 `P2C.finals_sealed_sub()` —— 拼一遍就是抄第二份，
  抄本必然落后（memory `fb-hand-rolled-copies-drift`）。

### 11.4 途中栽的一个坑（记下来）

第一版把这一段插在 `sc.queue_free()` **之后** ⇒ 场景已释放，
`_all_label_texts(sc)` 当场 `previously freed` 报错，整份测试**从那里断掉**：

```
rc=0 · 0 条 FAIL · 没打 ALL PASS
```

正是 CLAUDE.md §2 说的「极易误判成真失败」的那个形状 —— 看着像 5 条断言红了，
实际是后半份**一条都没跑**。⇒ 锚点改到 `queue_free()` 之前。

★另外：红行的 detail 一开始印 `_blob.substr(0, 120)`，而新增的 186 个 Label
绝大多数是统计表里的数字 ⇒ 红了印出来是一串「57」。
