# 同名装备带多件：每件各自生效、统计分开

> 状态：实施中（2026-11-13 · 随周一 11-16 版本；代码与门禁已完成，等 CI 与发版）
> ★done-when：§6 验收 V1~V7 全部打勾，ship 进 main，RULES_VER 已升

## 1. 需求原文（用户 2026-11-13，语音转写，逐字）

- 「那还有一些问题啊，比如说我携带两个这个三肺的远古炮台会怎么样？理论上它应该是怎么样的？」
- 「对呀、啊，那两周两件肯定召唤两个炮台啊，三件召唤三个炮台，不是？如果有出现两件相同装备，肯定是各自就是各自省各自的这个效果呀，也不能说共享啊，你懂我意思吗？你说两个两个相同装备，它打的伤害，凭什么说你共享统计啊？那肯定是分开啊。嗯，你自己看吧。」

（「三肺」= 3 费；「各自省各自的」= 各自生效各自的。）

## 2. 调查结论

### 2.1 起因：058 远古炮台带两件

- 登场钩把召唤写成单个开关：`equip_stats_apply.gd:239-241` `u["_turret_pending"] = true; u["_turret_si"] = si` —— 第二件覆盖第一件的星级。
- 首帧只消费一次：`RealtimeBattle3DScene.gd:2409-2411`。召唤物引用只有一个槽 `u["_turret_ref"]`（`equip_system.gd:290`）。
- ⇒ 两件只出一座炮台，星级取装备栏**排在后面**那件（3★+1★ 可能放出 1★ 炮台，比只带一件还差）。032 唤灵骨符同形（`equip_stats_apply.gd:249-251`、主场景 2406-2408）。

### 2.2 根子：状态按装备 id 只有一槽

- `u["eq_state"]` 以装备 id 为键（`battle_spawn.gd:478`），所有钩子循环「逐件遍历、按 id 取同一份 stt」：
  `_tick_eq_intervals`（`equip_system.gd:381`，已在 09-15 改成「计时器只推一次、到点每件各放一次」，但 stt 仍共用）、
  `_eq_on_hit`（1525/1554）、`_eq_on_target`（2239/2245）、`_eq_on_dodge`（2320）、`_eq_on_cast`（2339）、
  on-death（2516）、`_eq_tick`（2681）、各批系统 `tick_unit`（food 78 / potion / spirit / staff_synergy 125 …）、
  `_eq_apply_flags`（`equip_stats_apply.gd:187`）。
- 计数 / 弹药 / 阶段 / 充能 / 召唤物引用在两件之间共用 ⇒ 第二件要么没效果、要么把第一件的节奏打乱。
- 052 左轮 10-16 修过一次（弹数 × 件数，`equip_stats_apply.gd:234-236`），是逐件打补丁，不是通解。

### 2.3 统计按 (携带者, 装备 id) 记账

- `EquipTally._add`（`equip_tally.gd:181`）以 id 为键 ⇒ 两件同名装备的伤害 / 治疗 / 护盾合进同一行；面板 `info_panel.gd:1006` 按 id 取 ⇒ 两格显示同一个数。

粗筛标出 53 / 96 件（含噪声：防御类量不出；随机数先后造成的 3% 级差）。典型（产出 = 敌方承伤 + 我方回血 + 获盾）：

## 3. 需求 ↔ 代码的出入

- **8 月「实装契约 §4」写的「多件同带 → 取星级更高的那一件，不是相加」**（`docs/plans/20260806-实装契约-批④.md:90`，标为「用户历次拍板」，代码里 `eq_blade_batch.gd:56`、`eq_relic_batch.gd:46/113`、`eq_gadget_batch.gd:125`、`equip_stats_apply.gd:288`（060）、`incense_stone_system.gd:33` 照此实现）—— 与本次原话相反。**本次（11-13）取代它**；09-15 用户对 075 说的「如果装备两个75，应该各做各的吧」与本次同向。
- 「各自生效」的落点：每件 = 一份独立实例（自己的星级、计时、计数、召唤物、统计行）。两份效果落到**同一个目标**上怎么叠，与「两只龟各带一件」时一致 —— 例：光环 / 减益本来就规定「多来源取最高」的（094 碑光环、`thorn_cut.gd:33`），照旧取最高；本来就各算各的（护盾、伤害、自身增益），就各给各的。

## 4. 方案

### 4.1 份号（copy key）

- 同一只龟身上同名装备按装备栏顺序编号：第 1 件 = 原 id（`p2eq_058`），第 2 件起 = `p2eq_058#2`、`p2eq_058#3`。
- **第 1 件的键与现在一字不差 ⇒ 不带重复装备的对局结果完全不变**（规则指纹 5 局不该动 —— V5 验）。
- 工具函数放 `EquipStatsApply`：`ck_of(u, e)`（按 `is_same` 定位条目）、`copies(u, iid)`、`base_id(ck)`。

### 4.2 统一入口改成按份号（一处改、全表受益）

`eq_state[ck]` 取状态、`tally.push(u, ck)` 记账（`battle._cur_eq_item` 仍写原 id —— 它是「哪种装备」的语义，盾羁绊认的是种类）。
入口清单：`_eq_apply_flags` · `_b4_on_spawn_all` · `_tick_eq_intervals`（取消「计时器每种只推一次」，每件自己的计时器）· `_eq_on_basic_attack` · `_eq_on_hit` · `_eq_on_target` · `_eq_on_dodge` · `_eq_on_cast` · on-death · `_eq_tick` · 各批系统 `tick_unit` / `use_first_of` / `use_b4` · `fire_equip_effect`。

### 4.3 逐件：入口以外按 id 直接取状态 / 写在龟身上的

按 §2.4 标出的件逐件读代码改（清单在实施回填里逐件记：改了什么、为什么）。召唤类一律「每件召一个、各自星级、各自引用」。写死「取高星」的件改成每件各算。

### 4.4 统计与面板

- 记账键 = 份号 ⇒ `_st_eq` / 结算行 `_st_eq|p2eq_058#2|phy` / 快照 / 回放天然分开。
- 面板按「这一格是这只龟身上第几件同名装备」算份号取统计（`info_panel.gd` 1667 / 2173 两个入口）。

### 4.5 规则版本

改对局结果（只在带重复装备时）⇒ `RULES_VER` 6 → 7（随周一版本）。

## 6. 验收标准

- V1 探针 v2：每件 × [3★,3★] —— 两份各自的装备账都 > 0；[3★,1★] 与 [1★,3★] —— 3★ 那份的账都大于 1★ 那份（证明星级各算各的、不被覆盖）。召唤类 B 的召唤物 = 2×A。
- V2 058 / 032：两件 = 两座炮台 / 两只骷髅，各自星级（门禁 `verify_dup_equip`）。
- V3 面板：两件同名装备两格显示各自的统计。
- V4 反向验证：把份号函数改回返回原 id ⇒ V1/V2 变红；逐字节还原。
- V5 不带重复装备：`verify_rules_fingerprint` 5 局逐步状态与改前一致（只差统计列时用 `RULES_FP_DUMP` 对比逐步状态）。
- V6 回放 / 直播覆盖测试照绿（`verify_stream_coverage` 等）。
- V7 precheck + CI 全绿。
