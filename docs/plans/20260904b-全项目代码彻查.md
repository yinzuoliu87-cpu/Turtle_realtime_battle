## 4. 方案

### 4.1 主线：把「多路径概念」做成机制，而不是靠人记得

**真伤那件事的根因不是路径多，是没有机制强制所有路径走同一个标准。**
`UIPalette` / `FLOAT_STYLE` 这两张标准表存在了很久，但只有一条路遵守，而**没有任何门禁会为此变红**。

做法（每个多路径概念一条）：

```
给概念 X 的每条路径喂【同一份输入】，断言它们的【可观察结果】相同。
```

这正是 `verify_true_dmg_white` ② 那条的形状：两条伤害路打同一种真伤，读回的 `font_color` 必须相同。

| 批次 | 概念 | 要断言"同输入同输出"的项 |
|---|---|---|
| **A** | 伤害（2 条） | 颜色 ✅已做 / 跳法 ✅已做 / **排行** / **暴击判定** / **护甲魔抗结算** / **统计记账** |
| **B** | 击飞（2 条） | 高度曲线 / 落点钳制（`ARENA` 边界）/ 落地伤害 / 期间无敌 |
| **C** | 选靶（3 条） | 排除条件（是否排除大师/蛋/召唤物/驯服）/ 距离口径 / 阵营判定（`_eff_side` 还是 `side`） |

### 4.2 副线：按实测排优先级，不是按"清单上有"

| 优先级 | 项 | 依据 |
|---|---|---|
| **P0** | §4.1 三个多路径概念 | 用户点名的形状，且已出过一次事 |
| **P1** | 死参数 43 处（先修判据的误报） | 静态可扫，改完能进门禁棘轮 |
| **P2** | 直读 `dict["key"]` 的**真风险子集** | 3704 处里绝大多数安全，要先找出判据 |
| **P3** | 重复代码 83 组 | 抽工厂函数；收益是可维护性，不是正确性 |
| **P4** | 信号 / O(n²) / 热路径分配 | **实测基本干净**，不值得投入 |

### 4.3 不做什么

- **不做**「通读 9 万行」——做不到，且已有 288 项门禁覆盖大部分维度。
- **不做**大规模重构。这个项目已经有 250 个自证测试 + 38 个审计器，
  重构的风险远大于收益；找问题 + 焊门禁才是正确的投入。
- **不为 P4 那几项写门禁** —— 实测干净的地方加门禁只会增加噪声。

## 8. 实施回填

### 批次 A-4（v0.19.325）—— 统计记账收口

**真 bug**：`_record_buckets()` 是抽好的共用记账函数，`_apply_damage_from` 走它，
而 `_apply_damage` **自己抄了一遍**，条件还不一样：

| | 共用函数 | 自己抄的那份 |
|---|---|---|
| 记「造成」的条件 | `src.has("side")` | `src.get("**alive**")` |

⇒ **施加者阵亡后** DoT 继续跳的伤害走这条路**不算给他**，走另一条照算。
用户 2026-07-19 报的「统计面板感觉很多伤害没统计」那次**只修了一半**（补了 `_st_dealt`，条件却用了 `alive`）。

**门禁** `tests/verify_dmg_paths_agree.gd` 9 条。形状固定：**给两条路喂同一份输入，断言可观察结果相同**。
流程严格按「先写门禁证明它是红的（3 条红）→ 修 → 反向验证（改回去当场红 2 条）」。

### ★★★ 我的判据连错两次（记下来免得下次再犯）

第一版断言「**两条路的伤害数值相同**」——而 `_apply_damage_from` 走完整结算会吃
**稀有度加成 +20%**（`_BASIC_RARITY_BONUS`），100 点进去 120 点出来。**那是对的，不是 bug。**
差点把正确的差异当 bug 修（memory [[fb-judge-must-fit-the-shape]]）。

⇒ 判据改成「**记的账 == 这条路自己实际造成的伤害**」，对两条路都成立，
且它才是「统计面板显示的数对不对」的真定义。

**通用教训**：比较多条路径时，比的是「**该发生的行为发不发生**」和「**各自内部自洽**」，
**不是**「数值相同」——路径之间本来就可能有不同的乘算。

### 批次 C（v0.19.326）—— 主动索敌六条路收口

**真 bug**：`battle_targeting.gd` 有**六个**函数回答同一个问题「哪些敌人能被主动选中」：

| 路径 | 组装期的机甲 | 调用次数 |
|---|---|---|
| `_pick_enemies_of`（走 `_is_untargetable`） | 排除 ✅ | 50 |
| **`_nearest_enemy`** | **选得中** ❌ | **80（普攻主线）** |
| `_nearest_enemy_from` / `_targetable_enemies` / `_acquire_target` | 选得中 ❌ | — |

`_is_untargetable(o)` 查 `untargetable_until` **或** `_assembling`，其余五个只查前者
⇒ **赛博龟组装机甲的 5 秒里，普攻照样锁得住它。**

而 `_pick_enemies_of` 头上写着**用法铁律**「凡随机挑一个/最近一个/单体指向都走这个」——
**铁律写在注释里，没有门禁强制**。与真伤颜色同一个病。

**门禁** `tests/verify_target_paths_agree.gd` 8 条：四种该被排除的情形
（机甲组装 / 黑洞 / 围栏蛋 / 大师）各问六条路一遍。

### 这轮暴露的两条「判据问题」

| | |
|---|---|
| **假判据** | `verify_eq_gadget_batch` 用**源码子串匹配**查 `untargetable_until` 在不在。收口后字符串变了它就红 —— **行为变好了，判据却红**。已更新并注明真正验行为的在新门禁 |
| **我的分母也错了** | 第一版用「另造一个干净的对照单位」，而它离得远一点 ⇒ `_nearest_enemy` 只返回更近的那个 ⇒ 分母自己红。改成**同一单位 setup 前后对比** |

### 一条虚惊（记下来免得下次误判）

`verify_eq_venom_drone` 报性能 1.0261ms > 1.0 预算 ⇒ 单独跑三次都是 **0.33ms**。
全套门禁并行跑（JOBS=2）时 CPU 争抢导致。**性能类断言在并行门禁下本就对环境敏感**，
遇到先单独跑三次再判，别当回归。

### 二、`zero_caller_audit.py` 的同名掩护盲区 —— 本轮最有价值的一条

主判据是「名字在全仓出现过就算有人调」⇒ **同名方法互相掩护**。
实测受检目录 106 文件 / 1859 函数中，**61 个名字被 ≥2 文件定义，共 302 个定义处**
（`clear_all` 16 处 · `tick` 36 处 · `on_hit` 11 处）。

**`IncenseStoneSystem.clear_all()` 就是这么漏过去的** —— 写着完整的换路撤场
（写回存档 → `_revoke()` → 复位加载闸 → 清香台），**全仓零调用者**，而门禁一直报绿。

不调是**有意**的（`dual_lane_flow.gd:513`），但那条注释的理由与代码事实相反 ——
它说「清了就把进度抹了」，而函数第一件事就是 `_persist_chg` **把余额写回存档**。
三条后果**逐个实测均无影响**：

| 担心 | 实测 |
|---|---|
| 香台残留到下一路 | **不残留**（分母①换路前=1 · 分母②携带者已离场 · 换路+5 秒 `_altars`=0）。原注释担心的「靠 `_world` 兜底是**别人的**生命周期」实际兜住了 |
| `_revoke()` 没撤 buff | buff 写在**单位字典自己**身上，换路整批离场 |
| `_persist_chg` 没写回 | 它另有活调用点在 `:200`（刻痕当时就写回） |

⇒ 标 `# zero-caller-ok:` 并把三条实测钉进函数注释，免得下一个人再查一遍。

**加了第二道网**：对同名方法的**每个定义处**单独判（①同文件裸调 `fn(`，或
②任意处限定调用 `X.fn(`）。302 个定义处里恰好抓到 **1 个真死函数** ——
`potion_eq_vfx._ring_mesh`（2026-08-11 用户批「程序生成的圆环」后换成真瓶子立绘，
函数留着 23 行没人调，旁边注释还在解释它为什么被弃用）⇒ **已删**
（逐行核对：只删 1 个 `func` / 23 行 / 0 新增 / 脚本能加载）。
**零误报所以不留台账，新增当场红**，已反向验证。
