---

## 0. 先纠正一个我一开始就搞错的模型（后面所有结论都建立在这上面）

`project.godot` 是 `stretch/mode=canvas_items` + `stretch/aspect=expand`，基准 1280×720。

我最初以为是「**锁高 720，宽 = 720 × 比例**」——**只对了一半**。
`expand` 锁的是**受限的那一轴**：

| 窗口 | 视口 | 锁哪轴 |
|---|---|---|
| 21:9（1680×720 窗口） | **1680×720** | 锁高，宽变大 |
| 19.5:9 iPhone 横屏 | **1560×720** | 锁高，宽变大 |
| 16:9 | **1280×720** | 正好基准 |
| 4:3 iPad | **1280×960** | **锁宽，高变大** |
| 1:1 折叠屏 | **1280×1280** | 锁宽，高变大 |
| 720×1280 竖窗口(PC 可拉出来) | **1280×2275** | 锁宽，高变大 |

**推论（这条决定了整个方案）：视口宽永远 ≥ 1280，高永远 ≥ 720。**
所以适配要解决的**不是「内容被挤扁/溢出」，而是「多出来的空地怎么分」**。

> 我按错模型做过一次判断：以为 iPad 视口只有 960 宽 → 「PK 条 948 会溢出 268px」。
> 实测视口是 1280×960，PK 条根本不会收缩。那条结论是错的，已作废。
> （同一个错误模型还写在 `battle_hud.gd` 的注释里，一并改正了。）

## 1. 大厂做法与证据

| 结论 | 出处 |
|---|---|
| 移动横屏基准用 1280×720 + `canvas_items` + `expand`；`expand` 要求 Control 靠**锚点**定位 | [Godot · Multiple resolutions](https://docs.godotengine.org/en/stable/tutorials/rendering/multiple_resolutions.html) |
| 桌面参考分辨率 1920×1080；像素画基准常用 640×360 | 同上 |
| 像素游戏建议 `stretch/scale_mode = integer`（避免整行像素被吞/被复制） | 同上 |
| 最小可点尺寸 iOS HIG **44×44 pt** | Apple HIG · Layout |
| 最小可点尺寸 Material **48×48 dp** | [Material · Touch target](https://m2.material.io/develop/web/supporting/touch-target) |
| 窗口尺寸变化要主动重排（Godot 不会替你挪绝对定位的节点） | [Godot forum · size_changed relayout](https://forum.godotengine.org/t/refreshing-control-node-when-window-size-changed/132294) |

**通行做法**（这也是本方案采用的）：
**内容锁在一个「设计框」里居中，背景铺满整窗，chrome（返回/投降/币值）贴真实屏幕边（安全区锚定）。**

**`scale_mode = integer` 本项目【不开】** —— 它会把缩放倍率向下取整，1080p 上 1280×720 只能 ×1，
四周留出大片黑边。本项目立绘是 4000×1000 的高分辨率插画、不是低分辨率像素图
（2026-07-31 实测过低分辨率渲染会把龟糊成一团），留黑的代价远大于收益。
已在 `project.godot` 里以注释形式记录，免得下次有人「按像素游戏最佳实践」顺手加上。

## 2. 实测出来的问题（`tests/_probe_ui_layout.gd` 量真实 `get_global_rect()`，不是看像素猜）

| 屏 | 1280×720 偏移 | 1680×720 偏移 | 诊断 |
|---|---|---|---|
| 排行榜 | −126 | **−326** | 差 −200 = 完全没重排 |
| 战绩 | −119 | **−319** | 同上 |
| 设置 | −174 | **−374** | 同上 |
| 商店 | −146 | **−246** | 差 −100 = **半重排**（顶栏按视口铺、其余按设计坐标） |
| 背包 | +16 | +16 | 同商店那套半适配 |
| 主菜单 | +0 | +0 | 有 `content_root`，正确 |
| 匹配 | +0 | −86 | 取消键贴边（正确 chrome 行为） |

**根因**：主菜单/匹配有 `content_root`（1280×720 设计框居中于视口），
其余七屏**没有**——直接按设计坐标画在视口 (0,0)，宽屏多出来的 400px 全堆右边。
差值恰好等于 `(视口宽−1280)/2`，这是"完全不重排"的指纹。

**另外两个独立 bug**（都是这次量出来的）：

- **主菜单版本号根本看不见**：`_menu_label` 设了 `PRESET_FULL_RECT`，
  `_version_stamp` 之后手动设的 `size=(200,22)` 下一帧被布局重算成 **1480×744**，
  再叠上右对齐 → 文字画到 x≈2544，**在屏幕外**。
  CLAUDE.md §2.5 写着版本号的全部价值是"测试者报 bug 能说清版本"——看不见等于没有。
- **图鉴页签写死 1280**：`start_x = (1280.0 - total_w)/2`，而 TabBar 是全宽锚 →
  21:9 上整条页签坐在中心左边 200px。

## 3. 做了什么

### PC 一板
1. 新增 **`scripts/util/ui_frame.gd`**（`UIFrame.attach(host)`，每屏一行）：
   建 1280×720 内容层居中于真实视口，收编现有非满铺子节点，`size_changed` 时重新居中，
   `_process` 里按子节点数变化收编异步晚建的节点（排行榜从云端拉榜就是这种）。
   满铺背景/遮罩**不**进框（它们本来就该铺满整窗）。
2. 七屏各接一行：商店（**含上锁屏那条 early-return 分支**）、背包、排行榜、战绩、设置、训龟大师。
3. 商店/背包的 `vw = max(W, 视口宽)` 改回 `W` —— 半适配比不适配更乱。
4. 版本号锚点先掰回 `TOP_LEFT` 再设 size/position。
5. 图鉴页签用真实视口宽居中。
6. `project.godot`：`resizable=true`；`GameState._pc_window_setup()` 设 **最小窗口 640×360**。
   （全屏与 F11/Alt+Enter **早就有**，在设置页 + `_unhandled_key_input`，没重造。）
7. **战斗场景补接 `size_changed`** —— 它是全项目唯一不接的场景。
   `battle_hud.on_viewport_resized()`：PK 条重建、右上两键重摆
   （★不整体重建 `_build_topright_btns`，那会把投降确认框和日志面板再建一份）。

### 手机一板（触控热区）
阈值换算：iPhone 14 横屏 844×390pt，视口高恒 720 → 1pt = 1.846 视口像素 ⇒ **44pt = 81 视口像素**。
（我第一版直接拿 44 当阈值，那等于只要求了 24pt。）

| 元素 | 改前 | 改后 |
|---|---|---|
| 选龟 稀有度筛选 ×7 | 46×30（15pt） | 52×52（28pt） |
| 选龟 返回/清空/上次 | 高 36/29（15pt） | 高 58（24pt） |
| 图鉴 页签 ×5 | 170×36（20pt） | 170×56（30pt） |
| 设置/战绩 圆图标键 | 36×36（20pt） | 48×48（26pt） |
| 设置 音量滑条 | 轨道 8px（**4pt**）+ 把手 28（15pt） | 整行 48px 透明命中条（26pt），把手改 IGNORE |
| 背包 `?` 帮助 | 28×28（15pt） | 48×48（26pt） |
| 背包 前排/后排 | 50×22（12pt） | 56×44（24pt） |

结果：**全部 10 屏在 19.5:9 下 0 个"严重档"（<22pt）热区**，唯一剩下的是
`🛠 调试场`（只在 debug 构建出现，正式包没有），已在门禁里白名单。

### 门禁
**`tests/verify_ui_layout.gd`**（42 条断言，进 `run-tests.sh` 自动发现）：
10 屏 × 4 比例，用 **SubViewport** 直接设视口尺寸（真窗口要起 40 个进程，进不了 CI）。
①不溢出 ②内容层精确居中于 `(视口−设计)/2` ③无 <40px 可点元素 ②b 图鉴页签居中。

**反向验证 6/6 全部会红**：拆排行榜居中 / 拆设置居中 / 设计框不居中 / 热区改回小 /
版本号锚点改回 / 图鉴页签写死 1280。

## 4. 已知风险与未决点

- **R1｜44pt 未完全达标。** 门禁卡的是"严重档 40 视口像素(≈22pt)"，不是 HIG 的 81 像素(44pt)。
  把每个键都做到 81 像素高 = 在 720 高的设计里每个键占 11% 屏高 = **重画全部界面**，
  超出本次范围。现状是"手指点得中"，不是"完全合规"。要不要做完整达标，需要拍板。
- **R2｜图鉴详情长条目会被裁尾。** 详情面板原本用 `fit_content` 自动长高，长条目穿出边框
  一直画到屏幕外；这次设了 `clip_contents=true`，改成裁在面板内。
  **正解是把 Detail 换成 ScrollContainer**，未做。当前是"看不全"（好过"画到屏幕外"）。
- **R3｜选龟与图鉴走的是另一套布局哲学**（整屏按视口等比缩放，自带 `_sp()/_sf()`），
  门禁的②对它们豁免、只由①③兜住 + 给图鉴单加了②b。选龟侧没有等价的针对性断言 ——
  它的构图回归目前**没人守**。
- **R4｜`UIFrame._process` 每帧比一次子节点数**。开销极小（一个 int 比较），
  但它是"轮询"而不是"事件"，理论上有一帧延迟。异步建完内容的那一帧可能没居中。
- **R5｜没验真机。** 全部结论来自 SubViewport 与桌面窗口实测；iOS 刘海/灵动岛的真实安全区
  只在真机上才准（代码走的是 `SafeArea.margins`，与摇杆/圆盘同一套）。
- **R6｜极端竖窗口（PC 拉成 720×1280 → 视口 1280×2275）没做专门处理。**
  内容会居中在极高的视口里，上下大片空地。最小窗口 640×360 挡不住这种拉法。
