## 3. 与现状的出入

1. **`install_uid` 不是账号**。它是「这台机器」，换设备即丢档。D3 的匿名+补绑要求一个**服务端身份**，
   `install_uid` 只能作为「首次匿名登录的凭据」，不能当主键。
2. **`ghost_id` 的「谁」这一维刚补上场次，但还没补「账号」**（A6/U11 加的是场次）。
   接了真服务器之后主键必须是 `(account_id, season_week, battles)`，否则两台设备同一个人会互相覆盖
   —— 这正是 memory `fb-id-without-owner-dimension` 记过的形状。
3. **隐私政策草稿已经过期**：`docs/隐私政策.md` 里「不会上传：…邮箱」那句，在 D3 的补绑邮箱一上就是**假的**。
   要按 v2 **重写**，不是填空。还要补：每场上传快照（D5）、重放存 3 天（U7）、
   周日掉线代打用最后锁定阵容（D8）、Supabase 侧 IP 日志保留期。
4. **停服开关目前不存在**。周一维护窗口要能「停服 → 发版本 → 开服」，
   而客户端现在连不上只会**静默失败**（`remote_pool` 的设计是"连不上就当本地池"）。
   这在平时是对的，在维护期会让玩家以为游戏坏了 ⇒ 要区分「没配后端」与「后端主动停服」。

## 4. 方案

### D-1　先把「有没有后端」做成可见状态（不依赖 Supabase，可立刻做）

`remote_pool` 现在只有「有 url / 没 url」两态。加第三态：**后端可达但主动停服**（维护中）。
- 客户端：`GET /status` 返回 `{"maintenance": bool, "notice": "..."}`；停服时主菜单显式提示，不静默回落。
- ⚠ 判据要区分三态，不能只验「连不上时不崩」。

### D-2　Supabase 项目与表结构

需要用户先建项目（见 §5）。表：

| 表 | 主键 | 字段要点 | 保留期 |
|---|---|---|---|
| `accounts` | `account_id` (uuid) | `email`(可空，补绑后填) / `created_at` / `last_seen` | 长期 |
| `ghosts` | `(account_id, season_week, battles)` | 阵容快照 JSON / `uploaded_at` / `season_wins` / `hearts` / `season_sweeps` / `client_version` | 本周 + 上周 |
| `matches` | `match_id` | `week` / `phase` / 双方 `account_id` / **种子** / 双方阵容快照 / 结果摘要 / `client_version` | **到周一自动删** |
| `standings` | `(week, account_id)` | `wins` / `hearts` / `sweeps` / `promoted` / `title` | 长期（头衔要留） |

★`ghosts` 的主键必须含 `account_id`，理由见 §3.2。
★`matches` 带 `client_version`，播放前比对（U7 的实现要求①）。

### D-3　账号：匿名起步 + 补绑邮箱

- 首次启动：Supabase **匿名登录** → 拿 `account_id`，本地存起来（与 `install_uid` 并存，后者只做首次绑定凭据）。
- 补绑：玩家在设置里填邮箱 → Supabase 邮箱 OTP → 把匿名账号**升级**为带邮箱的账号（同一 `account_id`，不新建）。
- 换设备：用邮箱登录取回同一个 `account_id`。**没绑邮箱换设备就是丢档**，这一点要在 UI 上说清楚。

### D-4　上传与匹配接线

- 每场结算后 `POST /ghost`（已有调用点，A 阶段的 `_settle_season` 里）→ 写 `ghosts`，同键覆盖。
- 匹配 `GET /opponent?week=&battles=` → 服务端按 §2.3 的口径选（同场次 → 倒序最新 → 排除自己）。
  ⚠ **排除自己要按 `account_id`**，不是按 `ghost_id` 前缀。
- 回落链与记账沿用 A6 的 `match_src_counts`（精确 / 同桶 / 机器人三路各自计数）。

### D-5　服务端账目校验（D7 第一步）

Edge Function 复用 `server/rules.mjs`：
- 每场上报的 `coins 增量 / xp 增量 / hearts 变化` 必须落在规则算得出的区间内，越界记一条 `flag`，**不拒绝**（第一步只观测）。
- 抽检：每周随机抽 N 场，把种子 + 双方阵容存下来，人工/离线用 det 模式重算比对。
- **预留复算接口**：`POST /verify` 的签名先定下来，实现留空返回 `{"verified": null}`。

- **Supabase 免费档一周无请求自动暂停** —— 已列入 I1 的相邻风险；上线后有玩家就不会触发。
- **邮箱 OTP 依赖 Supabase 的发信额度**，超了要接第三方 SMTP。几百人规模下不会超。
- **我无法验证真实网络条件**：本机代理会改写 POST body（memory `fb-local-proxy-corrupts-post-body`），
  探针工具必须绕开代理；而「用代理模拟海外」是**无效实验**（它对国内域名走直连）。
  ⇒ 真实连通性只能等用户在英国实测。
