## 3. 与现状的出入

1. **`install_uid` 不是账号**。它是「这台机器」，换设备即丢档。D3 的匿名+补绑要求一个**服务端身份**，
   `install_uid` 只能作为「首次匿名登录的凭据」，不能当主键。
2. **`ghost_id` 的「谁」这一维刚补上场次，但还没补「账号」**（A6/U11 加的是场次）。
   接了真服务器之后主键必须是 `(account_id, season_week, battles)`，否则两台设备同一个人会互相覆盖
   —— 这正是 memory `fb-id-without-owner-dimension` 记过的形状。
3. **隐私政策草稿已经过期**：`docs/隐私政策.md` 里「不会上传：…邮箱」那句，在 D3 的补绑邮箱一上就是**假的**。
   要按 v2 **重写**，不是填空。还要补：每场上传快照（D5）、重放存 3 天（U7）、
   周日掉线代打用最后锁定阵容（D8）、Supabase 侧 IP 日志保留期。
4. **停服开关目前不存在**。周一维护窗口要能「停服 → 发版本 → 开服」，
   而客户端现在连不上只会**静默失败**（`remote_pool` 的设计是"连不上就当本地池"）。
   这在平时是对的，在维护期会让玩家以为游戏坏了 ⇒ 要区分「没配后端」与「后端主动停服」。

## 4. 方案

### D-1　先把「有没有后端」做成可见状态（不依赖 Supabase，可立刻做）

`remote_pool` 现在只有「有 url / 没 url」两态。加第三态：**后端可达但主动停服**（维护中）。
- 客户端：`GET /status` 返回 `{"maintenance": bool, "notice": "..."}`；停服时主菜单显式提示，不静默回落。
- ⚠ 判据要区分三态，不能只验「连不上时不崩」。

### D-2　Supabase 项目与表结构

需要用户先建项目（见 §5）。表：

| 表 | 主键 | 字段要点 | 保留期 |
|---|---|---|---|
| `accounts` | `account_id` (uuid) | `email`(可空，补绑后填) / `created_at` / `last_seen` | 长期 |
| `ghosts` | `(account_id, season_week, battles)` | 阵容快照 JSON / `uploaded_at` / `season_wins` / `hearts` / `season_sweeps` / `client_version` | 本周 + 上周 |
| `matches` | `match_id` | `week` / `phase` / 双方 `account_id` / **种子** / 双方阵容快照 / 结果摘要 / `client_version` | **到周一自动删** |
| `standings` | `(week, account_id)` | `wins` / `hearts` / `sweeps` / `promoted` / `title` | 长期（头衔要留） |

★`ghosts` 的主键必须含 `account_id`，理由见 §3.2。
★`matches` 带 `client_version`，播放前比对（U7 的实现要求①）。

### D-3　账号：匿名起步 + 补绑邮箱

- 首次启动：Supabase **匿名登录** → 拿 `account_id`，本地存起来（与 `install_uid` 并存，后者只做首次绑定凭据）。
- 补绑：玩家在设置里填邮箱 → Supabase 邮箱 OTP → 把匿名账号**升级**为带邮箱的账号（同一 `account_id`，不新建）。
- 换设备：用邮箱登录取回同一个 `account_id`。

#### D-3b　补绑 / 取回　—— ✅ 代码已落地（v0.19.423），⚠ 端到端还没通

★两条流程**第二步的判据正好相反**，写成一个函数必然有一半是错的：
- 补绑 `PUT /auth/v1/user` → 验码（`type=email_change`）⇒
  **返回的 id 必须等于当前 `account_id`**。不等 = 服务端新建了号，
  接受它就是**静默**把玩家的赛季身份换掉（排名/战绩/鬼影全断）。
- 换设备 `POST /auth/v1/otp` → 验码（`type=email`）⇒
  返回的 id **本来就和本机的不同**，那正是要换过去的那个。
★端点形状是 2026-09-21 真打 Supabase 拿到的（非法邮箱 → 400 `validation_failed`；
乱码 token → 403 `otp_expired`），不是凭印象写的。

**⚠ 未决 ①（挡住端到端）**：Supabase 的默认邮件模板只放一条链接，
模板里要有 `{{ .Token }}` 才会带那串 6 位数字码。
这是**后台面板上的一次性设置**，需要有人去点一下。
不做的话玩家收到的邮件里没有码，输入框就是死的。
★为什么不用链接：链接会把人带到浏览器完成登录，App 这边拿不回会话，
除非做 deep link（iOS URL scheme / universal link）—— 而这是个 **unsigned IPA +
Sideloadly** 分发的包，deep link 又脆又没法验。所以 OTP 码是对的那条路。

**⚠ 未决 ②（更要紧）：绑邮箱找回的是【账号】，不是【存档】。**
2026-09-21 逐表核实：服务端五张表 `accounts` / `ghosts` / `matches` /
`standings` / `service_status` **没有一张存玩家存档**
（`accounts` 只有 `display_name` / `created_at` / `last_seen`）。
龟等级、装备、深海币全在本机 `user://savegame.json` ⇒
**绑了邮箱换设备，照样丢龟丢装备。**
★本方案书自己第 126 行原来写着「没绑邮箱换设备就是丢档」，
隐含「绑了就不丢」—— 那个前提**架构上不成立**。
设置页的文案已经按事实改掉（v0.19.423），但**功能本身的缺口还在**。
⇒ 要不要做**存档同步**（新开一张表 + 上传/取回 + 冲突以哪边为准）
  是一个**要拍板的产品决定**，不是实现细节。它还需要改 `schema.sql`
  并在后台跑一次 —— 与未决 ① 一样要有人点面板。

#### D-3c　登录态续期　—— ✅ 已落地（v0.19.424），bug 修复

**问题（已核实，不是推测）**：`access_token` 只活在内存里（`static var _token`），
只在注册与验码时被赋值，**从不写盘、从不刷新**；而 `ensure_signed_in_async()`
见到已有 `account_id` 就直接返回。于是：
- 装机后第一次打开：有 token，上传/匹配正常；
- **重开 App 之后**：`_token` 为空 → 请求头退回 anon key →
  写 `ghosts` 被 **401 RLS** 拒（09-21 curl 实测）、读 `ghosts` 因
  `auth.uid() is not null` 拿到空列表；
- 就算不重开，token **3600 秒就过期**（回包 `expires_in: 3600`）。
⇒ **v0.19.420~423 的后端接线只在装机后第一个小时里真正工作。**
★为什么所有探针和门禁都没抓到：它们全是「一个进程里从注册跑到底」，
  **从没模拟过重启**。这一类要专门补一条「跨进程」的判据。

**真实回包形状（09-21 实测，不是凭印象）**：
- 注册回包本来就带 `refresh_token` 与 `expires_in` / `expires_at` —— **是我们一直扔掉了**；
- `POST /auth/v1/token?grant_type=refresh_token` → 200，同一个账号，
  **refresh_token 会轮换**（每次换新的）；
- 立刻重用旧 refresh_token → 仍 200（服务端有约 10 秒的重用宽限）；
- 乱码 refresh_token → **400 `refresh_token_not_found`**。

**方案**：
- `refresh_token` 存进 `GameState.auth_refresh` —— **设备本地**：不上云、清档保留、切轮不动
  （走 `account_id` 那条身份线）。
- 开机：有 `account_id` 且有 `auth_refresh` ⇒ 刷新一次；**拿到新的 refresh_token 立刻写盘**。
- 过期前续：记服务端给的 `expires_at`（绝对时刻，不信本机时钟算差值以外的东西），
  剩不到 5 分钟就刷新。
- ★★刷新失败**分两类，处理完全相反**：
  · 连不上 / 5xx ⇒ **什么都不做**，保留 refresh_token，下次再试。
    网络问题**绝不能**把人登出。
  · 400 `refresh_token_not_found` / 已用过 ⇒ 这份登录**真的失效了**：
    - 匿名号：重新匿名注册（`account_id` 会变；本机存档不受影响）；
    - **绑了邮箱的：不许自动建新号**（那是静默换身份），
      设置页提示「登录已失效，用邮箱重新登录」→ 走取回流程拿回同一个号。
- 老用户迁移（v0.19.420~423 装过的）：有 `account_id` 但**没有** refresh_token
  ⇒ 按「失效」处理（匿名 ⇒ 重新注册一次）。
- 顺带补上 D-3b 漏掉的入口：设置页加「已有账号？用邮箱取回」按钮 ——
  v0.19.423 只给了「绑定邮箱」，**取回流程写了但点不到**。

### D-4　上传与匹配接线

**拆成 a / b 两步交付**，理由同 D-3：前一半能单独交付并被验证，
捆在一条里只会让「D-4 做完没有」答不上来。

#### D-4a　每场都传　—— ✅ 已落地（v0.19.421）

每场结算后把阵容快照 upsert 进 `ghosts`（调用点就在 `_settle_season` 里）。
- 主键三维 `(account_id, season_week, battles)` 在 `Backend.upload_ghost()` 里凑齐；
  **缺任何一维就不传**，不许填 0 / 空串凑一行 —— 那会在服务端造出主键 `("",0,0)` 的垃圾
  并**覆盖别人的行**（memory `fb-id-without-owner-dimension`）。
- upsert 靠 `Prefer: resolution=merge-duplicates`；同键再传是**覆盖**，不是 409。
- **投降局不传**（判据 = `lane_results` 是空字典）。
- ★★ **请求头必须用登录拿到的 access token 当 Bearer**，不能用 anon key ——
  实测拿 anon key 写 `ghosts` 直接 **401 + RLS violation**。这条不打真请求发现不了：
  上传是「发完就忘」，全部失败在玩家侧**完全无感**。

#### D-4b　匹配搬家　—— ✅ 已落地（v0.19.422）

- 匹配改成 `GET /rest/v1/ghosts`：同一周 + 同场次 → 倒序最新 → 排除自己。
  ⚠ **排除自己要按 `account_id`**，不是按 `ghost_id` 前缀。
- ★★ **拉回来的快照必须过 `RemotePool.snapshot_valid()`**。
  理由不是假想：2026-09-21 验 upsert 时往 `ghosts` 写过探针行，而 `ghosts`
  **故意没给 delete 策略**（客户端删不掉自己的行，防止「打不过就把自己撤下来」），
  所以那几行还在库里。池子里混进结构不全的行是**常态**，不是意外。
- 回落链与记账沿用 A6 的 `match_src_counts`（精确 / 同桶 / 机器人三路各自计数）。
- ★实际实现比原计划多一条：拉 `battles in (N, N+1)` **两档**而不是只拉 N+1。
  写的时候才发现 `season_total_battles += 1` 在【非表演赛】分支里 ⇒
  **0 命玩家打表演赛时场次不涨**，卡在同一个数反复打；只拉 N+1 会让这类玩家
  的池子永远是空的、一直打机器人。
- ★`backend_url`（旧协议）**最终决定不填** —— 新层走 Supabase REST，
  旧层那条网络路径已无用武之地。不删它是因为 `remote_pool.gd` 里的
  `snapshot_valid` / `ingest_remote` / 上传旗被新层复用着。

### D-5　服务端账目校验（D7 第一步）

Edge Function 复用 `server/rules.mjs`：
- 每场上报的 `coins 增量 / xp 增量 / hearts 变化` 必须落在规则算得出的区间内，越界记一条 `flag`，**不拒绝**（第一步只观测）。

### D-8　存档同步　—— 用户 2026-09-21 拍板「需要存档同步的」；客户端 ✅ v0.19.425，服务端 ✅ v0.19.426，⚠ 对玩家生效要等发信服务

**为什么要做**：D-3b 核实出服务端五张表没有一张存玩家存档 ⇒
绑邮箱只能找回账号、找不回龟和装备。玩家说「绑定邮箱」时期待的是后者。

**方案**：
- 新表 `saves(account_id pk, payload jsonb, save_rev bigint, client_version, updated_at)`，
  RLS 只能读写自己的，**没有 delete 策略**（删号走 `auth.users` 级联）。
- 服务端函数 `push_save(payload, expected_rev, client_version)`：
  **在服务端原子地比较并交换** —— 云端当前版本 ≠ 我上次见到的 ⇒ 拒绝并返回冲突。
  ★判新旧**只看版本号，不看时间戳**：设备时钟不可信
  （memory 记过「28 个字段的重置时刻全由设备时钟定」那一类）。
- **只有绑了邮箱的账号才同步**。匿名 = 本机，隐私面更小，也不存一堆永远取不回的数据。
  绑定成功那一刻立刻推一次。
- 什么进云：`_save_dict()` **减去设备本地键** ——
  音量 / 全屏 / 画质 / `install_uid` / `account_id` / `account_email` /
  `auth_refresh` / `cloud_rev`。★`account_id` **永远不许从云端存档里读**，
  身份只来自登录。
- 何时推：`GameState.save()` 标脏 → 20 秒一拍 + 切后台时推一次；内容没变（哈希相同）不推。
  ★挂在 `save()` 上而不是逐个挂「打完一局 / 买东西 / 换装备」——
  逐个挂必然漏一个（memory「手抄的副本必然落后」）。
- 取回（换设备）：验码成功 → 拉云端存档 →
  有 ⇒ **先把本机存档备份成 `savegame.before-recover-<时刻>.json`** 再整体替换；
  没有 ⇒ 把本机的推上去。确认框里写清「这台设备现在的进度会被换掉」。
- 冲突（两台设备交替玩）：服务端回冲突 ⇒ **停推** + 设置页提示
  「云端存档和这台设备的不一样」+ 二选一（用云端的 / 用这台的覆盖云端），
  **各自写清会丢什么**。不做合并 —— 合并游戏状态没有安全做法。
- 隐私政策补一节：存档是**新的数据类别**，GDPR 要求写明存什么、为什么、存多久、怎么删。

**实测依据**：真实存档 10,467 字节 / 54 个字段，最大的是 `match_history`（5,384 字节，
代码里已封顶 50 条）⇒ 几百个玩家合计几 MB，免费档 500 MB 绰绰有余。

### D-3c / D-8 的已知风险与未决点（2026-09-21）

1. **客户端权威**：玩家改了本地存档再推上去，服务端分辨不出来。单机进度本来就是
   客户端说了算，这不新增风险面；但作弊存档打出来的阵容会进鬼影池 —— D-5 账目校验才是缓解。
2. **冲突只能二选一**，没有合并。两台设备交替玩的人会丢掉其中一边的一段进度（会提示）。
3. 推送最多晚 20 秒：刚打完一局就被杀进程，云端落后一局（本机文件不受影响，下次开机补推）。
4. **refresh_token 轮换的窗口**：拿到新令牌、还没写盘就崩了 ⇒ 下次开机拿旧令牌去刷 ⇒
   超过约 10 秒的重用宽限会被拒 ⇒ 匿名号失效（绑了邮箱的能用邮箱找回）。
   写盘紧跟在拿到令牌之后，窗口只有一次文件写入那么长。
5. **后台改动需要凭据**：建 `saves` 表、改邮件模板都要后台权限。本机目前**没有**任何
   Supabase 后台凭据（09-20 建项目时的数据库密码没留）。一次性拿一个 Personal Access Token
   之后，这两件与以后所有后台改动都能走 Management API 在后台完成，不用再碰浏览器。
6. 匿名老用户迁移时 `account_id` 会变一次 —— 他们在服务端的鬼影与榜单记录挂在旧 id 上。
   只影响 v0.19.420~423 的测试包，且这几版的后端本来就只工作了第一个小时。
