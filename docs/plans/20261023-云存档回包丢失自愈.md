# 云存档「回包丢了 ⇒ 永久冲突」自愈

日期：2026-10-23　|　状态：已完成（客户端；随下一个包生效）

## 1. 需求原文

- 用户 2026-10-22（LouisT01 #F5ZRDR 设置页截图：已绑定邮箱、云端同步已开启）「查一下呢」—— 云端存档自 10-17 起没再更新。
- 2026-10-23「你自己查那个问题」

## 2. 调查（改之前的现状，代码实查）

- 用 pymobiledevice3 从手机沙盒拉出存档：`savegame.before-recover-1792707733.json`（10-22 22:22 UTC 邮箱登录取回前的本机存档）里 `cloud_rev = 440`。
- 正式服 `public.saves` 这个号是第 **441** 版，`client_version 0.19.570`，`updated_at 2026-10-17 00:27 UTC`，内容是上一周（周锚 10-12、等级 8）的进度；本机已是本周（周锚 10-19、等级 6）。
- ⇒ 第 441 版就是这台手机自己推上去的，但手机没记下新版本号。`push_save` 是比较并交换：之后每一推都带期望 440 ⇒ 服务端回「冲突，云端 441」⇒ 客户端停推、等玩家去设置页二选一，没有任何别的提示。
- 推送在切后台时也会触发（`GameState._notification` → `maybe_push_save(true)`）；iOS 切后台会挂起 / 杀掉进程 ⇒ 服务端已经提交、回包没回来，正是这个形状。
- 邮箱登录取回之后同步恢复正常（手机现在 `cloud_rev = 473`）。

## 3. 需求 ↔ 代码的出入

- 设计上把「冲突」当成「另一台设备推过」；但「自己推的、回包丢了」也会走到同一个分支，而且是永久的。

## 4. 方案

- 新文件 `scripts/net/save_own_write.gd`；`supabase.gd` 只加 7 行挂钩。
- 每推之前把「账号 + 期望版本号 + 这一推的内容指纹」落盘（`user://cloud_push_unacked.json`，进程被杀也记得；同一期望版本号的多推都记）。
- 推送成功 ⇒ 清掉记录。冲突且云端版本 = 期望 + 1 ⇒ 拉云端那份比指纹：是自己发过的 ⇒ 认下版本号、标脏，下一拍接着推；不是 ⇒ 真冲突，照旧停推；没拉到 ⇒ 不下结论，下一拍再推再查。
- 指纹按线上形态归一（序列化 → 解析一遍再哈希），服务端存的就是请求里的 `p_payload` 原样。

## 5. 已知风险与未决点

1. ⚠ 只覆盖「冲突版本 = 期望 + 1」：回包丢了之后又有别的设备推过，就仍是真冲突（这时本来就该让玩家选）。
2. ❓ 真冲突仍然只在设置页提示（「处理存档冲突」），不打开设置就看不到；这次不改，等用户定要不要主菜单也提示。
3. ⚠ 服务端没改；如果 jsonb 改写了某种数字格式导致指纹对不上，退化成原来的「冲突」行为（不会更糟）。
