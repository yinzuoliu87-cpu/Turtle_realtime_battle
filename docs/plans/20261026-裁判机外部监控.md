# 裁判机外部监控 + 整机失联自动软重启

日期：2026-10-26　|　状态：**实施中**

## 1. 需求原文

2026-10-25 裁判机整机断网之后，我提议加外部监控，问用户要不要带自动重启：

- 用户：「你觉得怎么样」
- 我：建议做；倾向带自动重启（只在确实整机失联时）。
- 用户：「你自己看」

⇒ 范围由我定：**外部探活 + 报警 + 整机失联时自动软重启**。下面凡是数字（间隔 / 阈值 / 限频）都是我的建议，不是用户原话。

## 2. 调查结论

**事故（2026-10-25，详见 memory `ref-hetzner-referee-server`「故障记录」）**：

- 10:09 UTC 机器非正常重启（`last -x` 里上一次开机后没有 shutdown 记录；当天 unattended-upgrades 只升了 zlib、没重启，内核没变）。
- 10:17:46 起整机网络断：`systemd-resolved` 开始降级、外来包不再进、裁判 4 线程心跳停。
- 11:3x 我装 0.22.1 时 SSH 超时才发现（`referee_backlog()->workers.seen_sec` = 4742，约 79 分钟）。用户同意后 Hetzner API 软重启，10 秒后恢复。

**现有的健康检查为什么没报**：

- `turtle-referee-health.timer` 每分钟跑 `referee_poller.py --health`（`server/referee/README.md`「运维」一节），**跑在同一台机器上**，失败只进 journald（`systemctl status turtle-referee-health`），没有任何对外通知。整机断网时它自己也连不上库（实测日志 10:29:05 `Temporary failure in name resolution`）。
- 外部没有任何东西在看这台机器。

**可用的外部信号**：

- `https://stream.turtlearena.xyz/healthz`（Caddy，`server/stream/README.md`；memory 记 200）—— 整机断网时打不开。
- 心跳表 `public.referee_workers(worker, versions, seen_at)`（`server/supabase/schema.sql:2746`），由轮询器每轮写（`schema.sql:2980`）。但读它的 `referee_backlog()` 只授权 `service_role`（`schema.sql` 该函数后 `revoke … from public, anon, authenticated`）⇒ 外部拿不到。
- 心跳表里可能留着历史线程名（换过 WORKERS / 线程名的旧行不会删）⇒ 用「**最新**一次心跳距今」判机器活着，不用「最旧」。

**PostgREST 版本闸**：`pgrst.db_pre_request = public.check_client_version`（`server/supabase/migrations/20261019_min_version_gate.sql:102`）—— 外部调用要带 `X-Client-Version` 头，否则 426。

## 3. 需求 ↔ 代码的出入

- 我 10-25 说「Hetzner 令牌只让它用在重启这一个动作上」—— **不成立**：Hetzner Cloud API 令牌只有「只读 / 读写」两档，按项目授权，不能限定到某个动作。能保证的只是**脚本只调 reboot**。已在 10-26 回复里更正。
- 本机没有 `gh` / GitHub token（CLAUDE.md §6）⇒ 我**加不了仓库 Secrets**。`HCLOUD_TOKEN` 要用户自己在 GitHub 网页上填；没填之前工作流只报警、不重启（照常跑，不红在「缺密钥」上）。

## 4. 方案

| # | 改动 | 文件 |
|---|---|---|
| A | 新迁移：`public.referee_health()` —— 只返回几个数：最新心跳距今秒数、180 秒内有心跳的线程数、排队数、最老排队秒数。`security definer`，授权 `anon`。不暴露任何玩家数据 / 线程名 / 版本列表 | `server/supabase/migrations/20261026_referee_health.sql` + `tests/20261026_referee_health_check.sql` + `schema.sql` 末尾同段 |
| B | 探活脚本：两个信号（healthz / 心跳）→ 纯函数 `decide()` 给结论；失联则复查一次；确实整机失联才软重启 | `tools/referee_watch.py`（`--selftest` 量 `decide()` 全部分支） |
| C | GitHub Actions 定时跑 B（每 10 分钟 + 手动） | `.github/workflows/referee-watch.yml` |

**判据（`decide()`）**：

| healthz | 最新心跳 | 结论 | 动作 |
|---|---|---|---|
| 200 | ≤ 300 秒 | 正常 | 无 |
| 200 | > 300 秒 或 0 个新鲜线程 | 程序挂了、机器在 | 报警（工作流红），**不重启** |
| 打不开 | ≤ 300 秒 | 只有 Caddy / 直播口有问题 | 报警，不重启 |
| 打不开 | > 600 秒 | **整机失联** | 隔 180 秒复查，仍失联 ⇒ 软重启（限频见下）+ 报警 |
| 心跳读不到（库连不上 / 426） | — | 监控自己的问题 | 报警，不重启 |

**限频**：重启前查 Hetzner `GET /servers/{id}/actions`，最近 60 分钟内有过 reboot / reset / poweron ⇒ 不再重启，只报警。不在 GitHub 那边存状态。

**报警渠道**：工作流 `exit 1` ⇒ GitHub 给最后改过定时语法的人（= 用户账号）发失败邮件。Job Summary 写清哪一项失败、有没有自动重启。

## 5. 已知风险与未决点

- **R1 GitHub 定时不准**（未堵）：高峰时 schedule 会晚 5～15 分钟、偶尔跳过一次。最坏约 20～30 分钟发现。比现在（无人发现）好得多。
- **R2 重启那一刀没有实弹验过**（未验）：不能为了测而重启正式服。`decide()` 与限频逻辑由 `--selftest` 全分支量过；Hetzner `GET actions` 只读那一半实跑过；`POST reboot` 本身只验了请求形状（10-25 手工调过同一个接口）。
- **R3 令牌权限过大**（未决·接受）：`HCLOUD_TOKEN` 是项目读写令牌，能删机器。放在 GitHub 加密 Secrets 里，只有本仓库工作流能读，日志自动打码；脚本只调 `GET actions` 与 `POST reboot`。
- **R4 误重启**（已堵）：两个独立信号同时失联 + 180 秒复查 + 60 分钟限频。正常的版本发布 / Caddy 重载都不会同时让心跳停 10 分钟。
- **R5 失败邮件刷屏**（未堵）：断网期间每 10 分钟一封。接受（断网本来就该被吵醒）。
- **R6 用户还没填 HCLOUD_TOKEN**（未决）：没填就只报警。要用户在 GitHub 仓库 Settings → Secrets and variables → Actions 里加。
- **R7 内测服不在监控里**（接受）：内测服周末本来就由 `beta_peak_guard` 停掉，心跳停是常态；只看正式服。
