# 主站 × 小游戏 对接约定

版本：2026-11-06　|　状态：待主站确认　|　上线目标：2026-11-16（周一）

本文给主站开发者，写清楚两边各做什么、接口怎么约定。接口路径和字段是我方建议，主站有现成规范的可以提出修改。

## 1. 分工

两个产品只互通三样东西：**账号、玩家持有的龟、龟的等级**。

| 事项 | 主站 | 小游戏 |
|---|---|---|
| 账号 | 账号主体，提供登录 | 一一对应地存一个账号 |
| 龟与等级 | 唯一账本：拥有、抽取、升级、经验 | 只读，打周赛时上报经验事件 |
| 擂台赛开轮、停轮 | 决定并通知小游戏 | 按通知执行 |
| 撮合、对战、裁判 | 不参与 | 负责 |
| 战果 | 接收、查询、自己的业务处理 | 保存并发给主站 |
| 看录像 | 内嵌小游戏提供的网页播放器 | 提供播放器 |

小游戏**不显示也不接收**主站的积分、余额或任何结算信息。

玩家想打擂台赛必须安装小游戏（iOS 或安卓 APK），因为阵容在小游戏里配置。

## 2. 账号

### 2.1 建号互相同步

| 触发 | 动作 |
|---|---|
| 玩家在主站注册 | 主站调 `POST 小游戏/mainsite/account`，小游戏建好对应账号（玩家没装 App 也建） |
| 玩家在小游戏首次进入 | 小游戏调 `POST 主站/game/account`，主站建号并赠送一只小龟 |

两个接口都要幂等：同一个对方账号 ID 重复调用，返回同一个结果。

请求带昵称和头像；小游戏建号失败时会重试，玩家在此期间可以正常玩。

### 2.2 已有主站号的玩家登录小游戏

做法与电视、桌面软件登录账号相同，玩家不需要手动输入任何码：

1. 玩家在小游戏点「用主站账号登录」。
2. 小游戏生成一次性登录码（5 分钟有效），用**系统浏览器**打开 `主站/game/link?code=XXXXXX`。
3. 玩家在主站完成登录（主站现有的 Google、微信等方式都可用），点「确认登录小游戏」。
4. 主站调 `POST 小游戏/mainsite/link/confirm`，传登录码和主站用户 ID。
5. 小游戏一直在轮询，收到确认后切换到这个账号。玩家回到 App 就是登录状态。

必须用系统浏览器：Google 登录不支持内嵌网页。换手机找回账号走同一个流程。

**主站要做：** 一个确认页，一次回调。

### 2.3 删号

任意一边删号，都要通知对方同步处理。接口待双方约定。

## 3. 龟与等级

- **查询：** `GET 主站/game/users/{user_id}/pets`，返回 `[{pet_id, level}]`。龟的 ID 两边相同。
- **数量：** 主站目前 11 只，以后同步到 28 只。按 ID 对应，不写死数量。
- **等级范围：** 1～10。
- **周限免：** 每个号每周 7 只 1 级限免龟，由小游戏计算，自己拥有的不在其中。
- **经验：** 周赛每局裁判算完，小游戏调 `POST 主站/game/exp`，上报 `{match_id, user_id, pet_id, won, mode}`；主站按自己的规则换算并设上限。幂等键为 `match_id + pet_id`。

以下情况**不上报经验**：
- 限免龟。
- 擂台赛的所有对局（擂台局等同切磋，没有任何成长）。

## 4. 擂台赛

### 4.1 流程

1. 主站调 `POST 小游戏/mainsite/arena/open`，传 `{run_id, user_id}`，表示这个号可以开始一轮。
2. 玩家打开小游戏，点「准备」确认阵容。阵容在此刻锁定。
3. 小游戏把玩家放进队列，后台等待，玩家可以离线。
4. 配到对手后由裁判机算出结果。
5. 小游戏调 `POST 主站/game/arena/result` 发送战果。
6. 主站在回复里说明这一轮继续还是停止（见 4.3）。继续就自动排下一场，阵容不变。

### 4.2 规则

| 项目 | 规则 |
|---|---|
| 开放时间 | 周二 00:00 到周日结束（UTC）；周一休赛 |
| 参加条件 | 玩家已选龟并打完本大轮第一场 |
| 对局性质 | 等同切磋：按锁定时的阵容和进度打，打完没有任何成长 |
| 配对 | 只配本大轮总场次相同的玩家，先到先配，等多久都不放宽 |
| 不配对 | 同一设备的两个号；陪练号 |
| 同一对手 | 有其他人在等时不连续配同一对手 |
| 换周 | 周一 00:00 UTC 所有进行中的轮结束 |

### 4.3 接口

**战果（小游戏 → 主站）** `POST 主站/game/arena/result`

```json
{
  "match_id": "uuid",
  "run_a": "主站的 run_id", "user_a": "主站用户 ID",
  "run_b": "主站的 run_id", "user_b": "主站用户 ID",
  "winner": "a",
  "replay_url": "https://…",
  "finished_at": 1794000000
}
```

- `winner` 为 `a` 或 `b`。对局没有平局。
- 裁判出错或超过 30 分钟没有结果时，`winner` 为 `null`，这一场作废，由主站决定如何处理。
- 幂等键为 `match_id`，同一场重复发送只处理一次。
- 发送失败时小游戏按退避重试。

**主站的回复**

```json
{ "run_a": "continue", "run_b": "stop" }
```

小游戏据此决定是否继续排下一场，所以**不会多打一场**。

**停轮（主站 → 小游戏）** `POST 小游戏/mainsite/arena/stop`，传 `{run_id, reason}`。正在进行的这一场打完才停。

**一轮结束（小游戏 → 主站）** `POST 主站/game/arena/run-ended`，传 `{run_id, reason}`，用于小游戏主动结束的情况。`reason` 包括 `week_end`（换周）、`lineup_invalid`（阵容不再合法，例如版本更新删了装备）、`pet_lost`（玩家不再持有这只龟）。

**查询（主站 → 小游戏）** `GET 小游戏/mainsite/arena/runs/{run_id}/matches`，用于对账。

### 4.4 录像

小游戏提供轻量网页对局播放器，主站内嵌 `https://…/player?match={match_id}` 即可。

## 5. 陪练号

小游戏有一批陪练号（目前约 286 个）用于周赛撮合。

- 小游戏批量调用建号接口时带 `bot: true`。
- 主站为它们建**空账号**：不送龟、不发通知、不进排行榜和运营统计。
- 陪练号在主站没有任何行为，也不参与擂台赛。
- 陪练号的龟和等级由小游戏自己管理，不查主站，也不上报经验。

## 6. 接口通用约定

- **鉴权：** 服务器之间互相调用，用共享密钥做 HMAC-SHA256 签名，带时间戳，时差超过 5 分钟拒绝。
- **密钥：** 内测和正式各一套，不进代码仓库。
- **格式：** JSON，时间一律 UTC 秒。
- **幂等：** 所有写接口都要幂等，收到重复请求返回与第一次相同的结果。
