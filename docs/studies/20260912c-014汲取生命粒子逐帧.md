## 第二版做出来了，1:1 实拍仍然不合格

粒子系统接上之后，实拍读成 **一坨白色亮片**。
量下来是**两个互相独立的毛病**，一个是配色、一个是尺寸——两条都不是"觉得不好看"，是量出来的。

### ⓐ 配色串档：`jade` 是薄荷青，不是绿

素材走 `pixelize_sheet` 重索引，我挑了 `jade` 板。烤出来的色分布：

| 色 | 占比 | 板上身份 |
|---|---|---|
| (110, 200, 148) | **79.4%** | jade 主绿 |
| (58, 150, 104) | 11.1% | jade 暗绿 |
| (184, 232, 200) | 6.3% | jade 浅绿 |
| (238, 250, 240) | 3.2% | jade 高光 |

`jade` 板自己的注释就写着「**薄荷青（偏蓝绿）**」。而战场上：

- 龟的**身体是青色**、龟壳是暗绿（实测底色 (47,111,55) / (13,96,48)）
- 台子按真机参数开着泛光（`VFXLAB_GLOW=1`）

⇒ 薄荷青粒子 **和龟本身同色系**，再被泛光一糊，1:1 下根本认不出"这是绿色的粒子"。

**判据形状**（memory `fb-judge-must-fit-the-shape`）：光说"g 通道最大"卡不住 —— jade 的 g 也最大。
区别在蓝：

| | g − r | b − r |
|---|---|---|
| jade 主色 (110,200,148) | +90 | **+38**（蓝明显高于红 ⇒ 偏青） |
| life 主色 (104,244,112) | **+140** | **+8**（蓝红几乎相等 ⇒ 正绿） |

⇒ 门禁判据 = `g − r ≥ 100` 且 `|b − r| ≤ 25`。两条**都**能把 jade 判红（已实测）。

新加的 `life` 板亮度阶梯仍照 gold 那组（247/210/189/140/95/65），只换色相，所以和其它板放同一画面里明暗层级一致。

### ⓑ 贴图被压 3.4 倍

这一条**不是看出来的，是染色量出来的**（CLAUDE.md「染色法」）：把 `_mote` 整体 `modulate` 成品红、
关掉泛光（黑场无 bloom 才是量测基线），再数品红连通域。

```
f12 t=29.60s  品红 122 px  连通域 2 个  最大 (120, 16, 16)
f13 t=29.70s  品红 263 px  连通域 10 个 最大 (28, 7, 7)   ← 爆发的 10 粒，各 7×7
```

**一粒在屏幕上只有 7×7 像素，而贴图一格是 24×24。**

像素画非整数倍缩放 = 像素网格被打烂，这是本项目像素风三条硬约束之首
（`scripts/scenes/battle/battle_ballistics.gd:675`）。菱形 + 四芒的结构在 0.3 倍下全被丢掉，
只剩最亮的芯 —— 于是 ⓐ 的薄荷青 + ⓑ 的糊，合起来就是「白色亮片」。

**标尺是同一帧里量的**（不是从别处抄的数）：

- 一只龟在屏上 ≈45 像素高，立绘帧高 = `TARGET_BODY_H` = 2.0 m
- ⇒ 台子（1280×720 · zoom=1.0）下 **≈23.5 屏幕像素/米**，即 **1 屏幕像素 = 0.0426 m**

> ⚠ 这个数**随视口高度变**。别处文件里写的 28.148 px/m 是另一档视口量的，两边都不算错；
> 真正与分辨率无关的说法是下面这条 ——

⇒ 定成 **一粒 = 0.511 m ≈ 四分之一个龟高**，贴图一格 **12px** ⇒ `pixel_size = 0.0426` ≈ **1 texel : 1 屏幕像素**。

## 拍点：台子那一串是错的，已改

台子原先登记的 `shots` 是 `38.0 … 43.7` —— **只有 5.7 秒，比 8 秒的汲取周期还短**，
而实拍量到这一局第一次汲取在 **≈29.0 秒**（叠满 25 层硬化的时刻随挨打节奏浮动，
同一个台子连跑三次量到 **29.0 / 29.05 / 29.6**）。

⇒ 那一版拍点**必然什么都拍不到**，而"什么都没拍到"极容易被我读成"特效没做出来"——
今天已经因此误判过三次（013 的刺、020 的哑铃、014 的汲取）。

已改成 **28.0 ~ 36.2 每 0.2 秒**（跨 8.2 秒 > 周期 8 秒），**结构上保证至少罩住一次**。

## 门禁与反向验证

`tests/verify_drain_stream.gd`（19 条）量的全是**真实产出**：从 `_world` 捞出新建的 `Sprite3D`，
读它贴图里的真实像素、读 `pixel_size`、手推它自己的 tween 量位置与 alpha。

六条变异逐条反向验证，**各红在各自的判据上**：

| 变异 | 红在 |
|---|---|
| M1 素材退回 jade 薄荷青 | ② 主色是绿的（g−r=90 < 100） |
| M2 尺寸退回 17 码 | ④ pixel_size 0.0340 ≠ 0.0426 |
| M3 摆幅归零＝直线 | ⑥ 飘舞：弧垂 0.18 m < 0.35 |
| M4 退回一出生就淡 | ⑥ 淡出病：飞到一半 alpha 0.00 |
| M5 粒子只剩 3 粒 | ① 分母：少于 8 粒连不成一道波纹 |
| M6 爆发半径归零 | ⑦ 爆发：半径 0.00 → 0.00 |

### 反向验证自己也踩了两个坑，写在这里

**① 判据一开始没卡住形状。** 「飘舞」第一版量的是「粒子到起点—终点直线的垂距」——
把摆幅 `DRAIN_WAVE` 改成 0（＝退回直线）之后**照样绿**，因为粒子在①抽取那一步本来就会
左右扇开一段（那是"抽"不是"飘"）。改成量**这一粒自己的轨迹弯不弯**：三点采样，
看中点离「首尾两点连成的弦」有多远（弧垂）。直线的话中点贴在弦上。

**② 素材还原之后没真的还原。** `shutil.move` **保留 mtime** ⇒ 还原后的文件时间戳比上一次导入还旧
⇒ Godot `--import` 判"没变"直接跳过 ⇒ `.ctex` 里留着的还是变异版素材。
结果 M2 / M3 / M6 三条报的全是 **jade 的颜色**，而它们改的根本不是颜色。
⇒ 还原三件套：回写 + `os.utime` + 删 `.md5` 强制重导，**再跑一次基线证明真的回来了**。
（同族：memory `fb-restore-mutations-after-reverse-verify` / `fb-replaced-asset-needs-reimport`）
